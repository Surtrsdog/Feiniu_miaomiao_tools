> 状态：**已实装**（v2.1）。
> 代码：计算在 `akcalc/core/sandbox.py`，界面在
> `akcalc/ui/sandbox_panel.py`，渲染在 `akcalc/ui/map_render.py`
> 的 `_draw_sandbox()`。
> 目标读者：以后要改这个功能的人（大概率还是我）。

## 〇、实装后回填：方案里猜错/猜对的地方

写这份方案时列了三个「硬难题」（§3）。实装后逐条对照：

| 难题 | 方案里的判断 | 实装结论 |
|---|---|---|
| 干员会不会让敌人绕路 | 「大概率不会，要验证」 | **确实不会**。main_16-11 上把整列干员摆满，全部 8 条路线的 `total_time`/`total_length` 与空图**逐位相同**。所以 `operators` 永不进 `blocked`。 |
| 减速怎么算时间 | 「按段积分，不能整体乘」 | **正确**。0.5 倍速下 `32.00s -> 48.00s`（倍率 1.50 而非 2.00），因为 122s 的 pre_wait 一分不动，只有移动段翻倍。 |
| 箱子改变路径的代价 | 「每次都要重算，可能卡」 | **不卡**。`analyze_all` 单次 0.83 ms（main_16-11，8 条路线），放箱子即时重算完全无感。 |

还有一个方案里没写、实装才发现的问题：

* **缓存键**。渲染器按 key 决定是否重烘焙静态底图（约 60 ms）。
  沙盘的所有棋子必须走动态层，key 里**只**加
  `self.sandbox is not None` 这一个布尔。否则每放一个箱子整张底图
  重建，拖动石块肉眼可见地掉帧。

## 一、这个功能到底是什么

用户的原话是「模拟沙盘的纸上谈兵功能」——本质上是一个
**不 fighting 的棋board**：

- 不播伤害、不算 DPS、不做自动化；
- 用户自己在图上摆干员、踢敌人、加减速；
- 工具只负责三件事：**画出来**、**算路径**、**算数值**。

换句话说，它不是一个「战斗模拟器」，而是一个
**带实时寻路反馈的图板**。这个定位很重要，因为它决定了
哪些东西**不做**（见 §5）。

用户明确列出的能力清单（逐条对上）：

| # | 用户要求 | 归到哪个模块 |
|---|---|---|
| 1 | 选中敌人给状态 | 敌人棋子 |
| 2 | 手动去掉敌人（模拟被击杀） | 敌人棋子 |
| 3 | 手动部署干员、放在地图上 | 干员棋子 |
| 4 | 不做交互（干员不攻击） | 全局约束 |
| 5 | 只在选中干员时显示攻击范围 | 干员棋子 |
| 6 | 手动踢掉敌人 | 同 2 |
| 7 | 给敌人加减速（填数值 + 持续时间） | buff 系统 |
| 8 | 干员落地可模拟阻挡 | 阻挡判定 |
| 9 | 打到一半可手动摆放敌人棋子 | 敌人棋子 |
| 10 | 摆干员棋子模拟剩下的一半思路 | 干员棋子 |
| 11 | 像国际象棋 | 交互风格 |
| 12 | 棋子干员不攻击 | 同 4 |
| 13 | 能不能杀用户拿数据自己算、杀掉就手动踢掉 | **不做自动战斗** |
| 14 | 摆箱子影响路径时要重新模拟路径 | 寻路联动 |

第 13 条是整个需求里最关键的一句：**「能不能杀用户拿数据自己算」**
——用户自己拿干员面板和敌人面板去心算，工具**不代劳**，
只负责在踢掉敌人时同步显示。这直接把工作量砍掉一大半。

## 二、难度评估（先说结论）

**总难度：中等偏低**，远低于「战斗模拟器」，高于「加个图层」。

核心原因是基础设施已经就位：

| 已有能力 | 位置 | 沙盘能不能直接用 |
|---|---|---|
| 地图解析（地形/可通行/门） | `core/maps.py` | ✅ 直接复用 |
| 敌人路径求解 | `core/routes.py` `analyze_all` | ✅ 直接复用 |
| 单点最短路 | `core/pathfinding.py` `find_path` | ✅ 直接复用 |
| 敌人位置推算 | `core/timeline.py` `positions_at` | ✅ 直接复用 |
| 地图绘制 | `ui/map_render.py` | ⚠️ 需要加棋子层 |
| 鼠标命中检测 | `ui/map_canvas.py` | ✅ 已有 hover/click |

**实测性能**（`main_10-11`，43 条路线）：

- 全量 `analyze_all`：**5.1 ms**
- 带 `blocked` 集合重算：**6.0 ms**

这个数字决定了架构：**每次用户放一个箱子，直接整张图重算就好**，
不需要增量更新、不需要缓存失效逻辑。6 ms 在人类感知里是「瞬间」。

**核心可行性已实测通过**（`a001_02` route[1]）：

```
放箱子前  [(3,5), (3,4), (3,3), (4,2), (4,1), (5,0)]
箱放(4,2) [(3,5), (3,4), (4,3), (5,2), (5,1), (5,0)]
```

路径确实绕开了箱子重新规划——这就是沙盘需要的全部「智能」，
而且它已经能用了，一行 `analyze_all(gm, blocked={...})` 就够。

真正的难点**不在性能，在三个语义问题**（见 §3）。

## 三、三个真正的难点

### 难点 1：路径被改变后，「已经走了一半的敌人」怎么办

这是整个沙盘唯一有歧义的地方。

场景：敌人 12 号已经走到地图中间，用户在它前方放了个箱子。
这时 12 号应该：

- (A) 从**当前位置**重新寻路到终点；
- (B) 无视箱子，继续走原路线；
- (C) 从当前位置重新寻路，但**保留已经走过的时间**。

游戏里的真实行为是 (A)：敌人被阻挡时会切换到「Return」行为，
从当前位置走向终点（见 PRTS〈作战机制〉）。所以沙盘应该选 **A**。

**但 A 有个坑**：`analyze_all` 是按「起点 → 终点」整条算的，
它不知道敌人现在在哪。要支持 A，必须在沙盘里维护
**每只敌人的「当前所处段」**，然后只对「当前位置 → 终点」这一段
调用 `find_path`。

实现上不难（`find_path` 本身就是点对点的），但需要新增一个
`resume_from(route, current_pos)` 的辅助函数——**这是唯一需要
新写的核心逻辑**，估计 40~60 行。

### 难点 2：干员阻挡到底怎么判定

用户说「干员落地可模拟阻挡」，但**不要求**模拟「谁挡住谁」的
完整战斗。

⚠️ **这里有一个必须说清楚的事实，否则整个功能会做错方向：**

> **干员不会改变敌人的行进路线。**
> 游戏里只有**道路障碍物（Roadblock）**和**静态障碍物**会被纳入
> 寻路计算，干员的阻挡是「碰撞级」的——敌人照原路走过来，
> 撞到干员才停下开打，**不会提前绕路**。
> 出处：[PRTS〈作战机制〉](https://prts.wiki/w/%E4%BD%9C%E6%88%98%E6%9C%BA%E5%88%B6)、
> [wiki.gg `Pathing`](https://arknights.wiki.gg/wiki/Pathing)。

所以 §1 表里第 8 条「干员落地可模拟阻挡」和第 14 条
「摆箱子影响路径时要重新模拟路径」是**两种完全不同的机制**，
沙盘必须分开实现：

| 摆放物 | 对路径的影响 | 沙盘怎么做 |
|---|---|---|
| 干员 | **无**（路线不变） | 只画在图上；用于判定「会不会撞上」 |
| 箱子（Roadblock） | **有**（重新寻路） | 传给 `blocked`，跑 `analyze_all` |

也就是说，**只有箱子走 `blocked`，干员绝不能进 `blocked`**。
如果把干员也塞进 `blocked`，沙盘会画出「敌人绕开干员走」——
这与游戏行为相反，属于**错误的模拟**，比不做还糟。

干员在沙盘里的正确用途（符合用户「纸上谈兵」的定位）：

1. 画出占位和攻击范围，让用户自己判断「够不够得着」；
2. 标出「路线与干员格的重叠点」，提示这里会触发阻挡；
3. 至于挡几秒、打不打得死，**用户自己算**（§1 第 13 条）。

**不需要**实现「阻挡数」概念，v1 连重叠判定都可以只做高亮。

### 难点 3：减速 buff 怎么作用于时间

用户要求「手动给敌人加 buff，只包括减速类，可填数值和持续时间」。

作用点很明确：`RouteAnalysis` 的每段都有 `time`，
减速就是**把某段时间乘以系数**。但要注意：

- 减速是**按倍率**还是**按绝对值**？游戏里 `move_speed` 是倍率
  （0.5 = 半速），所以用倍率；
- 持续时间到了要**自动恢复**，所以沙盘需要一个「时间轴上的 buff 区间」，
  而不是一个布尔标记；
- 多个减速叠加时的公式游戏里是**乘法**（0.5 × 0.5 = 0.25），
  但同一来源不叠加。

方案：沙盘维护 `buffs = [(enemy_idx, start_t, end_t, mult)]`，
算位置时按区间积分。这一段需要重写 `pose_at` 的一个变体
（`pose_at_with_buffs`），估计 50~70 行。

**已验证的一个坑**（`a001_02` route[0] 实测）：

```
              move_speed=1.0   move_speed=0.5
移动段 time        8.83 s          17.66 s     ← 精确 2.00 倍
pre_wait(罚站)   122.00 s         122.00 s    ← 完全不变
total_time       130.83 s         139.66 s    ← 只涨了 6.8%
```

所以**减速只作用于「移动段」，罚站是常量**。如果沙盘图省事
直接拿 `total_time` 去乘倍率，会得出「减速 50% 后 261 秒到达」
这种离谱结果。必须按段积计时：

```python
total = pre_wait + sum(seg.wait_after + seg.time / mult)
```

这也意味着：对一条罚站 122 秒、走路 8.8 秒的路线，
减速在体感上几乎无效——这是**真实存在的游戏现象**，
沙盘应该如实反映，而不是替用户「修正」。

## 四、界面方案

### 4.1 布局：不要新开一个页面

沙盘应该**长在寻路分析页上**，作为一个模式开关：

```
┌─────────────────────────────────────────────────┐
│ 寻路分析                          [ 推演模式 ]  │  ← 新增开关
├──────────────┬──────────────────────────────────┤
│              │                                  │
│  出怪表      │           地图 canvas             │
│  （可点击）   │   · 敌人棋子（圆点 + 编号）       │
│              │   · 干员棋子（方块 + 职业色）     │
│              │   · 箱子（×）                     │
│              │   · 选中棋子时：攻击范围高亮       │
│              │                                  │
├──────────────┴──────────────────────────────────┤
│ 时间 ──────●────────────────  120s              │  ← 复用现有滑块
│ [踢掉选中] [加减速] [放箱子] [清空推演]          │  ← 新增工具条
└─────────────────────────────────────────────────┘
```

为什么复用寻路页而不是新建页面：

1. 沙盘的**全部输入**（地图、路线、时间轴）寻路页已经有了；
2. 用户的心智模型就是「在寻路图上推演」，切页面反而割裂；
3. 新建页面要重做一遍缩放/平移/悬停，纯属浪费。

### 4.2 三种棋子

| 棋子 | 画法 | 交互 |
|---|---|---|
| 敌人 | 沿用现有圆点（已带编号悬停） | 单击选中 → 显示「踢掉」「加减速」 |
| 干员 | 圆角方块 + 职业色 + 名字首字 | 单击选中 → 显示攻击范围；再点空地=移动 |
| 箱子 | 灰色 × | 点空地放置；**放置后触发路径重算** |

**三者对路径的作用完全不同，这是最容易做错的地方**：

- 干员：**不影响路径**，只做占位 + 攻击范围 + 「会在这里被挡」的提示；
- 箱子：**影响路径**，放下去立刻 `analyze_all(gm, blocked=boxes)`；
- 敌人棋子：只是标记，不影响任何计算。

**攻击范围**：干员数据里有 `rangeId`，但沙盘不需要精确到格子——
用户说「只在选中干员时显示攻击范围」，所以画一个**半透明色块**
标出大致范围即可。如果要精确，`ranges.json` 里有现成的格子表。

### 4.3 交互约束（用户明确要求「像国际象棋」）

- 一次只选中一个棋子；
- 选中态有明显描边；
- 点空白处取消选中；
- **不做**拖拽（拖拽和「点两下移动」在 Tk canvas 上实现成本差 3 倍，
  收益却很低）。

## 五、明确不做的部分

这一节比「做什么」更重要，防止后续无限扩张：

| 不做 | 原因 |
|---|---|
| 自动战斗 / 伤害结算 | 用户原话「能不能杀用户拿数据自己算」 |
| 干员攻击动画 / 弹道 | 同上 |
| 敌人反击 / 阻挡数消耗 | 属战斗逻辑，v1 不碰 |
| 费用回复 / 部署 CD | 沙盘不模拟时间压力 |
| 自动推荐摆位 | 那是求解器，不是沙盘 |
| 多存档 / 分享 | 和「纸上谈兵」定位无关 |

## 六、实现路径（分三步，每步可独立交付）

### 第 1 步：数据层（不碰界面）

新增 `core/sandbox.py`：

```python
class Sandbox:
    """沙盘状态：棋子、箱子、buff、已踢掉的敌人。"""
    def __init__(self, game_map, analyses, timeline): ...
    def place_operator(self, row, col, op_id, facing) -> None
    def place_box(self, row, col) -> None
    def remove_enemy(self, enemy_key) -> None
    def add_slow(self, enemy_key, mult, duration) -> None
    def blocked_tiles(self) -> set          # **只有箱子**，不含干员！
    def recompute(self) -> List[RouteAnalysis]   # 调 analyze_all
    def pose_at(self, enemy_key, seconds) -> (row, col)
    def overlap(self) -> set                # 路线与干员格的重叠点
```

关键点：`recompute()` 就是

```python
RT.analyze_all(self.game_map, blocked=self.boxes_only())
```

**一行**。这是整个方案里最省事的地方，因为 `analyze_all`
本来就是纯函数、支持 `blocked`、而且只要 6 ms。

⚠️ 方法名故意写成 `blocked_tiles` 会误导——它**只能装箱子**。
建议直接命名 `boxes_only()`，从命名上堵死「顺手把干员加进去」这条路。
干员的占位单独存 `self.operators`，永远不参与寻路。

`overlap()` 是干员唯一的「功能」：算出哪条路线会经过干员格，
在地图上打一个红圈提示「这里会发生阻挡」。不改变路线，只做提示。

### 第 2 步：渲染层（加三个 draw 函数）

在 `ui/map_render.py` 里加：

- `_draw_operators(im)` —— 方块 + 职业色 + 首字
- `_draw_boxes(im)` —— 灰色 ×
- `_draw_range(im, op)` —— 选中干员的半透明范围
- `_draw_sandbox_enemies(im)` —— 复用现有的 `_draw_enemies`，
  只是数据源换成沙盘状态

渲染层要注意：**沙盘棋子不能进 `_build_base()` 的缓存 key**，
否则每次移动棋子都要重画整张底图（底图有地形、网格、机关，
是重活）。棋子必须画在**动态层**，和敌人圆点同类。

### 第 3 步：交互层

在 `ui/map_canvas.py` 里加：

- 命中检测：已有的 hover 逻辑扩展成「命中棋子」
- 三种模式：`select` / `place_op` / `place_box`
- 工具条按钮绑定

## 七、工作量估算

| 步骤 | 内容 | 估计 |
|---|---|---|
| 1 | `core/sandbox.py`（含 `pose_at_with_buffs`） | 4~6 小时 |
| 2 | 渲染三个函数 | 2~3 小时 |
| 3 | 交互 + 工具条 + 模式切换 | 3~4 小时 |
| 4 | 联调 + 边界（瞬移、飞行、罚站） | 2~3 小时 |
| | **合计** | **11~16 小时** |

按一个工作日 6 小时有效编码算，**大约 2~3 个工作日**。

难度分布很不均：**第 1 步占了一半工作量**，因为要处理
「从当前位置续算」和「减速区间」两个语义问题。第 2、3 步
基本是照着现有代码抄。

如果**砍掉「从当前位置续算」**（即箱子放下去后，所有敌人
一律从起点按新路径重算，不保留进度），第 1 步能压到 2~3 小时，
总量降到 **7~10 小时**。这个取舍取决于用户能接受多少失真：

- 保留续算：放箱子后，已经走过一半的敌人会「就地转向」，
  最贴近游戏；
- 砍掉续算：整图重算，已走过的敌人会跳回起点重新走，
  看着很怪，但**不影响用户判断「新路径长什么样」**。

考虑到用户反复强调「几乎所有交互由用户自己脑测」，
**v1 建议直接砍掉续算**，把精力放在摆得顺手、看得清楚上。
真需要续算时再补。

## 八、最容易翻车的地方

1. **瞬移路线**。`RouteAnalysis.teleports` 里记着传送段，
   `pose_at` 遇到瞬移是直接跳过去的。沙盘如果按「当前位置续算」，
   碰到瞬移点必须特殊处理，否则敌人会「穿墙」重算出一条新路。

2. **飞行单位**。飞行敌人不吃地面阻挡，放箱子对它们**无效**。
   沙盘必须按 `route.motion_mode == "FLY"` 分流，否则用户会觉得
   「我放了个箱子怎么它还是直着飞」。

3. **罚站（WAIT_FOR_SECONDS）**。这段时间敌人在原地不动，
   减速 buff 对它**没有意义**（速度乘以系数，但你没在动）。
   `pose_at` 里要把罚站段单独拎出来，别把减速乘进去。

4. **缓存 key**。`_build_base` 的 key 里如果混进沙盘状态，
   每放一个箱子会重画整张底图，帧率直接崩。

5. **多敌人同格**。现有 `_draw_enemies` 已经用圆周偏移错开了，
   沙盘棋子要沿用同一套，否则一堆敌人叠在一起点不中。

## 九、和现有功能的关系

| 现有功能 | 关系 |
|---|---|
| 寻路分析 | 沙盘是它的**超集**，共用 canvas 和时间轴 |
| 时间轴播放 | 沙盘模式下**暂停**自动播放，改由用户拖滑块 |
| 伤害面板 | 完全独立，沙盘不调用 |
| 数据字段图鉴 | 独立 |
| 状态机图鉴 | 独立（但沙盘将来可以显示干员技能状态） |

## 十、结论

**可以做，而且比听起来简单。**

真正的工作量集中在 `core/sandbox.py` 一个文件里，界面部分是
在现有 canvas 上加三个绘制函数和一个模式开关。核心的
路径求解已经现成，性能也完全够（6 ms 全量重算）。

建议：**先做第 1 步**，用脚本跑通「放箱子 → 路径改变」和
「加减速 → 到达时间变长」两件事。这两件事一件跑通，就说明
整个方案成立；跑不通，界面做得再漂亮也没用。
