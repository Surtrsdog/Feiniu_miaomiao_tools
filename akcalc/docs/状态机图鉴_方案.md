# 状态机描述图鉴 · 设计方案

> 状态：**仅方案，未实装**。本文只做设计论证，不含任何程序改动。
> 目标是先在纸面上把「状态机图鉴」该长什么样、数据从哪来、坑在哪说清楚，
> 下个版本再按这份文档落地。

---

## 一、为什么要单独做一个「状态机」图鉴

现在工具里已有的图鉴是**静态属性表**：

| 图鉴 | 回答的问题 | 数据源 |
|---|---|---|
| 干员图鉴 | 这个干员面板多少攻击、几个技能 | `operators.json` |
| 敌人图鉴 | 这个敌人多少血、多少防 | `enemy_database.json` |
| 数据字段图鉴 | 这个字段是什么意思、怎么用 | `codex_fields.json` |
| 伤害计算 | 打一下掉多少血 | `core/damage.py` |

它们都隐含一个假设：**干员和敌人是「一个数」，不是「随时间变的机器」**。

但这个假设在实战里经常失效。最典型的三类问题，现在的面板一个都答不了：

1. **「这个干员几秒能开出技能？」**
   面板能算出技能期间 DPS，但算不出**第一次开技能的时刻**——
   这取决于初始 SP、SP 回复方式（自然/攻击/受击）、是否被自回速限制。
   一个 `initSp=75 / spCost=90 / 自然回复` 的真银斩，答案是
   **第 15 秒**回满（`(90-75)/1.0`）；第二轮起要等满 90 秒。
   这中间的落差（15 秒 vs 90 秒）正是面板看不出来的东西。

2. **「这个敌人在第 40 秒是走还是停？」**
   敌人被动里藏着 `stun`、`sleep`、`bind`、`speed` 之类的状态修正。
   现在寻路分析把它们当成一条恒定速度的轨迹，而实际在
   留声机、传送门、冰冻源附近，敌人的速度会**跳变**。

3. **「这个技能开完之后还剩几发子弹？」**
   `durationType=AMMO` 的 39 个技能（天空大扫除、近身铳斗……）
   不按时间结束，按**弹药数**结束。「持续 30 秒」和「打完 8 发」
   是两个完全不同的生命周期。

一句话：**现有图鉴描述「是什么」，状态机图鉴要描述「怎么变」。**

## 二、状态机到底要建模哪几层

不要试图一次把整个战斗都建成状态机——那会变成一个游戏引擎，
既做不完也测不了。建议按**三个互相独立、可以分别上线**的层次切：

### 层次 A：干员技能生命周期（优先级最高）

状态集合很小，而且完全由解包数据决定：

```
        部署
         │
         ▼
   ┌───────────┐   SP 满 & 手动   ┌───────────┐
   │  CHARGING │ ───────────────▶ │  READY    │
   │  (充能中)  │                  │ (可开启)   │
   └───────────┘                  └───────────┘
         ▲                              │ 点击
         │ 技能结束                      ▼
   ┌───────────┐                  ┌───────────┐
   │  COOLDOWN │ ◀─────────────── │  ACTIVE   │
   │  (冷却中)  │                  │ (技能中)   │
   └───────────┘                  └───────────┘
```

**关键：`CHARGING` 和 `COOLDOWN` 在游戏里是同一个状态。**
解包数据里 `initSp` 只管开局那一次，之后每次都是 `spCost`。
如果图鉴把它们画成两个框，用户会以为「技能结束后要从 0 重新攒」——
其实是从 0 攒没错，但**开局那次是从 `initSp` 起步**，这两者必须
在图上标注清楚，否则算「第几次开技能」会差一整个周期。

以真银斩为例，同一个 `CHARGING` 状态在两个阶段长度完全不同：

| 阶段 | 时长来源 | 实际值 |
|---|---|---|
| 第一轮从部署到可开启 | `spCost - initSp` = 90 − 75 | **15 秒** |
| 之后每一轮 | `spCost` = 90 | **90 秒** |

6 倍的差距，而现有的伤害面板对此一无所知。

这个层次的输入字段（全部已在 `skill_table_full.json` 里）：

| 字段 | 取值 | 含义 | 坑 |
|---|---|---|---|
| `skillType` | `MANUAL` / `AUTO` / `PASSIVE` | 手动点 / 满了自动开 / 被动常驻 | `PASSIVE` 也带 `spData`，但 SP 无意义 |
| `spData.spType` | `INCREASE_WITH_TIME` / `INCREASE_WHEN_ATTACK` / `INCREASE_WHEN_TAKEN_DAMAGE` / `8` | 自然回 / 攻击回 / 受击回 / **不回** | **`8` 是整数，不是字符串**，用 `== "..."` 判断会全部漏掉 |
| `spData.spCost` | 数值 | 每次开启消耗 | `spType==8` 时有 618/635 是 0，属正常 |
| `spData.initSp` | 数值 | **仅**开局初始 SP | 不是每轮都有 |
| `spData.increment` | `1.0` / `0.0` / `3.0` | 每次回复的量 | 有 403 条是 0（不回复） |
| `spData.maxChargeTime` | `0`–`5` | 可蓄力次数 | 0 = 不支持蓄力；蓄力时 `spCost×n` 才够 |
| `durationType` | `NONE` / `AMMO` | 时间结束 / 打完弹药 | `AMMO` 共 39 条 |
| `duration` | `30.0` / `-1.0` / `0.0` | 持续时间 | **`-1.0` 表示无限（574 条）**，不是「持续 1 秒」 |

> ⚠️ `duration = -1.0` 和 `duration = 0.0` 必须分开处理。
> 真实分布：`0.0` 620 条、`-1.0` 574 条、`30.0` 129 条……
> 把 `-1` 当成 0 会让「无限持续技能」显示成「瞬间结束」。

> ⚠️ 更隐蔽的一点：**`AMMO` 技能的 `duration` 也是 `-1.0`**
> （天空大扫除 `durationType=AMMO, duration=-1.0`）。
> 所以判断「这技能什么时候结束」**不能看 `duration`**，必须先看
> `durationType`：
> - `NONE` + `duration=-1.0` → 真正无限，只能手动关
> - `NONE` + `duration=30.0` → 30 秒自然结束
> - `AMMO` → 时长由弹药数决定，`duration` 无关紧要
>
> 弹药数在描述里是 `{attack@trigger_time}` 占位符，需要从 `blackboard` 取值。
> 拿不到时图鉴应显示「弹药数未知」而不是回退到 `duration`。

### 层次 B：敌人受控/加速状态

敌人的状态**不是自己产生的**，是被机制和干员技能施加的。
所以这一层更像「状态叠加表」而不是「状态图」。

下表的「实测出现次数」是从 1829 条技能的 `blackboard` 里数出来的
（`grep` 全量 token 键）。**没有实测支撑的条目不要凭印象加进来**
——`bind`（束缚）和 `slow`（减速）在 `blackboard` 里是 **0 次**，
写进图鉴只会给出一个永远查不到数据的字段。

| 状态 | 来源 | 效果 | blackboard 键 | 实测次数 |
|---|---|---|---|---|
| 眩晕 | 干员技能、地图机关 | 停止移动与攻击 | `stun` (+ `attack@stun` 等变体) | **575** |
| 沉默 | 干员技能 | 禁用敌方技能 | `silence` (+ `attack@silence`) | **40** |
| 睡眠 | 干员技能 | 停止一切，受击解除 | `sleep` (+ `attack@sleep`) | **50** |
| 冰冻 | 冰冻源机关 | 停止，抗性相关 | `frozen` / `freeze` | **13** |
| 移速修正 | 各类减速/加速 | 速度乘算 | `move_speed` | **193** |

> ⚠️ 键名极不统一：眩晕至少有 `stun`、`attack@stun`、`attack@s2_stun`、
> `attack@s3_stun`、`attack@stun_main`、`stun_time`、`stun_duration`、
> `stun_prob` 等 10 余种写法。**不能写 `bb["stun"]` 这种精确查找**，
> 必须用「键名包含 `stun`」的子串匹配，并且**区分 `_prob`（概率）、
> `_duration`（时长）、裸键（时长）** 三种语义，否则会把
> 「眩晕概率 30%」当成「眩晕 30 秒」。

这一层与现有的 `core/interactions.py`（`EnemyInteraction` /
`SpeedModifier`）天然衔接——它已经在抽速度修正了，只差把
**时间轴**接上去。注意 `interactions.py` 现在只有 `speed_mods`
和 `auras` 两个列表，**没有眩晕/冰冻这类硬控**，那是从干员技能的
`blackboard` 来的（见上表）。两者需要合并成一份「某敌人在 t 时刻
受到哪些状态」的查询，而不是各算各的。

### 层次 C：地图机制驱动的状态

传送门、留声机、源石祭坛……这些已经在
`core/mechanisms.py` 里做过了（391 certain / 58 inferred / 1 no-exit）。
**这一层建议直接复用 `mechanisms` 的结论，不重复建模**，
只在图鉴里加一段「本关有哪些机制、它们在第几秒触发」。

## 三、界面形态：不要画流程图，要画「时间条 + 状态色带」

这里是最容易做错的地方。第一直觉是画一个 Graphviz 那样的方框箭头图，
但那对用户没用——用户想知道的是**「第 30 秒时这个干员在干什么」**，
不是「状态之间有哪几条边」。

建议的呈现：**横向时间轴 + 纵向状态行**，也就是把状态机「展开」成甘特图。

```
干员 银灰 · 真银斩  (MANUAL, 自然回 SP 1.0/秒, initSp=75, spCost=90, 持续 30s)
部署时刻记为 0s

 SP   ▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
      75/90 满
      ├──15s──┼────30s────┼──────────────90s──────────────┤
 时间  0s     15s         45s                            135s
 状态 │CHARGING│  ACTIVE (真银斩)  │        COOLDOWN        │
      ├────────┼───────────────────┼────────────────────────┤
 攻击 │ 普通攻击 │    攻击力 ×3.0     │        普通攻击          │
      └────────┴───────────────────┴────────────────────────┘
             ▲ 用户在这里点技能（可拖动）
             └ 第一轮只要 15s（initSp=75），之后每轮都要 90s
```

> 注意「READY」是一个**瞬时点**而不是一段：SP 满了就停在满值等用户点，
> 所以它在时间轴上没有宽度。上图为了看得见才单独标了一下。
> 第一轮 `CHARGING` 是 15 秒，而已 `COOLDOWN` 是 90 秒——
> 这个 6 倍差是面板完全体现不出来的，也是这个图鉴最大的价值点。
> 从部署到「第 2 次可开启」是 135 秒（15 + 30 + 90）。

这样做的三个好处：

1. **「技能时机」变成一个可拖动的竖线**，用户能直观看到
   「早开 5 秒」和「晚开 5 秒」分别损失多少覆盖时间。
   这和现有寻路分析里拖动时间轴的交互是**同一套手感**，学习成本为零。
2. **状态色带复用现有配色**（`path_panel` 的播放条已经有一致色板）。
3. 不用引入图形库，用 Canvas 画矩形条即可，与现有
   `timeline_canvas.py` / `playback.py` 的实现方式一致。

### 面板要给出哪几个「硬数字」

光看图还不够，要配一小组可复制的结论：

- **首次可开启时间** = `max(0, (spCost - initSp) / rate)`
  （`rate` 按 `spType` 取：自然回=1.0/秒，攻击回=每次攻击，受击回=每次受击）
- **循环周期** = `spCost / rate + duration`（不含首轮）
- **技能覆盖率（稳态）** = `duration / 循环周期`
  真银斩：`30 / (90 + 30)` = **25%**
- **第 n 次可开启时刻** = `首次可开启 + (n-1) × 循环周期`
- **弹药类技能**改为「预计耗时」= `弹药数 / 攻速`，
  且**不套用上面的覆盖率公式**（弹药技能没有固定时长）

> 这几个公式都很简单，但**必须把假设写在旁边**：
> 「自然回 SP 按每秒 1 点计，不含天赋/模组加成」。
> 否则用户会拿它跟 PRTS 的实测值对不上，然后不信任整个工具。

## 四、数据从哪来（以及哪些地方必须做兜底）

### 4.1 已有、可直接用

> ⚠️ **先认清是哪个文件**：仓库里有两个技能表，
> `skill_table.json`（908 条，末级只有 `bb`/`desc`/`name`，**没有** `spData`）
> 和 `skill_table_full.json`（1829 条，**有完整的 `spData`**）。
> 状态机图鉴**必须用 `skill_table_full.json`**。
> `codex_fields.json` 里那条「skill_table.json 里同样没有 spData」
> 说的是前者，别被它误导。

| 需求 | 现成数据 | 覆盖度 |
|---|---|---|
| 技能 SP 结构 | `skill_table_full.json` → `levels[-1].spData` | 1829 条，全覆盖 |
| 技能类型 | 同上 → `skillType` | 全覆盖 |
| 持续时间 | 同上 → `duration` / `durationType` | 全覆盖 |
| 技能数值 | 同上 → `blackboard` | 200 个 token 已在 `codex_fields.json` 建档 |
| 敌人速度修正 | `core/interactions.py` | 已有抽取逻辑 |
| 地图机制 | `core/mechanisms.py` | 已覆盖 508 关 |

### 4.2 缺的，需要新建

**（1）干员的 SP 回复速率**
`spType` 只说「怎么回」，不说「每秒回多少」。
自然回复在游戏里是每秒 1 点（不含天赋），但**这个常数在解包里没有**，
必须硬编码并注明出处。

> 注意：敌人数据里**有** `attributes.spRecoveryPerSec`（每秒回复倍率，
> 1.0=正常，0=不回），但那是**敌人**的技力，不能拿来当干员的常数。
> 干员这一侧的 SP 速率在五个数据源里都没有。

**（2）攻击间隔 → 实际攻速**
已有 `attack_interval`，换算公式**已经存在**，不需要新写：

```python
# core/damage.py:197
def effective_attack_interval(t0, attack_speed=100.0):
    """实际攻击间隔 T = T0 / (clamp(S, 10, 600) / 100)。"""
    s = max(C.ATTACK_SPEED_MIN, min(C.ATTACK_SPEED_MAX, attack_speed))
    return t0 / (s / 100.0)
```

注意两个容易搞错的地方：
- 参数 `attack_speed` 的**基准是 100**（不是 0），`+30` 攻速传的是 `130`。
  `skilldata.extract()` 给出的 `attack_speed` 是**增量**（如 `30`），
  图鉴要自己加 100 再传进去，否则 `<30> / 100 = 0.3`，
  攻击间隔反而被拉长 3.3 倍。
- 有 `10 ≤ S ≤ 600` 的钳制，所以攻速堆到极端值会让曲线走平。

图鉴要把这个函数提为公共引用，不要再抄一遍公式。

**（3）「第几秒能打到人」**
这是**唯一真正难的部分**，因为它需要敌人位置数据。
好消息：寻路分析已经算出了每条路线的敌人位置时间序列
（`core/routes.py` / `core/timeline.py`）。
图鉴不需要重新算，**只要引用寻路分析的结论**即可。

> 建议：第一版**不做**「自动判断技能该在几秒开」。
> 那是策略推荐，属于另一个产品。图鉴只给出**时间轴和数字**，
> 让用户自己判断。

## 五、实现路径（建议分三步，每步都能单独交付）

### 第 1 步：纯数据层（不碰 UI）

新建 `core/statemachine.py`，只做三件事：

```python
@dataclass
class SkillCycle:
    name: str
    skill_type: str        # MANUAL / AUTO / PASSIVE
    sp_type: str           # 归一化后的字符串，整数 8 转成 "NONE"
    sp_cost: float
    init_sp: float
    increment: float
    max_charge: int
    duration: float        # -1.0 原样保留
    duration_type: str     # NONE / AMMO

    def first_ready(self, rate: float = 1.0) -> float: ...
    def cycle_length(self, rate: float = 1.0) -> float: ...
    def nth_ready(self, n: int, rate: float = 1.0) -> float: ...
```

**这一步必须做的事：把 `spType` 的整数 `8` 归一化。**
635 条技能会踩到这个坑，不处理就是「这些技能全部没有 SP 信息」。

### 第 2 步：图鉴页面（只读，静态时间条）

在 `ui/data_index.py` 里加一个 `StateIndexView(_IndexView)`，
跟 `FieldsIndexView` 同一套骨架。左侧列表列出所有带 SP 的技能，
右侧画时间色带。**这一步不接敌人、不接地图**，先把
「干员技能生命周期」这一层做扎实。

### 第 3 步（可选）：与寻路分析联动

在寻路分析里选中某个敌人时，叠加一条「该敌人受到的减速/眩晕」
时间带。这一步依赖前两步，且收益边际——建议先看第 1、2 步的用户反馈再决定。

## 六、必须提前定下的设计取舍

这几条如果事后再改，代价很大：

1. **`duration = -1.0`（无限）如何在色带上表示？**
   建议画成「延伸出画布外的箭头」而不是画满整条——画满会让人以为
   技能会自然结束。

2. **蓄力技能（`maxChargeTime > 1`，共 102 条）怎么画？**
   建议画成「叠起来的 n 个格子」，每满一格填一格，
   而不是把 `spCost × n` 当成一个大格子。

3. **被动技能要不要出现在时间轴上？**
   建议**出现，但画成贯穿全程的底纹**，而不是一个状态块。
   它的 SP 字段是无意义的（`spCost=0`），但用户需要知道
   「这个干员有一个常驻被动」。

4. **AUTO 技能要不要画「可开启」状态？**
   不需要。`AUTO` 没有「可开启」这个用户决策点，满了就自动进 `ACTIVE`。
   画出来反而误导。

5. **要不要显示「不算天赋加成」的警告？**
   要，而且要**显眼**。天赋带来的 SP 回复/初始 SP 加成没有进解包
   `spData`，图鉴给出的是**裸技能的基线**。

## 七、和现有功能的关系（避免重复造轮子）

| 现有模块 | 状态机图鉴如何复用 |
|---|---|
| `core/skilldata.py` | 直接复用 `extract()` 的倍率/连击解析，不重写 |
| `core/skills.py` | `SkillLevel` 已有 `cost`/`initial`/`duration`，是 `spData` 的上层封装 |
| `core/damage_type.py` | 复用，无需改动 |
| `core/interactions.py` | 敌人速度状态直接用它 |
| `core/mechanisms.py` | 地图机制层整个复用，不重建 |
| `ui/data_index.py` | 新增 `StateIndexView`，与 `FieldsIndexView` 同骨架 |
| `ui/timeline_canvas.py` | 色带绘制可参考现有实现 |

**唯一需要真正新写的是 `core/statemachine.py` 和 `StateIndexView`。**

## 八、结论与建议

- **值得做**，但**第一版只做层次 A（干员技能生命周期）**。
  层次 B（敌人受控状态）和层次 C（地图机制）在现有代码里已经各有实现
  （`interactions.py` / `mechanisms.py`），但它们是**为寻路分析服务的
  内部结构**，不是面向用户的图鉴。硬把它俩塞进新图鉴，会变成
  「同一件事两套逻辑」，维护成本翻倍。建议第一版先不碰，
  等层次 A 上线、确认用户真的需要「敌人第几秒被控」再补。
- **界面用时间色带，不要用流程图**。用户要的是「第几秒在干什么」。
- **先把 `spType == 8` 归一化**，这是 635 条技能的隐形地雷。
- **`AMMO` 技能不能按 `duration` 判断时长**（39 条，`duration` 恒为 `-1.0`），
  必须先判 `durationType`。
- **所有数字必须标注假设**（自然回 SP 1/秒、不含天赋），
  否则对不上实测就会失去信任。
- **第一版不做「推荐开技能时机」**。那是策略层，不是图鉴该回答的问题。

按上面第 1、2 步的拆分，预计新增代码约 400–600 行
（`statemachine.py` 约 200 行，`StateIndexView` 约 300 行），
不改动任何现有计算路径，风险可控。
