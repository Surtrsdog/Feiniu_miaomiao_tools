# 沙盘 / 路线分析 —— 数据解析修复记录

本文件记录「沙盘修正」这一轮里**已定位并修好**的数据层问题。
每一条都给了现象、根因、影响面（实测数字）和改法，便于以后回查。

---

## 1. `buildableType` 数字枚举没被识别 —— 102 个老关卡整图不可部署

**现象**：沙盘里选好干员右键格子，没有任何可部署位置。

**根因**：`buildableType` 在新关卡里是字符串（`"MELEE"`/`"RANGED"`/`"ALL"`/`"NONE"`），
在早期关卡里是数字（`1`/`2`/`3`/`0`）。解析时只认字符串，数字被原样留下，
于是 `buildable_melee` / `buildable_ranged` 全是 `False`。

全库原始分布：

| 取值 | 次数 |
|---|---|
| `'NONE'` | 144767 |
| `'MELEE'` | 52538 |
| `'RANGED'` | 23737 |
| `'ALL'` | 5816 |
| `0`（数字） | 5751 |
| `1`（数字） | 2158 |
| `2`（数字） | 1072 |
| `3`（数字） | 85 |

**改法**：`core/maps.py` 加 `_BUILD_BY_INT = {0:"NONE",1:"MELEE",2:"RANGED",3:"ALL"}`
和 `_norm_buildable()`，在构造 `Tile` 时统一归一化。

## 2. `passableMask` 数字枚举映射反了 —— 105 个关卡路线几乎全部不可达

**现象**：整关的敌人都画不出路线，或者路线乱穿墙。

**根因**：`_MASK_BY_INT` 写成了 `{0:"ALL",1:"FLY_ONLY",2:"WALK_ONLY",3:"NONE"}`，
与实机语义**正好相反**。正确是：

```python
_MASK_BY_INT = {0: "NONE", 1: "WALK_ONLY", 2: "FLY_ONLY", 3: "ALL"}
```

**效果**：修前这 105 个关卡可达率接近 0%；修后 **2923/2923 条路线 100% 可达**。
全库扫描 **89187/89240（99.94%）** 可达，只有 25 个关卡各有 1–3 条不可达。

## 3. `WAIT_CURRENT_FRAGMENT_TIME` / `WAIT_CURRENT_WAVE_TIME` 被当成秒数

**现象**：某些关卡的罚站时间离谱，时间轴被拉成一条直线。

**根因**：这两种检查点的 `time` 字段**不是时长**，而是「等到当前片段/波次结束」，
值只是占位（常见 600 / 220）。被当成字面秒数累加进路线总时长。

实测：
- `act18d3_ex08` R1：算出 600s，该片段实际最长跨度 60s
- `main_05-07` R1：算出 220s，实际 29.5s
- `ro1_b-7` / `ro1_b-8`：600 / 470
- `main_09-03`：220

**影响面**：458 条路线 / 86 个文件，另有 168 处「相邻两个 WAIT 相加」跨 45 个文件。

**改法**：`RoutePoint.is_duration_wait` 只在 `kind == "WAIT_FOR_SECONDS"` 时为真，
`core/routes.py` 与 `ui/map_render.py` 的停驻累加都加了这个门。

## 4. `WAIT_FOR_SECONDS` 的「永久站桩」哨兵值被当真

**现象**：用户报的「罚站时间混乱」——悬停显示「还剩 9999 秒」。

**根因**：部分关卡用极大值表示「这只怪一直站着别等了」。
全库 `WAIT_FOR_SECONDS` 取值分布有一条干净断层：

| 取值 | 次数 | 含义 |
|---|---|---|
| ≤ 600 | 1492 | 真实罚站 |
| 999 | 751 | 哨兵 |
| 1000 | 51 | 哨兵 |
| 3000 | 5 | 哨兵 |
| 9999 | 36 | 哨兵 |
| 99999 | 6 | 哨兵 |

**改法**：
- `core/models.py`：`WAIT_SENTINEL_MIN = 900.0`、`WAIT_SENTINEL_CLAMP = 600.0`、
  `clamp_wait_time()`；`RoutePoint.wait_sentinel` 保留「这是哨兵」的标记。
- `core/routes.py`：**按路线合计封顶**。一条线里可能有多个哨兵
  （`act26side_01` route0 是两段 999 秒中间夹巡逻），逐项钳完再相加仍有 1200s，
  所以只要线上出现过哨兵，就把停驻总量压到 600s。

修前修后：

| 关卡 | 修前 | 修后 |
|---|---|---|
| `main_14-03` | 10001.0s | 602.0s |
| `main_14-04` | 10014.7s | 615.7s |
| `hard_14-01` | 10009.0s | 610.0s |
| `act47side_08` | 1029.3s | 629.3s |
| `act26side_01` | 1241.3s | 641.3s |

全库最长路线 1414s，剩 9 条超 900s 的**全是肉鸽长巡逻图**
（`rogue3_b-6` 310 格、`rogue5_b-9-c` 407 格，带大量 15–30s 真实停驻），
属于数据实况，不是 bug。

## 5. `PATROL_MOVE` 被当成无坐标检查点 —— 巡逻点被静默丢弃

**现象**：巡逻型敌人的罚站全部算到起点，位置也不对。

**根因**：`POSITIONED_CHECKPOINTS` 只含 `MOVE` / `APPEAR_AT_POS`，
漏了 `PATROL_MOVE` 和 `MAP_OFFSET_MOVE`。这两个类型**是有真实坐标的**。

全库实测各类型「有真实坐标」占比：

| 类型 | 条数 | 有真实坐标 |
|---|---|---|
| `MOVE` | 254346 | 100.0% |
| `APPEAR_AT_POS` | 11328 | 100.0% |
| `PATROL_MOVE` | 2021 | 100.0% ← 原先漏了 |
| `MAP_OFFSET_MOVE` | 2 | 100.0% ← 原先漏了 |
| `WAIT_FOR_SECONDS` | 62084 | 8.2% |
| `WAIT_CURRENT_FRAGMENT_TIME` | 3919 | 11.0% |
| `WAIT_CURRENT_WAVE_TIME` | 560 | 0.5% |
| `DISAPPEAR` | 11237 | 7.0% |

**影响面**：29 个关卡 / 2021 条检查点。

**改法**：`POSITIONED_CHECKPOINTS` 补上这两个类型。
`act26side_01` route0 的 `pre_wait` 从 1200s 变成 0s，移动时间从 8.8s 变成 41.3s
（真实情况是中途在 (2,6)、(2,2) 巡逻后才停）。

## 6. `Route.index` 与列表下标混用 —— 52% 的出怪画错路线

**现象**：点「本关出怪」里某一行，地图上高亮的路线对不上。

**根因**：`Route.index` 有意保留**原始 JSON 下标**（出怪事件的 `routeIndex`
直接对应它，见 `path_panel.py` 的隔离逻辑）。但多处消费方拿它当
`gm.routes[]` 的列表下标用。E_NUM 路线被跳过后，两者就分叉了。

**影响面**：1980 个关卡存在错位；**81813/156723 条出怪（52.2%）** 画错线。

**改法**：`GameMap.route_by_index(index)`（先精确匹配 `Route.index`，
再退回列表位置），`map_render.py` 3 处 + `path_panel.py` 1 处改用它。
注意 `maps.py` 里 `r.index = i` **不能改**，那是设计如此。

## 7. `_load_enemies` 的缓存 key 少了两级回退 —— 1716 个关卡出怪列表空白

**现象**：用户报「部分关卡右侧没有本关出怪」。

**根因**：路线缓存 key 有三条候选（`rel_path` 去 `.json` → `level_id` →
`level_id` 取 `#` 前段），`maps.get_level` 和 `path_panel._load_timeline` 都实现了，
唯独 `_load_enemies` 只用 `level_id`。

**影响面**：1716 个关卡。细分：984 个需要 `rel_path`、721 个需要去 `#` 后缀、
11 个两者都要。（另有 920 个关卡根本没有地图文件，13 个解析出 0 只怪，
1872 个本来就是对的。）

**改法**：`path_panel._raw_for(level_id, rel_path)` 统一实现三条候选链，
`_load_timeline` 和 `_load_enemies` 都走它。

## 8. `isValid=false` / `hiddenGroup` / `randomSpawnGroupKey` 三个门控字段没读

**现象**：用户报「大部分地图会多出很多不符合实机的怪」，
举例 H8-4 多一组平民、纵怒多出数个领舞者。

**根因**：三个字段都会影响「实机这一局到底出什么」，原先全都没读：

| 字段 | 条数 | 涉及地图 | 含义 |
|---|---|---|---|
| `isValid=false` | 2202 | 95 | 这条出怪永不触发（废案） |
| `hiddenGroup` | 6961 | 744 | 同关互斥编队，实机只出一组 |
| `randomSpawnGroupKey` | 10680 | 584 | 随机候选包，按 weight 抽一个 |
| `weight`（非 0） | 15137 | 611 | 上者的权重 |

`hiddenGroup` 的实际取值：`raid` 1328、`normal` 1094、`copper_d` 461、
`fstar` 429、`shsdgo4` 326、`extra_enemy` 321、`calamity` 194 …

典型例子 `act1multi_06`：

```
hiddenGroup=normal  408 只
hiddenGroup=raid    446 只
hiddenGroup=None    101 只
合计                955 只   ← 原先全部列出
```

实机任一组最多约 509–547 只，所以界面看起来「多了一倍怪」。

**改法**：`SpawnEvent` 增加 `disabled` / `hidden_group` / `random_group`，
`Timeline.effective_events()` + `groups(effective=True)` 折叠互斥组
（自动挑「只数最多」的那组）+ 剔除废案。界面上加「按实机编队」开关，**默认开**。

实测：

| 关卡 | 原先行数 | 按实机编队后 |
|---|---|---|
| `act1multi_06` | 323 行 / 955 只 | 189 行 / 547 只 |
| `act36side_ex03` | 273 行 | 0 行（273 条全 `isValid=false`） |

`randomSpawnGroupKey` 的**加权抽取没有模拟**——那需要随机数，
而用户要的是「看这关有什么怪」，全列更有信息量。

## 9. `branches[]` 完全没解析 —— 5 个关卡出怪列表永久空白

**现象**：部分关卡右侧「本关出怪」永远空白。

**根因**：出怪只读 `waves[]`，没读 `branches[]`。`branches[]` 是
**装置/陷阱触发的条件出怪**，分支名就是触发它的装置 key：
`trap_068_badbox#1`、`summon_cjglon`、`mbx1`、`bonore_dfello1`、`fire` …

全库 744 个地图含 branches，共 4904 条 SPAWN 动作。其中 738 个地图 `waves`
本身也有怪（只表现为「少数怪漏了」），但下面 5 关**整关的怪全在 branches 里**
（`waves` 只有 `PLAY_OPERA` 之类演出动作）：

`act1dp_01` / `act1dp_02` / `act1dp_05` / `act1dp_ex04` / `act1dp_tr01`

**改法**：`parse_timeline()` 增加分支解析，每个分支**独立从 0 起算**
（不把不同分支的时间相加，那会造出不存在的顺序），结果标上
`SpawnEvent.branch = <分支名>`，`wave_index = -1`。

实测这几个关卡现在：

| 关卡 | 事件 | 列表行 | 分支数 |
|---|---|---|---|
| `act1dp_01` | 4 | 4 | 1 |
| `act1dp_02` | 11 | 11 | 8 |
| `act1dp_05` | 5 | 5 | 1 |
| `act1dp_ex04` | 5 | 5 | 1 |
| `act1dp_tr01` | 4 | 4 | 1 |

## 10. 空白列表要说清原因

空白本身有两种完全不同的成因，界面上必须区分，否则看起来都像解析失败：

- 数据里压根没有敌人（纯演出/机制关）
- 有敌人，但全被 `isValid=false` 标成废案；或全被「按实机编队」折叠掉

`_empty_spawn_reason()` 会给出具体原因，例如：

> （本关 273 条出怪全部标记为未启用 isValid=false，实机不会出怪；
> 取消「按实机编队」可强制列出）

## 11. 粗轴导出漏掉 `is_ranged` / `block_count` —— 高台干员换个机器就会被当成地面干员

**现象**：在 A 机把「W」（远程位）部署到高台，导出粗轴 JSON，拿到 B 机导入后，
W 变成「地面干员」，开始替玩家挡地面敌人，到达时间全偏。

**根因**：`core/sandbox_track.py` 的 `CoarseTrack.to_dict()` 只写了 `ground` /
`facing` / `skill` 等字段，`Deployment.is_ranged` 和 `block_count` **两边都没落盘**；
`_deployment_from_dict()` 自然也不会读回来，于是导入后 `is_ranged=False`、
`block_count=0`。

这两字段直接决定 `Deployment.blocking`：

```python
@property
def blocking(self) -> int:
    if self.is_ranged:
        return 0          # 远程位不挡地面敌人
    return max(0, int(self.block_count))
```

`OperatorPiece.blocks` 有同样的规则。所以漏掉它们的后果不是「显示不准」，
而是**沙盘的核心阻挡判定整条走错**。

**改法**：`to_dict()` 补写 `ranged`（仅真时）与 `block`（仅非零时），
`_deployment_from_dict()` 补读；老版本 JSON 没有这两个键时按 `ground == "HIGH"`
兜底推断，比一律当近战安全。

实测（`main_08-04`，银灰地面 + W 高台）：

```
导入前  W @(1,5) is_ranged=True  blocks=0
导入后  W @(1,5) is_ranged=True  blocking=0    ← 修复后
（修复前 blocking=1，会被当成能挡 1 只地面敌人）
往返字节一致: True
```

`test_full_regression.py` 新增第 [7] 组 7 项断言锁死这条行为。

## 12. 源代码栏从「描述 JSON」改成「技能指令」

**需求**：源代码栏显示技能实现的**具体指令**，而不是描述 JSON。

**先说结论（这条必须讲清，否则就是在骗人）**：解包数据里**没有**客户端脚本。
`enemy_database.json` 的一条技能只有三样东西——`prefabKey`（客户端注册的
行为类名）、`blackboard`（一袋数值）、`cooldown`/`initCooldown`。真正的执行体
（行为树 / 状态机）编译在客户端里，任何工具都拿不到。所以「显示官方指令」
这件事在数据层面不可能做到。

**能做到的最近似物**：把 `blackboard` 的键名按**行为语义**排成执行顺序。
`atk_scale` 必然发生在伤害结算、`duration` 必然描述持续时间、`cooldown`
必然是触发节奏——这种先后关系由游戏机制本身决定，不是猜的。

新增 `akcalc/core/skill_instructions.py`，按八个槽位合成：

```
触发条件 → 选取目标 → 产生单位/资源 → 投射物 → 结算效果 → 位移 → 技力 → 计时
```

每一步都带原始键名，可逐条回溯到解包原文。

**实测**：全库 **1773 条**技能条目（717 只敌人全部形态）**100%** 能合成出
至少一步，步数分布 `{1:652, 2:491, 3:338, 4:161, 5:86, 6:38, 7:6, 8:1}`。

真实样本（爱国者 `enemy_1506_patrt`）：

```
技能1 throwspear[Rage]
  1. 开局第 15 秒可首次施放，之后每 20 秒一次   [initCooldown / cooldown]
  2. 造成攻击力 1.35 倍的伤害                  [atk_scale]
```

**两个口径必须分开**（混着写会误导）：

| | 敌人 | 干员 |
|---|---|---|
| 触发键名 | `initCooldown / cooldown` | `initSp / spCost` |
| 单位 | **秒** | **技力点数** |
| 动词 | 施放 | 开启 |
| 文案 | 开局第 15 秒可首次施放 | 落地自带 15 点技力，攒满 35 点可开启 |

干员侧原本写成「开局第 15 秒」是错的——15 是技力不是秒数。

**其他刻意处理的细节**：

- `prefabKey` 的形态后缀要拆开：`Immo[Rage]` = 行为类 `Immo` 的狂暴变体，
  不拆会当成两个无关技能。全库只有 30 条带后缀（`[Rage]` / `[Half]` /
  `[reborning]` / `[Reborn]` 等 10 种）。
- `cooldown = 0` 不说成「每 0 秒一次」（那是废话），改说「无冷却：条件一
  满足就立刻触发，触发条件本身在行为类里」。
- 干员的 `prefabId` 填的其实就是技能 ID（`skchr_xxx_3`），不是行为类名，
  不能拿它去查行为词典报「词典未收录」，要改说「末段 `_3` 表示三技能」。
- 干员侧额外接上 `statemachines`（525 条生命周期）的 `impl` / `pitfall`，
  那是唯一真实存在实现描述的数据，和指令栏并列给出。

指令栏排在参数表**之前**（用户打开弹窗第一句问的是「这技能干啥」），
并明确写出「解包只有行为类名 + 数值袋，没有客户端脚本」——不谎称有实现。

`test_full_regression.py` 新增第 [8] 组 **15 项**断言（含干员/敌人两套口径）。

## 13. 粗轴导出丢了技能回转参数（悬停回转永远显示「可开启」）

**症状**：导出的粗轴 JSON 里，干员只留下一个 `"skill": "真银斩"` 的**名字**，
重建出来的 `SkillCycle` 是 `sp_cost=0 / init_sp=0`。因为
`SkillCycle.is_passive` 就是 `sp_cost <= 0`，于是这枚干员被当成**被动技能**，
`state_at()` 直接返回 `ready=True`——「悬停干员显示技能回转」这条需求
在**导入回来的**沙盘上等于失效，而当场部署的沙盘又是好的，很容易漏测。

**根因**：`to_dict()` 只写了 `skill_name`，`_deployment_from_dict()` 也只读
`skill`。名字是给人看的，真正驱动回转的是数值，两者被混成了一个键。

**改法**：新增 `skill_sp` 子对象落盘四个数值（`cost` / `init` / `dur` /
`recover`，`infer_attack` 为真时才写），`skill` 仍然保留技能名保持可读。
`recover` 是**字符串枚举**（`AUTO` 等）不是数值，导入侧统一按 `str` 读，
否则会变成 `'1.0'` 这种脏值。

**实测**（银灰三技能，spCost=35 / initSp=15 / duration=20）：

```
导出  "skill": "真银斩", "skill_sp": {"cost":35.0,"init":15.0,"dur":20.0,"recover":"AUTO"}
导入  SkillCycle(sp_cost=35.0, init_sp=15.0, duration=20.0, recover='AUTO')
      is_passive = False          ← 修复前是 True
往返字节一致: True
```

回转逐帧（部署于 t=10，自然回复 1 点/秒）：

| 时刻 | ready | sp | active | next_in |
|---|---|---|---|---|
| 12s | False | 17 | False | 18.0 |
| 25s | False | 30 | False | 5.0 |
| 40s | True | 0 | **True** | 10.0 |
| 55s | False | 5 | False | 30.0 |
| 70s | False | 20 | False | 15.0 |

t=30 充满、t=30~50 技能中、t=50 归零重攒，与 `spCost=35 / duration=20`
的规则完全吻合。老版本没有 `skill_sp` 的文件仍可读，行为退回「视为被动」。

## 14. 图鉴批注的「分别导入导出」原本没设防

**症状**：图鉴的敌人批注和干员批注各自有「导出 / 导入」按钮，导出时也各自
写了 `annotations_enemy.json` / `annotations_operator.json` 两个文件，看起来
完全分开了。但把干员批注的文件喂给怪物批注的导入按钮，会**静默成功**。

**实测**（`probe_annot_robust.py`）：

```
=== 把 operator 文件导入到 enemy（跨类误导入）===
  返回: (1, 0)  enemy count: 1
  enemy keys: {'char_172_svrash': {'text': '银灰三技能', ...}}
  !! 跨类污染：干员批注被写进了怪物批注
```

**根因**：`export()` 早就把 `"kind": "operator"` / `"kind_cn": "干员批注"`
写进了文件头（**纯粹是给人看的**，注释里写得很清楚），但 `import_()` 从头到尾
没读过这个字段。两边的 key 空间又完全不重叠——干员是 `char_172_svrash`，
怪物是 `enemy_1506_patrt`——所以合并时「同 key 取新」的规则一次都没触发，
所有干员批注被当成「别人的新批注」原样并了进来。

**为什么这个 bug 特别难发现**：批注列表是按当前图鉴的条目去反查的，
孤儿 key（图鉴里没有 `char_xxx` 这只怪）根本不会显示。用户点错文件后界面
毫无变化，只有导出时才会看到文件里多了一堆对不上号的条目。

**修复**（`core/annotations.py` + `ui/annotation_card.py`）：

1. `import_()` 读 `raw["kind"]`，和目标类不一致直接 `AnnotationError`：
   `这份文件是「干员批注」，不能导进「怪物批注」。它应当用「干员批注」那一栏的导入按钮。`
2. 老版本导出**没有** `kind` 字段——那种文件仍然放行。宁可兼容，也不把用户
   的历史备份锁死。
3. UI 侧原本是「问一句『确定继续吗』，答是就硬导」，改成直接 `showerror`
   并指出该导到哪一栏。既然底层已经硬拒绝，再问一遍只会把用户引到一个
   必定失败的流程里。

**保留的健壮性**（全部实测）：

| 输入 | 行为 |
|---|---|
| 坏 JSON | `AnnotationError: 「xx.json」不是合法的 JSON：Expecting ...` |
| 不存在的文件 | `AnnotationError: 打不开「xx.json」：[Errno 2] No such file` |
| 空文件 / 空 `entries` | 返回 `(0, 0)`，弹「没有可导入的内容」，不算错 |
| 不可写路径 | `AnnotationError: 写入不了「Z:\no\such\dir\x.json」：...` |
| 空白批注 | `set()` 返回 `False`，不写入、不计数 |

`test_full_regression.py` 新增第 [10] 组 **13 项**锁死：两类 key 不互串、
导出文件头带 `kind`、清空后各自导回、跨类导入被拒且不污染、无 `kind` 老文件
仍可导入、空白批注被拒。

## 15. 「部分关卡没有本关出怪」——是模板波次，不是解析失败

**症状**：部分关卡右侧出怪列表是空的。

**扫全库的结论**（2570 个关卡、93630 条 spawn action）：

```
managedByScheduler=True  isValid=<缺省>   -> 91173   ← 正常出怪
managedByScheduler=True  isValid=False    ->  2455   ← 全部集中在 95 个关卡
managedByScheduler=False isValid=<缺省>   ->     2
```

`isValid` **只有两种取值**：缺省（正常）与 `False`（废弃）。不存在「同一关里
一部分 False、一部分缺省」把筛选逻辑骗过去的混合情况——所以「全关 disabled」
可以放心地判定成「这一关确实不出怪」。

**这些关卡是什么**：抽查 `act15mini_01`（FD-1 繁荣滋长，冻原狩猎）、
`act16mini_01`（TG-1 双向通风，"下井"）、`act36side_ex03`，共同特征是

* `levelId: null`、`mapId: null`、`enemies: []`
* 出怪 **100% `managedByScheduler: true`**（波次由调度器驱动）
* `isValid: false` 覆盖全部波次
* `runes` 里带倍率类全局修正（`enemy_attribute_mul`、`global_cost_recovery_mul`）

也就是说：解包数据里躺着的是一份**模板**波次，实机由关卡脚本另行下发。
塔防小游戏式的迷你活动都是这个形状。

**措辞修正**（`ui/path_panel.py::_empty_spawn_reason`）：原来写「实机不会
出怪」，对这类关卡是过度断言——模板明明是活的，只是不走 `waves`。改成

> （本关 N 条出怪在解包数据里全部标记为未启用 isValid=false，属模板波次
> （多为迷你玩法关），实机由关卡脚本另行下发；取消「按实机编队」可把模板
> 原样列出来）

并且「取消按实机编队」确实能把模板列出来（`act15mini_01` → 19 组、
`act16mini_01` → 10 组），用户不会被锁在空白页上。

其余空表成因也各有专属文案，不会笼统显示「没有记录」：数据里压根没敌人
（纯演出关）、全被编队择一折叠（附分组名）、全被「撇除无害单位」隐藏。
`test_full_regression.py` 第 [11] 组覆盖。

## 17. 「H8-4 多出平民」——无害单位默认没折叠，但也不能一刀切

**症状**：H8-4 的出怪表里冒出 3 只「乌萨斯平民」。

**根因不是数据错**。`enemy_3001_upeopl` 确实在该关的 `waves` 里，带
`isUnharmfulAndAlwaysCountAsKilled: true`——它的含义是「不计入剩余敌人总数 /
歼灭数」，**不是「不出场」**。实机里平民会走出来、能被打、会挡路，只是不计数。
解包忠实记录了这一点，所以数据层没有 bug。

问题在**界面默认值**：`var_hide_harmless` 默认 `False`，3 条平民就和真敌人
混在一张表里，用户看到的就是「多出平民」。

**为什么不能直接把默认改成 True**。扫全库：591 个关卡含无害单位、共 8378 条，
其中 **38 个关卡的出怪 100% 都是无害单位**——`act1arcade_*`、
`act1museum_*`（多索雷斯博物馆系列，每关 34~142 条）整体系列都是。默认折叠
会把「多出平民」换成「这一关什么都没有」，从一个 bug 换到另一个 bug。

**修复**（`ui/path_panel.py`）：新增 `_auto_harmless_default()`，加载关卡后
按数据自适应——

```python
n_harm = sum(1 for e in evs if e.harmless)
self.var_hide_harmless.set(0 < n_harm < len(evs))   # 全害 → 折叠；全无害 → 保持
```

判据是「有真敌人才折叠」：`0 < n_harm < len(evs)`。

再加一条约束：用户亲手勾过这个框就置 `_harmless_touched = True`，换关时不再
被自动值顶掉——人手选的偏好比自动推断优先。

**实测**：

| 关卡 | 总事件 | 无害 | 自动默认 | 列表条数 |
|---|---|---|---|---|
| `main_08-04` H8-4 | 57 | 3 | **隐藏** | 24（提示「已撇除 3 个无害单位」） |
| `main_08-15` | 8 | 8 | 显示 | 8 |
| `act1museum_m1_01` | 109 | 109 | 显示 | 87 |
| `act1museum_m2_03` | 142 | 142 | 显示 | 64 |
| `main_07-16` | 45 | 0 | 显示 | 33 |

`test_full_regression.py` 新增第 [12] 组 **6 项**：H8-4 确实有平民、也确实有
真敌人、折叠后仍有 24 组且不含平民、全库确实存在 38 个「全无害」关卡、这类
关卡折叠后确实会变空（所以必须保持显示）。

## 18. 「悬停干员显示技能回转」原本只显示「技能中」

**症状**：悬停场上的干员，技能那一栏永远是「技能中」，SP 多少、还差几秒
一次都看不到。

**两层原因，都是真的**：

**第一层——悬停压根没接线。** `MapCanvas` 的 `on_object_hover` 只发两种
事件：`"enemy"` 和 `"tile"`（`map_canvas.py:476`）。干员站立格走的是
`"tile"` 分支，而 `SandboxPanel._hover_tile` 里对干员只有一行
`parts.append("干员 %s" % op.name)`——**名字，没有回转**。右键菜单那边
倒是有 `_skill_text`，它的 docstring 明写「右键菜单与悬停共用」，实际
只有右键在用。修复：`_hover_tile` 复用同一个 `_skill_text`，并补上阻挡数
（高台干员按 `is_ranged` 不显示），两处口径就此一致。

**第二层——默认技能选错了，选中的那个永远显示「技能中」。**
`_pick_operator` 取 `skills[0]`。银灰的第一个技能是「强力击·γ型」：
`spCost=2、duration=0`，属于 `is_continuous`（持续型）。
`SkillSim.state_at` 对这类技能**永远**返回 `active=True`——不是算错，
而是「持续型技能没有『技能中』之外的态」这件事本身为真。于是即使把
悬停接上了，看到的还是恒定的「技能中」。

修复：新增 `_default_skill_of()`，按「信息量」挑默认技能——

1. 有 `duration` 且有 `cost` 的主动技能（真银斩这类）：能同时看到攒 SP
   和技能持续，回转曲线最完整；
2. 有 `cost` 但无 `duration` 的（充能类）；
3. 被动 / 无 SP 的：放最后，它本来就没有回转。

同档内按 SP 从多到少（大招优先），再相同时保持原顺序。**全库 441 个有
技能的干员实测：0 个落到无 SP 技能，0 个在「还有带 duration 的主动技能」
时落到持续型。**

**顺手修掉一个会让逻辑静默失效的坑。** `_skill_cycle_of` 原本是实例方法，
`_default_skill` 里 `try: self._skill_cycle_of(...) except: return (3, 0.0)`。
一旦从类上调用（`SandboxPanel._default_skill(None, ...)`，测试和复用都会
这么写），`self` 是 `None`，异常被 `except` 吞掉，**每个技能都拿到
`(3, 0.0)`，`min()` 于是恒取第一个**——排序代码看起来在跑，实际完全没生效。
现在把这段抽成模块级 `_cycle_of()` / `_default_skill_of()`，实例上的
`_skill_cycle_of` / `_default_skill` 退化成薄壳，两条路走同一份实现。

**实测悬停文案**（`main_08-04`，银灰落 `(1,9)`，真银斩 90SP/30s、初始 75SP）：

| 时刻 | 悬停显示 |
|---|---|
| t=5 | 干员 银灰（朝右） 阻挡 2 · **SP 80/90，还需 10.0s** |
| t=20 | 干员 银灰（朝右） 阻挡 2 · **技能中，还剩 25.0s** |
| t=35 | 干员 银灰（朝右） 阻挡 2 · **技能中，还剩 10.0s** |
| t=60 | 干员 银灰（朝右） 阻挡 2 · **SP 15/90，还需 75.0s** |
| t=75 | 干员 银灰（朝右） 阻挡 2 · **SP 30/90，还需 60.0s** |

t=60 的 SP 15 而不是 90，说明技能结束后确实归零重攒（90SP / 3.0s 一轮 =
正好 15）。

**回归**：`test_full_regression.py` 第 [13] 组 **12 项**，含「干员技能能读到
（不是 0 个样本假通过）」这条——第一版测试用了 `PO.load_operator()`，它返回
的对象 `skills` 恒为空，那一组在 **0 个样本**上「通过」了。改用 UI 同一条路
（`OperatorCache.load(...).data` → `dict_to_op`）后才有 441 个真实样本。

## 19. 飞行敌人被当成地面单位 —— `SpawnEvent` 上根本没有 `flying` 字段

```python
ra = self.analysis_for(event)          # 提前取，下面罚站也要用
```

## 27. 修掉两个真实缺陷（出怪表行登记 / 空白原因谎报）

这两个是这轮**新查出来的真 bug**，不是需求列表里的条目。

### 27.1 出怪表的行从来没登记过 → 选中高亮复位不了

`_load_enemies()` 里画完出怪表后用的是**局部变量** `rows`：

```python
rows = []
for gi, g in enumerate(groups):
    rows.append(self._make_spawn_row(self.spawn_host, gi, g))
for gi, row in enumerate(rows):
    row.grid(...)
    self._spawn_tiles.append(row)
```

而 `_clear_isolation()` 靠实例属性 `self._spawn_rows` 复位每一行的边框：

```python
for row in (getattr(self, "_spawn_rows", None) or []):
    row.configure(highlightbackground=DIVIDER)
```

`self._spawn_rows` 全文件只有两处：`__init__` 里初始化成 `[]`，和这里遍历。
**它永远是空的**。于是点「清空地图上的路径线」之后，出怪表里被点中的那一行
边框一直是高亮色，看起来还在隔离状态。

修法：画完补一句 `self._spawn_rows = rows`。验证（`main_08-04`）：

| 关卡 | `_spawn_rows` | `_spawn_tiles` | `groups` |
|---|---|---|---|
| main_08-04 | 24 | 24 | 24 ✅ |
| act1arcade_m1_01 | 44 | 44 | 44 ✅ |
| main_08-15 | 8 | 8 | 8 ✅ |

修之前这三行全是 `0`。

### 27.2 勾着「撇除无害单位」就把任何空白都说成「全是无害单位」

原代码：

```python
if self.var_hide_harmless.get():
    return "（本关 %d 条出怪全是无害单位，已被「撇除无害单位」隐藏…）" % n_all
```

只看勾选状态，**不验证是不是真的全**。`main_08-04` 有 57 条出怪、
其中只有 3 个无害单位，一旦列表因为别的原因空掉，界面就会理直气壮地说
「57 条全是无害单位」——这是把成因说错，比只说「不知道」更坏，因为用户会
按这句话去取消勾选，然后发现列表还是空的。

修法：先比 `harmless_count >= n_all` 才说「全是」，否则如实报
「N 条里 M 个是无害单位、剩下的被其他筛选条件隐藏了」。

「部分无害」不许说成「全是无害」、模板波次关必须说 `isValid=false`
且不许谎称「没有出怪记录」。

### 30.2 导出时可以选到库文件自己，把库冲掉

1. 导出先把内存内容写进去——看起来成功了；
2. 之后任何一次 `flush()`（导入另一类时必然触发）拿内存里的旧表**再覆盖

### 31.1 `canvas.find_all()` 只有 1 个图元 ≠ 没画

地图**不是**用 `create_line` / `create_rectangle` 一条条画的：`MapRenderer`
用 PIL 把整帧烘成一张 `PhotoImage`，canvas 上只贴这一个 image 图元。
所以数图元条数永远是 1，写成 `len(find_all()) > 50` 必然假失败。

正确验法是看**像素**：

```python
im = cv._r.render().convert("RGB")
cols = sorted(im.getcolors(maxcolors=1<<24), reverse=True)
ratio = 1.0 - cols[0][0] / float(im.size[0]*im.size[1])
# 颜色 > 8 种且非主色占比 > 5% 才算真的画了东西
```

实测：沙盘 `1134x387`，3104 种颜色，非主色 **38.1%**；寻路 `640x480`，
8218 种颜色，非主色 **74.8%**。

### 31.2 窗口 `withdraw()` 之后渲染帧是空的

第一版探针为了不弹窗，先 `app.withdraw()` 再 `update()`。结果 canvas
尺寸是 **0**，渲染出来是一张零尺寸空图——又变成「看起来没渲染」。

必须给窗口真实尺寸：`app.geometry("1400x900+30+20")` 再 `update()`。
这条也写进了回归第 [21] 组，注释里明说「不能 withdraw」。

## 34. 随机候选包 `randomSpawnGroupKey` 一直被当成「全都要出」（累计多算 6869 只）

| `randomSpawnGroupKey` + `weight` | **同一次抽取的备选，按 weight 抽一条** | 10680 条 / 568 图 / 1354 包 |

前两个 `timeline.py` 早就处理了，第三个没有——`effective_events()` 的旧注释
还明确写着「加权抽取没有在此模拟……全列出来更有信息量」。这个取舍对
**研究**没错，对**核对实机编队**是错的：它把「N 选 1」直接显示成 N 只。

全库普查（`probe_randgroup_census.py`，2574 个缓存文件）：

```
含 randomSpawnGroupKey  568
受影响的包             1354
```

101 条/组 1 个、810 条/组 1 个。也就是说**大多数关只多算 1 只**（不易察觉），
少数关多算几百只（一眼就炸）。

### 34.2 用户报的「咩的朋友角兽罚站」其实是这个

### 34.3 折叠规则：不掷骰子，可复现

真按 weight 掷骰子会导致每次打开结果不同、粗轴存档对不上、回归没法断言。
所以**不模拟随机**，而是「每个包留一个代表」：

1. `weight` 最大的那条优先（权重高的更可能是常规编队）
2. `weight` 相同取 `count` 大的
3. 再相同取先出现的（`action_index` 最小的）

这样「本关有什么怪」不漏主角，只数也不翻倍，且**同一份数据永远同一结果**。

`Timeline.fold_random_packs()` 实现该规则，`effective_events()` /
`groups()` 新增 `fold_random` 参数（默认 `False`，保持旧行为，避免动到
已有的 251 项断言）。`random_pack_summary()` 给界面提供「N 选 1、期望 X 只」
的标注数据。

## 36. 排查过程中差点写错的两件事（留档，避免以后再踩）

### 36.1 `analyses[i]` 不能用列表位置下标

丢 `E_NUM` 剧情占位路线这件事（`models.py` 的 `route_by_index` 注释里写过，
全库 1980 关 / 81813 只出怪受影响）会让 `Route.index` 与 **列表位置** 脱钩。
H8-4 就是：原始 `routes[]` 52 条，丢掉 15 条 `E_NUM` 后只剩 37 条，但
`SpawnEvent.route_index` 仍是原始下标 0…51。于是：

```python
an = RT.analyze_all(gm)          # 37 条，紧凑排列
an[38]                           # IndexError —— 或者更糟：取到隔壁那条
```

必须写成 `route_by_index(...)` / `{a.route_index: a for a in an}`。
本轮把 `path_panel._pre_wait_of`、回归 [23] 组里几处按下标取的写法
统一改成按字段查，并加了断言把「H8-4 确有错位」这件事固定住。

顺带确认 `RouteAnalysis.total_time` **已含 `pre_wait`**
（120 + 18 + 5 = 143 ✓），所以算到达时刻是 `出场 + total_time`，
再加一遍 `pre_wait` 会重复计。
`Sandbox.arrival_time()` 返回的是**历时**，不是绝对时刻——悬停文案
现在两个都显示（「到达 143.0s（历时 143.0s）」）。

### 36.2 「到达晚于 `timeline.duration`」不能当「走不到终点」

一度想给悬停加「超出关卡时长，走不到终点」的红字。实测这是错的：
`duration` 只是**最后一个出怪时间**，不是关卡结束时间。H8-4 有
**25 只**（含 12 只正常敌对，如 `enemy_1108_uterer_2` R35 于 176s 出场、
202s 到达）晚于 `duration`，它们在实机里完全正常。真要判断「走不到」
需要关卡的通关时长数据，解包数据里没有，所以这个提示已撤掉，
只保留诚实的「到达 X 秒」。

## 37. 「咩的朋友角兽罚站时间错误」：时长根本不在路线里

### 37.1 症状与根因

用户报「咩的朋友」的角兽罚站时间不对。查下来，**路线分析给的是 0 秒**：

```text
ro6_c_2（ISW-NO 咩的朋友） 全部 33 条原始路线 motionMode 都是 WALK
checkpoints: []      ← 每一条都是空数组
=> RouteAnalysis.pre_wait = 0.0
```

但实机每只角兽出场先站 90 秒。PRTS 角兽天赋页写得很清楚：

> 初始处于【休憩】状态：不进行攻击，**出场一段时间内（默认为 150 秒）**
> 持有[自缚]

也就是说，这个时长根本不属于路线，它是敌人的**天赋**，落在
`talentBlackboard` 的 `Revive.unmovable_duration` 键上。路线里没有
检查点，所以任何「只读路线」的实现都必然显示 0 —— 这不是算术错，
是数据源找错了。

### 37.2 三个数量级的普查（决定实现方式）

直接「有就套」是会出事的，所以先普查：

| 普查项 | 结果 |
|---|---|
| 敌人库 2186 个 id 里带 `Revive.unmovable_duration` 的 | **3 个**：角兽 150s / 亢角兽 150s / 鬣犄兽 150s |
| handbook `abilityList` 含「休憩」二字的 | **2 个**：只有角兽与亢角兽 |
| 2575 个缓存关里会碰到这 3 个敌人的 | 28 关 |
| 其中把该键**覆盖成正数**的 | **7 处**，全是角兽系（`ro6_c_2` 的 90s 在其中） |
| 显式覆盖成 `0.0`（本关不休憩）的 | 21 处 |

关键反证：**鬣犄兽也带这个键，默认也是 150s，但它没有休憩**。它的
`abilityList` 只有「优先攻击角兽和亢角兽」，PRTS 页也没有休憩描述。
如果照搬库默认值，会让大约 20 关的鬣犄兽凭空站 150 秒 —— 那是把
「复活后不能动」错读成「出场罚站」。

### 37.3 落地规则

`spawn_unmovable_of_ref(ref)` 的取值顺序：

1. 关卡 `overwrittenData.talentBlackboard` 里显式给了
   `Revive.unmovable_duration` → 就用它，**`0.0` 也是有效答案**
   （21 处显式禁用的关卡必须尊重）。
2. 没写覆盖 → 走 `spawn_unmovable_default(eid)`：角兽系（前缀
   `enemy_1303_mhshep`）回落 150s，其余一律 0。

**刻意不查敌人库本体**，有两个原因：

* 库默认 150s 对鬣犄兽是错的（见上）。
* 关卡会用**私有 id** 引用敌人：`act24side_01` 用
  `enemy_1303_mhshep_b`、`rogue5_2-2` 用 `_a`/`_c`，这些变体在
  敌人库 `by_id` 里**根本不存在**。一旦要求先 `lib.stats()` 成功，
  这些关的罚站就全丢了。靠前缀识别私有变体即可。

### 37.4 接进沙盘的三处（缺一处就是假修复）

只改悬停文案是不够的 —— 文案说「罚站 90 秒」而位置照跑，就是骗人。
`Sandbox` 里三处都要扣掉这段时间：

| 位置 | 处理 |
|---|---|
| `pose_at` | 先从墙上时长里扣掉 `spawn_unmovable_of`，再折算减速；扣完为负取 0 |
| `arrival_time` | 直接 `+ head`（这笔时间是常量，既不进 `total_time` 也不受减速影响） |
| `enemy_flags` | `elapsed < head` 就 `waiting=True`、`wait_left = head - elapsed` 并提前返回 |
| `_track_total` | 粗轴/播放总长要按「出怪时刻 + 到达」重算，否则动画在敌人刚抬脚时就结束 |

最后那条原本我以为是角兽问题，查下来是**普遍现象**：``timeline.duration``
只是**最后一个出怪时刻**，不是关卡结束，几乎每一关都短。

| 关卡 | 出怪到 | 最晚到达 | 差 |
|---|---|---|---|
| `main_08-04` | 163s | 193s | 30s |
| `hard_08-04` | 176s | 274s | 98s（平民罚站 270s） |
| `ro6_c_6` 纵怒 | 139s | 157s | 18s（领舞者罚站 120s） |
| `main_07-16` | 114s | 175s | 61s |
| `act1multi_football` | 80s | 357s | 277s |

只按 ``duration`` 收尾，进度条走到头时还有敌人在半路甚至没出发，用户看到
的仍然是「没动」。寻路面板早就有正确做法 ``Timeline.span(analyses)``，
沙盘这次对齐同一口径，并额外算上**出场罚站**（角兽的休憩不在路线的
``total_time`` 里）。改完 12 个抽样关的粗轴与最晚到达**逐关精确相等**。

注意 ``arrival_time`` 返回的历时**已经含**出场罚站，重算时不要再加一次
``head``。

`enemy_flags` 里那个提前返回是必须的：`wait_span_at` 查的是路线里的
检查点罚站，角兽的路线连检查点都没有，查不到。

数据由 UI 层灌进 `Sandbox.spawn_wait: Dict[str, float]`
（`sandbox_panel._load_spawn_wait`），核心不依赖敌人库。

实测（真实 Tk 界面）：

```text
t=0    角兽 · 未被阻挡 · 罚站中，还剩 90.0s · 到达 103.7s（历时 103.7s）
t=45   角兽 · 未被阻挡 · 罚站中，还剩 45.0s
t=89   角兽 · 未被阻挡 · 罚站中，还剩 1.0s
t=90   角兽 · 未被阻挡 · 未罚站
0~90s 位置恒为 (6.0, 1.0)；t=100 → (4.59, 5.41) 已动；t=120 已到终点
```

沙盘修完还要同步寻路面板，否则同一关两个页面一个写 90s、一个写 0s，
矛盾直接摊在用户面前。`PathPanel._pre_wait_of(route_index, enemy_id="")`
改成把两个来源**相加**：

* 路线预罚站（`RouteAnalysis.pre_wait`）—— 纵怒 R0~R2 的 120s 属于这类；
* 天赋休憩（`_spawn_wait[enemy_id]`）—— 角兽的 90s 属于这类。

只加不漏、不重不漏的验证方式是拿纵怒反向卡：它天赋表为空，合计必须
仍是 120s，不能被叠成 210s。路线详情栏也单独加了一行
「天赋罚站 90.0s ← 【休憩】出场自缚（不在路线上）」，并把全程改成
「103.66s（含天赋罚站 90.0s）」。

### 37.5 顺带确认：角兽 22 只不是多算

用户可能觉得「多出角兽」。原始数据 23 条，`effective_events(fold_random=True)`
折叠成 **22** 条；温泉“淘气包”20 条折叠成 10 条。剩下的差额来自
`randomSpawnGroupKey=g1`（两条同敌人不同路线，50/50 抽一条）以及大量
`rgk=None` 的独立点名。所以 22 是「一局真会出的上限」而不是翻倍。

### 37.6 又一次踩到的坑

`fold_random_packs()` **返回新列表，不原地修改**。第一次统计时我按
「调用完再数 `self.events`」写，得出「折叠前后都是 43 条」的错误结论，

其实是我读错了 API」。这类错误统一记在这里：**先怀疑自己的读法，
再怀疑产品**。

## 38. 沙盘交互收尾：buff 往返、开技能文案、图外悬停、PRTS 脏标签

这一节是「逐条对着目标验收」时抠出来的，四条都是真实缺陷，不是文档
补写。

### 38.1 导出的 buff 导不回来（数据丢失）

`CoarseTrack.dump` 原来直接 `data["buffs"] = list(buffs or [])`，而
`Sandbox.buffs` 的元素是四元组 `(key, t0, t1, mult)`。落进 JSON 就是
无键名的四元素数组：

```
"buffs": [["2|0|0|1|1", 40.0, 60.0, 0.5]]
```

导入端 `_apply_imported` 却只按 dict 读（`b.get("key")`），
`isinstance(b, dict)` 直接把它筛掉。结果：**导出的轴导入回来，减速
buff 全部消失，界面还提示「导入成功」**。这是「导出/导入粗轴」那条
要求上的实打实的数据丢失。

两侧一起改：

* 导出走 `_buff_to_dict`，落成带键名的对象：

  ```json
  {"key": "2|0|0|1|1", "t": 40.0, "dur": 20.0, "mult": 0.5}
  ```

  `t` + `dur` 比 `t0` + `t1` 更接近界面上「从第 40 秒起减速 20 秒」
  的说法；`box_count` / `buff_count` 照旧只在非空时写。

* 导入端**两种形状都认**：dict（新格式）与 4 元素序列（旧文件、
  以及任何人直接 dump 内存对象的结果）。`mult` 仍夹在 0~1。

验收：部署 + 撤退 + 开技能 + 箱子 + buff 各一份，导出再导入，
`buffs` 从 1 条变成 1 条（修前是 0 条），干员/箱子/关卡 id 全部一致；
再导一份空 `buffs` 能把界面上已有的 buff 清掉。

### 38.2 SP 没满时点「开启技能」也报「已记录…开技能」

`Sandbox.use_skill` 只记时刻（用户要的就是「只模拟回转」），所以
SP 只有 40/50 时点下去，`skill_uses` 照样追加。但右键菜单一律写
「开启技能（12.0s）」、回执一律写「已记录 X 在 12.0s 开技能」——
看起来像技能真的开了，转头看悬停还是 `SP 40/50，还需 10.0s`，
自相矛盾。

`state_at` 的四个可达状态各自给一句准确的话：

| 状态 | 菜单项 | 回执 |
|---|---|---|
| 被动（`sp_cost<=0`） | 开启技能（…，被动无 SP） | 被动技能，没有 SP 回转，只记了时刻 |
| 技能进行中 | 开启技能（…，技能中） | 技能本来就在进行中，又记了一次施放时刻 |
| SP 满未施放 | 开启技能（…，SP 已满） | SP 已满，记下了这次施放 |
| SP 未满 | 开启技能（…，SP x/y 未满，仅记时刻） | SP 只有 x/y，还没转好；只记下这个时刻… |

顺带确认了一个容易搞错的点：`ready=True` 且 `active=False`
**是真实可达的**（就是「SP 刚好满、还没按下去」那一瞬），不是死分支。
扫描 463 名干员，有 618 个技能存在这种时刻。

### 38.3 悬停地图外的格子只回一个坐标

`_hover_tile` 在 `tile is None` 时只输出 `(1,13)`，看着像功能坏了。
改成 `(1,13)　·　地图外（本图 13×9）`。

### 38.4 PRTS 的 `<span style=…>` 整段漏进技能描述

`gen_enemy_skills_prts.py` 里 `_TAG_RE = r"<[^>]{0,40}>"` 把标签长度
限死在 40 字符。可 PRTS 用内联样式标红：

```html
<span style="color:#fff;background:red;padding-inline:0.5em;box-shadow:0 0 5px red;">
```

这一个标签就 84 个字符，正则匹配不上，标签原文留在
`enemy_1587_ubbplwq`「封锁区和平治理计划」的描述里直接给用户看。
上界放宽到 300（仍不允许跨 `>`，不会误吞正文），并把数据文件里
那一条已经脏掉的记录清干净。

### 38.5 关于「半角逗号」的误判

先前怀疑 5 条 `effect` 里混了半角 `,`/`;`，逐条看下来**全部是坐标**
（`距离自身(1,1)偏移处`、`在(4,9)坐标(Y,X)`），PRTS 原文就是半角，
改成全角反而是错的。这类「按字符扫一遍就报缺陷」的检查要先看样本，
否则会把正确数据改坏。

### 38.6 源代码栏的指令：确认是「指令」而不是描述 JSON

链路是 `skill_codes` → `annotate_code` → `annotation_lines`，
`annotate_code` 收到的必须是 `skill_codes` 归一化后的
`{"key", "cooldown", "init", "sp_cost", "blackboard":[(k,v,vs)], "raw"}`，
不能直接喂 `enemyData.skills[i]` 原始 dict（那样 `bb` 全是
`key = valueStr`、`prefab` 为空，注解会谎称「没有 prefabKey」）。

真实数据验收：1773 条技能、600 条抽样，反推指令 0 条为空，平均 2.12
步；`enemy_10002_trtrsl` 的 `Shine` 反推出 5 步
（触发 → `range_radius` 1.6 格 → `stun` 12 → `interval` 12 →
`duration` 12），每步都带原键名，排在注解最前面。

### 39.1 箱子：穷举全部可放格，而不是「试几个」

「箱子不得堵死通往蓝门的全部路线」这条最容易被写成假测试——
随便放两个箱子看还能不能走，说一句「没堵死」就算过。真正要排除的是
**任何单个箱子格**都能把路全截断的情形，所以必须对每个可放格都试一遍。

`probe_box_ex.py` 在 8 张图上这样做：把该格真的塞进 `boxes`，重算
`analyze_all(blocked=...)`，统计仍然可达的事件数，然后撤销。

```text
main_00-01   33 格可放   最差可达 11/11   单箱致死格 0

main_04-04   93 格       最差 63/63       0
```

而这正是「拒绝理由」那套判定的底气——被拒的格子之所以被拒，是真的
会切断路线，不是保守。

### 39.4 这一轮新查出来的真缺陷：下拉里有、索引里没有

验收第 15 项（集成战略分层）时，我用「下拉项数 vs 索引键数」这个
口径去核对，本来只想确认分层没漏关，结果撞出一个真 bug：

```text
IS4 全部节点   下拉 293   索引 289   少 4
IS4 险路恶敌   下拉  21   索引  17   少 4
IS5 全部节点   下拉 270   索引 230   少 40
IS5 特殊作战   下拉  60   索引  25   少 35
IS6 全部节点   下拉 184   索引 119   少 65
IS6 作战       下拉  76   索引  51   少 25
```

共 10 个档位不一致，**IS6 有 65 关点不到**。根因在
`SandboxPanel._fill_levels`：它拿「● + 难度 + 关卡名」拼出来的**显示名**
当字典键（`self._stage_index[label] = st`）。而集成战略里同一个名字
常有好几个变体：

```text
ro4_b_4     ISW-DF 「紧急授课」
ro4_b_4_c   ISW-DF 「紧急授课」   ← 显示名完全相同

ro4_b_5_c   ISW-DF 「朝谒」
```

后一个盖掉前一个，于是下拉里 21 项、字典只剩 17 个键。用户点第 18 项
之后的关卡，`_on_load` 从字典里取到的是**另一关**——不是加载失败，
是静默加载错了地图，比报错更难受。

修法是先统计每个显示名出现几次，**只给重复的**追加
`（stage_id）` 作后缀，不重复的保持原样（界面看上去没变化）：

```text
● ISW-DF 紧急授课（ro4_b_4）
● ISW-DF 紧急授课（ro4_b_4_c）
● ISW-DF 朝谒（ro4_b_5）
● ISW-DF 朝谒（ro4_b_5_c）
```

修后 40 个档位全部 `下拉项数 == 索引键数`，且 `ro4_b_4_c` 单独选中后
载入的确实是 `ro4_b_4_c`。

### 39.5 同一个方法里的第二个坑：label 是个空格

改完上面的名字去重，顺手打印了整列，发现最后一项显示成「● 」
（一个圆点加空白）：

```text

●                       ← 修前
```

全库 4521 关里只有这 1 关 `label` 是空格（`ro4_b_9`，`sub_name` 为
「首领节点」）。下拉里看不出是什么关，选中它更不知道点到了什么。
兜底规则：`label` 去空白后为空就退到 `code`，再退到 `stage_id`，
有 `sub_name` 就拼上。现在显示「● ro4_b_9 首领节点」。

这个坑值得记的原因是它**只有 1 条数据**。用「抽样 100 关看看」的

### 39.6 这一轮我自己读错了 8 次 API

值得单独记一笔，因为 8 次全部发生在**验收**环节而不是实现环节，
而且形态高度一致：**照着「应该叫什么」去猜属性名，没先查**。

```text
猜的                          真的
cv.zoom                       sp._zoom（缩放在面板上，不在画布）
sp._hover_tile(敌人坐标)       敌人走 _hover_enemy，地块走 _hover_tile
for (r, c) in a.segments      RouteSegment 对象，格点在 seg.path 里
d["retreat_time"]             d["retreat"]
sp.playback.total()           sp._track_total()
图层看 _render_state()         图层直接写 canvas.show_ground / _r.show_mech
listbox 找 "Listbox"          真实控件是 _scrolled 建的 Canvas
_node_types[0] 是「全部节点」   「全部节点」是 values[0]，不在 _node_types 里
```

后果都一样：**产品是对的，探针报 FAIL**。如果当时图省事，照着 FAIL
去「修产品」，就会把本来正确的代码改坏——比如给 `RouteSegment` 加个
`__iter__` 来迁就探针的解包，或者把 `_hover_tile` 改成也会显示敌人。

所以流程上加一条：探针报 FAIL 时，先证明「探针读的位置是对的」，
再去怀疑产品。具体做法是打印原始值而不只打印布尔结论——上面 8 个里

### 40.3 「路线都不一样」的真实原因

26 条路线的起点只分布在 4 个格子上：

```text
startPosition  (7,0)×12   (1,0)×9   (2,12)×3   (7,12)×2
endPosition    (4,0)×14              (4,9)×12
```

同一个起点出发的 12 条路线，跑 `analyze_all` 得到的是**同一条路径**
`[(7,0),(6,1),(5,1),(4,0)]`——这不是算错，是这 12 只小兵在本关确实
共用一条路（`routeIndex` 各不相同但几何路径相同）。

实机里看着「路线都不一样」，来源是路线上的随机抖动：

```text
spawnRandomRange = {x: 0.1, y: 0.1}   ×23 条
spawnRandomRange = {0, 0}             ×3  条
spawnOffset      = {0, 0}             ×26 条
```

`spawnRandomRange` 是**像素级**的出场散开（0.1 格），怪物会左右错开
一点点走进同一条路，视觉上像不同路线，几何上是一条。我们的分析画的是
几何路径，所以必然重合——这是正确的表达，不该为了「看起来不一样」去
人为制造分支。

`(7,0)` 出口的几何也印证了只有一条路可走：`(7,0)` 往上是 `(6,0)`
`tile_forbidden`（FLY_ONLY 高台）、左/下都是越界或 `tile_forbidden`，
只有 `(7,1)` 和 `(6,1)` 两个地面可走，两条都汇入 `(4,0)`。

把「是不是有别的开关让它们走出不同路」也逐项排掉了——26 条路线的
五个寻路开关**完全相同**：

```text
motionMode            WALK       ×26
allowDiagonalMove     true       ×26
visitEveryTileCenter  false      ×26
visitEveryNodeCenter  false      ×26
visitEveryCheckPoint  false      ×26
```

按起点分组实测（`analyze_all` 与 raw routes 按位置一一对应，26↔26）：

```text
起点 (7,0)   12 条  不同几何路径 1 种  [(7,0),(6,1),(5,1),(4,0)]
起点 (1,0)    9 条  不同几何路径 1 种  [(1,0)…(1,6),(2,7),(3,7),(4,8),(4,9)]
起点 (2,12)   3 条  不同几何路径 1 种  [(2,12),(3,11),(4,10),(4,9)]
起点 (7,12)   2 条  不同几何路径 1 种  [(7,12)…(4,1),(4,0)]  ← 绕最长那条
```

> 排查留档：中途用 `r.get("routeIndex")` 去对齐 raw routes，一直匹配
> 0 条，看起来像「路线全丢了」。真实原因是 **4-4 的 raw route 里根本
> 没有 `routeIndex` 这个键**（官方 JSON 里也没有，`routeIndex` 只在
> 部分关卡出现）。`analyze_all` 的 `route_index` 是按列表下标给的，
> 所以对齐必须按**位置** `zip(ans, routes)`，不能按 `routeIndex` 查表。
> 又一次「先怀疑自己的读法」。

### 40.6 顺带修掉一个**真实**的参数丢失 bug

排查 4-4 悬停时发现：感染地板悬停只显示「感染地面」四个字，
`damage 180 / duration 300 / atk 0.5 / attack_speed 50` 全没了。
两层原因，都是真 bug：

**第一层：同一 tileKey 有多条 def 就放弃取参数。**

原实现把 blackboard 按 `tileKey` 收进池子，然后：

```python
pool = bb_pool.get(key) or [None]
bb = pool[0] if len(pool) == 1 else None   # ← 池子>1 就丢掉
```

4-4 的 `tile_infection` 在 `tiles` 里有两条 def（下标 33 和 56），
池子长度 2，于是 `bb=None`，`params={}`。修法是让每个 `Tile` 记住
自己对应哪一条 def：

```python
# models.py
@dataclass
class Tile:
    ...
    def_index: int = -1        # 对应 mapData.tiles 的下标

# maps.py
tile = Tile(..., def_index=idx)
```

`mechanisms.extract` 改成按 `tile.def_index` 精确定位。

> 这里踩了一个坑并当场修掉：第一版写成
> `idx = int(getattr(tile, "def_index", -1) or -1)`，
> `def_index == 0` 时 `0 or -1` 得到 `-1`，下标 0 的格子永远取不到
> 自己的 def（`act49side_11 (0,0)` 就是这么漏的）。改成显式判 `None`。

**第二层：参数白名单只有 13 个键，而解包实际用了 40+ 种。**

```text
白名单: tile mode interval damage atk atk_scale attack_speed
        move_speed duration prob interval_max interval_min special
```

漏掉的里面就有 `tile_defbreak` 的 `def`、`tile_bigforce` 的
`base_force_level`、`tile_healing` 的
`HP_RECOVERY_PER_SEC_BY_MAX_HP_RATIO`、`tile_volcano` 的
`cd_min/cd_max`、`tile_quicksand` 的 `falldown_stack_count` 等。
改成**全量收录** blackboard 所有键值，不再用白名单。

修后全量核对（2629 个缓存关卡，只统计「def 里确实带 blackboard」的格子）：

```text
修复前：6029 个应带参数的机关格，只有 2410 格拿到（39.97%），丢 3619
修复后：6029 个应带参数的机关格，6029 格拿到（100.00%），丢 0
```

4-4 的两处感染地板现在悬停是：

```text
感染地面　每跳伤害 180 · 攻击倍率 0.5 · 攻速 50 · 持续秒 300
```

`summary()` 同时把 raw key 换成了中文标签（`_PARAM_CN`），
未登记的键仍原样输出，不会再出现「看得见但读不懂」的英文键。

## 42. 沙盘四项：撤退重放、撤销重做、头像、阻挡动画

### 42.1 撤退后拖回部署期，干员消失

根因：`_render_state()` 直接用 `sb.operators`。那是**当前场上**状态——
游客把游标拖回部署期时，那枚干员在当前时刻其实已经撤了，`operators`
里没有他，地图上就空了。可是粗轴上明明还画着那一段部署条。

修法：新增 `Sandbox.operators_at(seconds)`，按 `track.all()` 回放——
「部署了且未到撤退时刻」的干员都算在场。已经撤退的按粗轴重建一枚影子
`OperatorPiece`，**只用于渲染，不写回 `self.operators`**。`overlap()` 和
`_render_state()` 都改用它。

实测：

```text
部署 (0,2) 后           operators={(0,2)}
撤退后                  operators={}          ← 当前时刻确实没人
撤退后 operators_at(3.0)   {(0,2): 阿消}      ← 拖回部署期，人回来了
撤退后 operators_at(40.0)  {}                ← 过了撤退时刻，不该显示
```

### 42.2 撤销 / 重做

`sandbox.py` 加 `_undo_stack` / `_redo_stack`，`push_history()` 深拷贝
`boxes/operators/kicked/buffs/track/analyses`，栈深上限 80，push 时清空
redo。UI 底部「撤一步」「重做」两个按钮 + `Ctrl+Z` / `Ctrl+Y`，按钮按
栈空自动禁用。

实测：

```text
部署   -> undo 栈 1
undo   -> 空           redo 栈 1
redo   -> 人回来
再 undo -> 空
新操作后 redo 栈 = 0   ← 符合办公软件习惯
```

### 42.3 头像：中间踩到一个「假完成」

### 42.4 阻挡动画

`pose_at()` 改成「无阻挡轨迹 + 阻挡罚站」：

1. 先按无阻挡算出敌人会在哪个整格、什么时刻撞上干员；
2. `_blocking_plan()` 按 `(阻挡格, 部署 uid)` 分组——同格撤退后再部署是
   两段**独立**容量，不能混算；每组按到达墙钟排序发「挡票」，前
   `block_count` 只拿票；
3. 拿到票的，`[arr_wall, release_wall)` 期间位置钉在干员格；
4. `release_wall` 之后从阻挡格按剩余墙钟继续走。

飞行敌人只被 `can_block_fly` 干员挡。所有状态变更都调
`_invalidate_plan()` 让缓存失效。

实测（1 行 6 列，10 秒走完，干员在 `(0,3)`）：

```text

block_count=2   t=9s   e1=(0,3)  e2=(0,3)   e3=(0,4.5)   前两只被挡
飞行 + fly=False  t=9s (0,4.5) 飞过
飞行 + fly=True   t=9s (0,3)   停住
```

| --- | --- |

但 PyInstaller 扫不到缩进块里的 import。

验证方法（关键）：不看 TOC，直接开 exe 的 PYZ 归档数模块。


结果：24 个关键模块全部在 PYZ 内，缺失 0。

### 43.2 `enemy_handbook_table.json` 没随包 → 图鉴天赋全空白

的 `seed` 列表里**没有它**。于是 exe 的 `_MEIPASS` 里根本没有源文件，
复制那一步静默跳过（`os.path.isfile(s)` 为 False 就 `pass`）。

后果正好命中用户的一条投诉——「敌人图鉴没有天赋与能力描写」：

同类坑还有两个，一起补上：

* `summon_stats.json` —— spec 打了，但 `seed_if_needed` 白名单漏了，

关键认知：**程序读的是 Releases API，不是仓库代码**。光 push 代码，

`APP_VERSION = "2.2"`，tag 用 `v2.2`。`parse_version` 会切成

### 44.5 上传大文件

### 44.6 网络抖动

这台机器直连 GitHub 是间歇性的：push 第一次成功，补推文档时连续
失败 3 次，第 4 次成功。脚本里要写重试（间隔 8 秒、5 次），
不要一次失败就判定没网。

诊断顺序（别急着改代码）：先看 `git config --list --show-origin`
有没有代理、再 `Test-NetConnection` 看端口、再看是不是 URL 级专用代理。

## 45 敌人抬手数据与 MCP 接口（v2.3）

本轮加了两件互不相干的事，但都属于「数据层」：

1. **敌人抬手（攻击前摇）** —— 解包 `bakemuzzledata` 算出来，接进敌人图鉴；
2. **MCP 接口** —— 让外接 AI 直接读干员 / 敌人 / 地图 / 路线数据。

顺带修了一个存在很久的**产品 bug**：所有敌人的 `is_flying` 恒为 False。

### 45.1 抬手为什么要从解包里算

「抬手」= 敌人攻击动画从第 0 帧播到真正打出伤害之间的秒数。它决定了
「我撤退干员能不能躲掉这一下」：

* 攻击间隔 3 秒、抬手 0.333 秒 → 抬手第 0.2 秒撤退，这一下空砍；
* 攻击间隔 3 秒、抬手 2.767 秒 → 从起手就锁定，撤了也白撤。

这个数值**不在** `enemy_database.json`（只有攻击间隔 atkInterval）、
也不在 PRTS 或任何 wiki API 里。唯一来源是解包的动作烘焙数据
`zh_CN/gamedata/bakemuzzledata/enemy/*.json`。

规模：**2109 个文件 / 89.2 MB**。构建期解析成 0.22 MB 的
`akcalc/data/enemy_attack_timing.json`，运行时不碰原始解包。

### 45.2 解包结构（实测）

顶层 `{'bakedAnimDatas': {...}, 'hash': ...}`，`bakedAnimDatas` 里
**只有 `Default` 一个键**（不是按骨骼分组）。`Default` 下面是
`md5 / skipZeroFrameUpdate / bakedMPDatas / bakedEvents`。

抬手就在 `bakedEvents`：

```
bakedEvents[<动画名>]['eventTime'][<events 里 OnAttack 的下标>]
```

单位是秒，从动画第 0 帧起算。

**`bakedMPDatas` 是姿势矩阵（每帧 22~23 个 float），图鉴用不到，不存。**

### 45.3 三个必须踩过的坑

**(1) 动画名根本不叫 `Attack`。** 实测 86 种名字：`Attack`(618)、
`Skill`(84)、`Start`(31)、`Attack_A`(25)、`Attack_B`(23)、`B_Attack`(23)、
`Attack_2`(20)、`A_Attack`(20)、`Combat`(12)、`Attack_Down`(12)、
`Attack_Up`(12)、`Attack2`(10)… 到 `White_Attack` / `Black_Attack`。

判定规则：名字含 `attack` 或 `combat`（小写比较），且不含 `skill`。
跳过词表：`skill, die, stun, idle, move, start, change, grab, click,
attackfinished`。

### 45.8 打包版 stdio：两个独立的坑

**(1) `console=False` 下流可能是 `None`。**
窗口模式 Windows 不分配控制台，`sys.stdin/stdout/stderr` 会是 `None`。
但 fd 0/1/2 仍然连着客户端给的管道，重新 `open()` 就能用。

**(2) 更阴险的：流不是 `None`，而是 GBK（cp936）。**
实测打包后的 exe，三个流是编码为 `cp936` 的 `TextIOWrapper`——
Python 按系统区域设置初始化了 stdio。后果分三层：

* 入站 `银灰`（UTF-8 `e9 93 b6 e7 81 b0`）被按 GBK 解成 `閾剁伆`，
  工具报「找不到干员」；
* 出站编成 GBK，客户端按 UTF-8 读是满屏乱码；
* **最隐蔽的一层**：`operator_professions` 这种以中文为字典键的工具，
  8 个职业名在乱码下有两对撞成同一串，字典键被合并，
  **静默只剩 6 类**。数据文件完全正常，看起来像「数据丢了」。

第一版只在 `is None` 时兜底，所以 GBK 情况根本没进分支。修法：
`_ensure_stdio()` 改成**无条件调用**，先试 `reconfigure(encoding="utf-8")`，
失败再按 fd 重新 `open(..., closefd=False, newline="\n")`。
`closefd=False` 很关键——不能把 fd 一起关掉。

`ascii` 也当作坏编码处理：写中文会静默变成 `?`。

实测修复前后：

```
[child] before=(cp936, cp936)  after=(utf-8, utf-8)
```

**(3) `--mcp` 判断必须在所有 GUI import 之前。**
PyInstaller 的入口是 `run_gui.py`（不是 `run.py`），而 `run_gui.py` 里
`from akcalc.ui.app import main` 是无条件的，会拉起 tkinter 和一整套面板。
必须把 `--mcp` 分支放在那行 import 之上。

**(4) `--mcp` 模式下异常不能弹窗。**
`run_gui.py` 的兜底是 `messagebox.showerror`，对 GUI 是对的，
但 MCP 是 stdio 服务：弹窗会让客户端一直超时，而且无桌面会话时
`tkinter.Tk()` 自己就抛，错误反而彻底消失。现在 `--mcp` 下只写日志 + stderr。

**(5) MCP 模式不经过 GUI，种子数据没人播种。**
打包版把种子数据放在 `_MEIPASS`，要靠 `Paths.ensure()` 复制到可写目录。
GUI 启动会调它，但 MCP **不经过 GUI**：全新安装的用户如果在客户端里
配好 MCP 就直接用，可写目录是空的，所有工具都报「敌人库还没下载」。
现在 `mcp/common.py:paths()` 首次获取时自己调一次 `ensure()`，
冷启动约 21 秒复制 34MB，之后毫秒级。

## 46. 抬手改成帧+秒双单位，换算器与 MCP 配置搬进设置

### 46.1 为什么帧是准数，不是估算

游戏 Spine 动画按 **30 fps 烘焙**，``bakedEvents[动画名].eventTime``
存的那个小数，本质就是「帧号 / 30」。

实测 1857 条数据：``round(a * 30)`` 与原始帧号的偏差最大
**0.001 帧**（3.3e-05 秒），纯粹是 JSON 里只存了 4 位小数。

所以帧数不是「四舍五入猜出来的」，而是**还原**了原始帧号。这一点
必须在代码注释里写清楚，否则下一个人看到 ``round()`` 会以为是近似，
然后「优化」成别的东西。

| 秒 | 帧 |
|---|---|
| 0.3333 | 10 |
| 0.4667 | 14 |
| 1.0333 | 31 |
| 4.8333 | 145 |

### 46.2 两个单位都留的理由

* **帧** —— 和游戏内、帧轴视频、卡帧操作对得上。玩家说「这怪抬手
  14 帧」比「0.467 秒」直观。
* **秒** —— 算撤退时机、技能覆盖时长、DPS 时是秒。

图鉴卡片主数字改成「抬手 14 帧　（0.467 秒）」，帧在前；底部补一行
「按 30 帧/秒 换算；1 帧 ≈ 0.033 秒」，让用户知道数是怎么来的。

### 46.3 MCP 加了换算工具

``attack_timing_convert`` 一个工具三种用法：

* ``{"value": 14, "from_unit": "frame"}`` → ``14 帧 / 0.467 秒``
* ``{"enemy": "源石虫"}`` → 该敌人的抬手（帧+秒）
* ``{}`` → 0~60 帧的换算表

``enemy_attack_timing`` 的返回值也加了 ``attack_windup_frames`` /
``by_animation_frames`` / ``fps``，旧的 ``attack_windup_seconds`` 保留，
不破坏已有调用方。工具总数 18 → 19。

### 46.4 三个只有在真机上才会踩到的坑

**(1) 在 GUI 后台线程里调 `serve()` 会把整个进程干掉。**
设置页的「MCP 自检」最初是 `serve(StringIO(...), StringIO())`。
`serve()` 会**改写全局** `sys.stdin/stdout/stderr` 然后进阻塞主循环——
在 GUI 的后台线程里这么干等于把进程的标准流偷走，实测 python 直接
`exit 1`，界面无声消失。
改用 `handle()`：纯函数，吃一个请求吐一个响应，不碰任何全局状态。
顺带给 `serve()` 加了 `try/finally` 还原 stdio，进程内复用不留痕。

**(2) `WARN` 从来没被 import 过。**
`_apply_update()` 里早有 `elif not info.ok: color = WARN`，但
`from .widgets import (...)` 那行没带 `WARN`。也就是说**「检查更新」
一旦失败就 NameError**——这条路径平时不走到，加新卡片时才被翻出来。
`widgets.py` 里 `WARN = ACCENT_TXT` 是有的，纯粹漏了导入。

**(3) 设置窗口内容一多就超出屏幕，且锁死不能调整。**
加了换算器和 MCP 两张卡后，`winfo_reqheight()` 从 ~600 涨到 **855**。
原来是 `resizable(False, False)`，1366x768 的笔记本上窗口加标题栏
超过可用高度，**底部「完成」按钮直接被挤出屏幕**，还拉不动，等于
用户点不到「完成」卡死在这一步。
改法：`resizable(True, True)` + body 换 `ScrollFrame` + 底部按钮
固定在不滚动的 foot 里 + `_center()` 把高度夹到「屏幕高 - 120」。

这里还有个**二次坑**：`ScrollFrame` 的 canvas 默认高 1px，包在
`expand=True` 里会让 `winfo_reqheight()` 只报 362px（标题栏 +
底部按钮），内容的 748px 全丢了，窗口一开就挤成一条矮条。所以
`_center()` 改用 `_scroll.inner.winfo_reqheight()` 当内容高度。

实测 1366x768 / 900 / 1080 三档，底部按钮都在屏内。

### 46.5 MCP 配置为什么不自动写进客户端

各家路径不一样（Claude Desktop 在 `%APPDATA%\Claude\`，Cursor 在项目
`.cursor/mcp.json`，Cline 在 VSCode 扩展存储里），而且用户文件里通常
**已经配了别的 server**，自动合并极易覆盖。
所以只生成 + 一键复制，让用户自己粘。设置卡片上把实际命令也显示
出来——用户把 exe 挪了位置时，一眼就能看出路径不对。

## 47. 抬手加 30/60/120 帧率档（用户澄清了「换算」的口径）

### 47.1 用户这次的原话与我的第一版误解

> 换算是指在30帧运行游戏下的抬手帧 在60帧下的抬手帧 切换是在30 60 120
> 中间切换 但是明日方舟本质是30帧游戏 大于三十的就插入计算了

第一版我把「换算」做成了「帧⇄秒」。用户要的是**同一抬手在不同运行
帧率下的帧数口径**：逻辑 30fps 是真帧；60/120 是高刷插值帧，
``14 帧@30 == 28 帧@60 == 56 帧@120``。

### 47.2 frames_at / at_fps_table

```python
SUPPORTED_FPS = (30, 60, 120)

frames_at(14, 60)   # 28
frames_at(14, 120)  # 56
at_fps_table(31)    # {"30": 31, "60": 62, "120": 124}
```

倍率不是整数时**向上取整**：插值帧宁可多报一帧（更保守），也不把
「半帧」悄悄抹掉让人误判能卡过去。

### 47.3 「图鉴里没有抬手」的乌龙与真改进

用户报「图鉴没显示抬手」。排查结论：**卡片一直在**，三个探针
FakeApp 缺 ``enemy_lib`` 导致 ``self._entry`` 为 None，``_build``
提前 return——探针错了，功能没坏。

但排查顺带暴露一个真缺陷：**15% 无数据的敌人，抬手卡是静默消失的**
（318/2186，多为装置/召唤物/剧情单位，bake 里 ``bakedEvents``
本来就没有攻击事件）。用户看到的就是「这功能时有时无」。
现在无数据也画卡，写明「未收录」+ 原因。

敌库没下载、但抬手表（随包分发）有数据的情况，也照样显示。

### 47.4 三处界面的口径

1. **图鉴卡**：主行不变，新增一行
   ``@30fps 10 帧 ｜ @60fps 20 帧 ｜ @120fps 40 帧``，
   尾行改成「游戏逻辑 30 帧/秒；60/120 为插值帧，时长与 30 帧一致」
2. **设置换算器**：新增「帧率档」单选（30/60/120）。选 60fps 再输
   28 帧指的是 60fps 口径；输秒数则不受档位影响（秒是绝对单位）
3. **MCP ``attack_timing_convert``**：新增 ``fps`` 参数
   （enum 30/60/120），所有返回带 ``frames_at_fps`` 三档对照，
   换算表也加了 ``at_60fps`` / ``at_120fps`` 列

一个实现细节：秒输入**不套档位标注**。第一版把 0.4667 秒也标注成
「28 帧@60fps」，口径错了——0.4667 秒在 30fps 口径就是 14 帧，
只有「帧」输入才需要按档位解释。
