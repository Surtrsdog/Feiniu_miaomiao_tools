## 二 批次 A · 播放表现（先做）

### A0 性能三连（P0，0.5 人天）

改动点全部在 `akcalc/core/sandbox.py`，**不碰 UI**。

#### A0.1 `analysis_for` 线性扫描 → 字典索引

位置：`sandbox.py:335`

```python
# 现状：每帧每只敌人 O(路线数) 线性扫描
def analysis_for(self, event_or_index):
    idx = ... getattr(event_or_index, "route_index", -1)
    for ra in self.analyses:
        if getattr(ra, "route_index", None) == idx:
            return ra
```

改法：在 `recompute()` / `analyze_all` 结果赋值处同步维护
`self._by_route = {ra.route_index: ra for ra in self.analyses}`，
`analysis_for` 直接 `return self._by_route.get(idx)`。

**约束**：不要用 `self.analyses[idx]` 下标访问——`analyze_all` 可能过滤
不可达路线，下标会错位。

#### A0.2 `_blocking_plan` 缓存键与 `t` 脱钩

位置：`sandbox.py:483`（函数）、`sandbox.py:498`（缓存判据）

现状：

```python
if (self._plan_cache_time == t and self._plan_cache is not None):
    return self._plan_cache
```

**实测证明该函数返回值与 `t` 无关**（同一关卡 `plan(0) == plan(150) == plan(300)`
逐条相同）。播放时 `t` 每帧都变，所以缓存**必然每帧失效**，
冷算 **88.66 ms**，命中 **0.0001 ms**。

改法：把缓存键换成「干员配置签名」，例如

```python
def _plan_sig(self):
    return tuple(sorted(
        (d.uid, d.row, d.col, d.deploy_time,
         d.retreat_time, d.block_count, d.can_block_fly)
        for d in self.track.all()))
```

`_invalidate_plan()` 现有调用点保持不变。**改完必须验证**
`plan(t) for t in (0,150,300)` 三者仍相同。

### A1 结束机制重定义（P0，1.5 人天）

#### A1.1 问题实证（先复现，再改）

`a001_06` 在 `(2,5)` 部署一枚 `block_count=1` 的近战干员，然后问
"播放到最后时刻，场上还有谁"：

```
_track_total 收尾时刻: 271.61
收尾时刻仍被钉在 (2,5) 的敌人: 1
   enemy_1001_bigbo  spawn 0.0  收尾时 (2.0, 5.0)  再 +300s 仍是 (2.0, 5.0)
```

**敌人永远到不了蓝门，但播放条到 271.61s 就结束了。**

根因：`arrival_time()` 算的是「无阻挡要走多久」，**完全不看 `_blocking_plan`**。

> **复现时必须用 `Sandbox.deploy(row, col, Deployment(...))`。
> 用 `place_operator()` 不行**——它不建 `Deployment`，`block_count=0`、`uid=0`，
> 根本挡不住任何敌人。这一点已踩过一次坑。

#### A1.2 三处时长口径各不相同（必须统一到沙盘口径）

| 位置 | 算法 | `a001_06` 实测 |
|---|---|---|
| `CoarseTrack.span()`（`sandbox_track.py:391`） | 只取动作时间，最小 1.0 防除零 | **1.0** |
| `Timeline.span(analyses)`（`timeline.py`） | `max(出场+无阻挡总时长) + 1.0` | **272.61** |
| `SandboxPanel._track_total()`（`sandbox_panel.py:2217`） | 上面取大，再逐只 `arrival_time` | **271.61** |

**不要改 `arrival_time` 和 `Timeline.span`**——路线分析必须忽略干员，
否则两个面板互相污染。要新增独立的沙盘收尾判定，让
`_track_total` 改用它。

#### A1.3 敌人状态机（八态）

| 状态 | 判定依据 | 是否「还在动」 |
|---|---|---|
| `PENDING` | `t < 出场时刻` | 否 |
| `MOVING` | 在路线上推进 | **是** |
| `BLOCKED` | `_blocking_plan` 有记录且 `t ∈ [arr_wall, release)` | 否 |
| `WAITING` | `ra.wait_span_at(route_secs)` 非空（路线自带罚站） | 否（会自恢复） |
| `SLOWED` | `speed_at()` < 1 但 > 0 | **是** |
| `LEAKED` | 走到蓝门 | 否（终态） |
| `VANISHED` | 走完 `vanish=True` 路线后消失 | 否（终态） |
| `KILLED` | 被 `kick()` | 否（终态） |
| `STUCK` | 被永久减速/永久阻挡，永远到不了终点 | 否（死锁） |

**`VANISHED` 绝对不能省。** 实测全库 2629 关中 **750 关（28.5%）含 `vanish` 路线**：

```
act10mini_03 route 6: total_time=25.00
  pose(end-0.1) = (1.05, 4.0)    还在场上
  pose(end)     = None           到终点消失
  note: "1 次瞬移，中途离场"
```

这类路线**终点不是蓝门**。若当成 `LEAKED` → **凭空扣血**；
当成 `STUCK` → **误报死锁**。判据是 `RouteAnalysis.vanish`（已有字段）。

#### A1.4 三层结束判据

| 判据 | 条件 | `verdict` |
|---|---|---|
| A 全部解决 | 所有敌人在 `{LEAKED, VANISHED, KILLED}` | `ALL_RESOLVED` |
| B 全部停滞 | 全在 `{LEAKED, VANISHED, KILLED, BLOCKED, WAITING, STUCK}`，无 `PENDING`，且**至少一只**在 `{BLOCKED, WAITING, STUCK}` | `DEADLOCK` |
| C 安全上限 | 模拟时长 > `max(600, 3 × 无阻挡总时长)` | `TIMEOUT` |

**判据 B 就是用户说的那个场景**，必须实现，且 `DEADLOCK` 时
**不停在"无阻挡时长"处**，要停在"确认再无任何运动会发生"处。

#### A1.5 停滞判定不许用「几帧没动」

一个诱人的错误写法：连续 N 帧位置不变 → 判定卡死。
**这会误判路线自带的罚站**（`wait_after` > 0 时敌人确实原地不动几秒，
之后会继续走）。必须**查状态**（`_blocking_plan` / `wait_span_at` /
`speed_at`），不许查位移。

#### A1.6 新增两个接口

```python
def state_at(self, seconds: float) -> dict:
    """返回 {time, enemies[], counts{}, verdict}。
    enemies[] 每项含 key / enemy_id / row / col / state /
    blocked_by / blocked_at / route_index / progress / eta_goal。
    counts 含 moving/blocked/waiting/leaked/vanished/killed/stuck/pending。
    verdict ∈ RUNNING|ALL_RESOLVED|DEADLOCK|TIMEOUT。"""

def solve_end(self) -> dict:
    """返回 {end_time, verdict, leaked, vanished, killed,
    stuck[], life_lost, warnings[]}。多次调用必须幂等。"""
```

`eta_goal`（预计还需多少秒到蓝门）是**沙盘最有价值的输出**——
UI 能在敌人旁边标「12s」，用户立刻知道要不要现在开技能。

#### A1.7 收尾时刻算法

```
对每只敌人:
  若 被挡 且 挡的人永不撤退   → STUCK，不参与 end_time
  若 被挡 且 在 t_r 撤退      → 到达 = t_r + 从阻挡格走完剩余路程
  否则                        → 到达 = 出场时刻 + arrival_time()
end_time = max(所有能到终点者的到达时刻, 最后一只出场时刻)
```

`end_time` 取「尘埃落定」时刻，不是「最后一只到达」时刻。

#### A1.8 `_track_total` 接线

`sandbox_panel.py:2217` 改为：

```python
def _track_total(self) -> float:
    if self.sandbox is None:
        return 60.0
    return max(60.0, self.sandbox.solve_end()["end_time"])
```

`CoarseTrack.span()` 不再参与播放时长（它本来就只是「动作时间跨度」）。
**但不要删 `span()`**，别处可能在用。

### A2 画面表现（P1，2 人天）

#### A2.1 先看真实瓶颈（别再猜）

`act1multi_football` 的 `render()` 用 **cProfile** 实测（200 只）：

```
_draw_enemies 累计 0.400s / 3 帧
  └─ ImageDraw.text       0.310s   ← 77%
       └─ ImageFont.getmask2 → Font.render   0.259s
  └─ 重叠错开 listcomp    0.050s   ← 12%
  └─ alpha_composite      0.024s   ←  6%
```

**结论：77% 的时间在「给每只敌人现场渲染中文名字」。**

分敌人数量实测（1400×900 视口）：

| 同时在场 | render 耗时 | fps |
|---|---|---|
| 10 | 8.6 ms | 116 |
| 40 | 26.3 ms | 38 |
| 160 | 93.3 ms | 11 |
| 320 | 196.8 ms | 5 |
| 1361 | **887 ms** | **1** |

成本随数量**线性**增长（每只约 0.5~0.6 ms），**不是 O(n²) 主导**。
所以「优化 O(n²)」只能拿回 12%，**必须动文字和显示策略**。

#### A2.2 三条改法（按收益排序）

| # | 改法 | 实测收益 | 说明 |
|---|---|---|---|
| 1 | **名字只画悬停/高亮的那一只** | 最大 | 现在 `map_render.py:1512` 是 `if self.cell >= 30 or hov or hit`，**默认视口 cell≈93 恒为真**，等于全画。改成 `if hov or hit` |
| 2 | 名字预渲染成 sprite 缓存 | 2.0× | 即使保留常显，也把 `(文字, 字号)` 缓存成 Image，之后只 `alpha_composite`。实测 336.7 → 166.8 ms |
| 3 | 重叠错开改分桶 | 179×（局部） | 现在 `map_render.py:1473` 每只都遍历全部。改按 `(round(r*2)/2, round(c*2)/2)` 建桶。微基准 118.6 → 0.76 ms，**结果逐项一致**（已验证） |

#### A2.3 按格聚合（唯一能到 60fps 的路径）

即使做完上面三条，1361 只仍约 20 fps。**必须加聚合显示**：

实测：

```
1361 只 → 聚合到 117 格
画 117 个「圆 + 数字」 = 13.7 ms → 73 fps        （对比当前 3 fps，提速 25×）
```

规则：

* 同格多只 → 画一个圆，半径 `min(rad * (1 + 0.55*log2(n)), cell*0.40)`；
* `n > 1` 时圆心写数字；
* **仅影响显示**，`solve_end()` 仍逐只精算；
* 提供开关「逐只 / 聚合」，默认在同时在场 > 60 只时自动切聚合。

同姓干员无法区分。头像资源 `data/icons/operator/128/*.png` 共 **461 张**
（缺 `暮落(集成战略)`、`真言` 两个，需退化为首字）。

**放在 A 批次做**（纯渲染、零逻辑风险、用户立刻看得见）。

### B6 桥接：允许的「只读计算」

沙盘**不模拟伤害**，但分析层**可以调用** `core/damage.py` 的纯函数做**可行性判断**：

* `compute_kill_time(total_hp, damage_per_hit, attack_interval)` → 杀这只怪要多久；
* 与「它被阻挡能撑多久」比较，判断「挡得住但杀不掉」；
* 这是**只读计算**，不产生伤害事件、不改沙盘状态。

**仅此一项允许跨越「不模拟伤害」的边界**，其余一律不许。

## 四 分析层：用户到底该算什么

用户要的是「分析后面怎么打」。**不要做计算器，做三个问题的答案。**

### 4.1 问题一：这套布置最后会漏几只？

唯一必须算对的问题。答案来自 `solve_end()`：

```
漏 3 只（2 只重装各扣 1 血，1 只 boss 扣 5 血）→ 共扣 7 血
生命 3 → 必败
```

判据只有一条：**有没有敌人没被击杀却走到了蓝门**。
不需要伤害计算，几何 + 阻挡容量 + 时间就够，**现在就能算对**。

### 4.2 问题二：漏的是哪一只、什么时候、从哪漏？

`solve_end()` 的 `leaked` 不能只给数字，必须逐只明细：

```json
{"enemy_id": "enemy_1001_bigbo", "leak_time": 47.3,
 "route_index": 3, "goal_cell": [6, 5],
 "reason": "block_capacity_exceeded",
 "blocker_uid": 2, "blocker_cell": [2, 5],
 "concurrent_blocked": 2, "blocker_capacity": 1}
```

`reason` 枚举：`no_blocker` / `block_capacity_exceeded` /
`blocker_retreated` / `flying_ignored` / `blocked_forever`。

### 4.3 问题三：要改成不漏，最少动哪一步？

**不做全局最优搜索**（组合爆炸、结果不可信、用户不会信）。
做三个廉价定向建议，每个 < 100 ms：

| 建议 | 算法 | 输出 |
|---|---|---|
| 补位 | 对每条漏怪路径，找经过的空可部署地面格，按「覆盖最多漏怪路线」排序 | 「在 (3,4) 放个近战可挡这 3 只」 |
| 加阻挡数 | 漏因是 `block_capacity_exceeded` 时，找该格相邻阻挡位/更高阻挡干员 | 「(2,5) 换成阻挡 2 的」 |
| 撤晚 | 漏因是 `blocker_retreated` 时，二分撤退时刻直到不漏 | **「最少守到 61.4s」** |

第三个尤其有用——**「最少守到几秒」是沙盘能给的最精确答案**。

### 4.4 明确不做

| 别做 | 原因 |
|---|---|
| 全局最优部署搜索 | 组合爆炸，结果不可信 |
| DPS 排行榜 | 沙盘不模拟伤害，假精度 |
| 「预计通关率 %」 | 无数据支撑，纯编造 |
| 自动算技能轴 | 技能效果不模拟，轴对不上实战 |

**沙盘是验算，不是求解。** 用户出方案，沙盘告诉他结果。

### 5.1 批次 A 新增

**性能**
1. `act1multi_football` 单帧计算阶段 ≤ 5 ms。
2. 同关 `render()` ≤ 18 ms（聚合模式）。
3. `_blocking_plan` 连续调 3 次，第 2、3 次耗时应 < 第 1 次的 1%。

**结束机制**
4. 空场（无干员）→ `verdict = ALL_RESOLVED`，`end_time ≈ 无阻挡总时长`。
5. 永久阻挡且容量够 → `verdict = DEADLOCK`，`stuck` 列出该敌人。
6. 阻挡后 60s 撤退 → `ALL_RESOLVED`，`end_time ≈ 60 + 剩余路程`，
   且该敌人**确实最终到达蓝门**。
7. 容量不足 → 超容量者 `LEAKED`，`reason = block_capacity_exceeded`。
8. 路线含长罚站（如 H8-4）→ 罚站期间 `state = WAITING`，
   **不得**误判 `STUCK`/`DEADLOCK`。
9. `vanish` 路线（`act10mini_03` route 6）→ 终点后 `state = VANISHED`，
   不计 `leaked`、不扣血、不触发 `DEADLOCK`。
10. 同关同时有 `vanish` 与普通路线 → 两终态并存，`verdict` 正确。

**一致性**
11. `verdict = ALL_RESOLVED` 时，逐只走完时间与 `end_time` 误差 < 0.1s。
12. 同配置重复调 `solve_end()` 结果完全相同（幂等）。
13. 增删箱子（不改变阻挡）**不得**改变任何敌人的 `LEAKED` 状态。

**渲染**
14. 8 个不同干员 → 8 个头像互不相同。
15. 缩放 0.5×~3× 头像清晰。
16. `暮落(集成战略)`、`真言` → 首字退化，不是白块。
17. **静态层重烘焙次数不因头像/图标增加**。
18. 重叠错开改分桶后，同一帧的偏移量与改前**逐项一致**。
