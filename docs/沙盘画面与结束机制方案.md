## 零 一句话结论

现在的播放有**三个独立的问题**，必须分开修，否则会互相掩盖：

| # | 问题 | 性质 | 实测证据 |
|---|---|---|---|
| 1 | 一帧 142ms，理论 7fps | **性能** | `act1multi_football` 实测 |
| 2 | 播放条结束时刻按「无阻挡路线」算 | **逻辑** | 被挡住的敌人仍钉在场上 |
| 3 | 沙盘没有「目标」概念 | **语义** | `summary()` 只有「敌人 97/97」 |

其中 **第 2 条是你这次指出的核心问题**，而且是真 bug，不是设计取舍。

## 一 播放画面为什么卡：两个必现的放大因子

### 1.1 现场测量

`act1multi_football`（13×9 格，1361 条路线，1393 只敌人）逐帧耗时：

```
t=  30s  在场 1377 只  一帧 135.33 ms  → 理论上限  7 fps
t= 120s  在场 1393 只  一帧 142.31 ms  → 理论上限  7 fps
t= 240s  在场 1393 只  一帧 136.45 ms  → 理论上限  7 fps
t= 300s  在场 1393 只  一帧 142.82 ms  → 理论上限  7 fps
```

**先纠正一个容易误读的口径**：上面的 142 ms 是**计算阶段**
（逐只 `pose_at` + `_blocking_plan`）的耗时，**不是整帧**。

真正的端到端一帧还要加上渲染。本机实测
（`act1multi_football`，t=2s，**1361 只同时在场**）：

| 阶段 | 耗时 |
|---|---|
| 计算（`pose_at` 全量，plan 冷） | **121.3 ms** |
| 渲染 `render()`（底图 + 敌人） | **933.8 ms** |
| **端到端一帧** | **1055.1 ms → 约 0.9 fps** |

**所以最坏关卡的真实体验是 1 fps 左右，不是 7 fps。** 而且
**渲染比计算还贵 8 倍**，两边都必须修——只修计算会卡在渲染（933 ms），
只修渲染会卡在计算（121 ms）。

普通关卡则完全正常（按「同时在场」实测，不是按「路线总数」）：

| 关卡 | 同时在场 | `render()` | fps |
|---|---|---|---|
| `main_04-04` | 0 | 1.0 ms | 1040 |
| `a001_06` | 11 | 2.0 ms | 509 |
| `main_08-04` | 0 | 0.9 ms | 1104 |
| `act1multi_06` | 39 | 3.4 ms | 290 |
| `act1multi_football` | **1361** | **267.6 ms** | **3.7** |

**关键**：`act1multi_06` 有 955 只敌人、1361 条路线，但因为出怪分散，
某时刻只有 39 只在场 → **3.4 ms，完全不卡**。
所以决定性能的不是「关卡有多少敌人」，而是**「某一时刻同时在场多少只」**。
只有 `act1multi_football` 这种 **t=0.1s 就涌出 1361 只**的关卡会崩。

这不是「所有关卡都卡」，是**单一关卡的极端同屏**。

### 1.2 根因 A：`_blocking_plan` 的缓存键是时间，但结果与时间无关

`sandbox.py:483` 的 `_blocking_plan(seconds)` 缓存判据是：

```python
if (self._plan_cache_time == t and self._plan_cache is not None):
    return self._plan_cache
```

`t` 是**当前播放时刻**。播放时每帧 `t` 都不同 → 缓存**必然每帧失效**。

但我实测了它到底依不依赖 `t`：

```
plan(t=0)   条数: 1
plan(t=150) 条数: 1
plan(t=300) 条数: 1
三者完全相同 : True
```

**返回值与 `t` 完全无关。** 因为函数内部虽然 `if t < t_spawn: continue` 跳过未出场的，
但真正决定「谁被谁挡」的是 `arr_wall` 与 `dep.alive_at(arr_wall)`——
两者都只依赖**干员配置**和**出怪时间**，与「你正在看哪一秒」无关。

冷启动一次 `_blocking_plan` = **88.66 ms**，缓存命中 = **0.0001 ms**。

> 这不是「缓存没做好」，是**缓存键选错了维度**。时间根本不进这个函数的语义。

### 1.3 根因 B：`analysis_for` 是线性扫描，且每帧每只敌人调一次

`sandbox.py:335`：

```python
def analysis_for(self, event_or_index):
    idx = ... getattr(event_or_index, "route_index", -1)
    for ra in self.analyses:            # ← O(路线数) 线性扫描
        if getattr(ra, "route_index", None) == idx:
            return ra
```

而 `_refresh_frame` 对**每只在场的敌人**都调 `pose_at` → `analysis_for`：

```
analysis_for ×1393   :  27.60 ms      ← 光查表就 27.6ms
pose_at 全量(plan已缓存):  32.62 ms
纯 ra.pose_at        :  30.03 ms
```

1393 只 × 1361 条路线 = **190 万次属性比较/帧**。

### 1.4 修复后实测

同一关卡，只做「`route_index → RouteAnalysis` 建索引」+「plan 缓存与 t 脱钩」
（**注意：这只修计算阶段，渲染的 933 ms 仍需 §四 的改法**）：

```
修复后一帧（索引 + plan 缓存）:    1.09 ms → 914 fps
修复前实测                    :  142.31 ms → 7 fps
提升倍数                      : 130.1x
```

**130 倍。** 而且这两处改动都是**纯内部优化，不改变任何语义**——
`_blocking_plan` 本来就该与 t 无关，索引只是把 O(n) 换成 O(1)。

### 1.5 还有一个隐藏的写法问题

`analysis_for` 用 `for` + `getattr(ra, "route_index", None) == idx` 逐条比，
但 `self.analyses` 是 `List[RouteAnalysis]`，`route_index` 在 `analyze_all` 里
是**顺序生成的**。理论上可以直接下标。不过为了不依赖这个假设（万一将来
`analyze_all` 过滤掉了不可达路线，下标就错位），方案里用**显式字典**而不是下标。

## 二 结束机制：现在的口径是错的

### 2.1 现状：三处各算各的，没有一处是「沙盘口径」

| 位置 | 算法 | 结果 |
|---|---|---|
| `CoarseTrack.span()`（`sandbox_track.py:391`） | 只取**动作时间**（部署/撤退） | `1.0` 秒 |
| `Timeline.span(analyses)`（`timeline.py`） | `max(出场时刻 + 该路线 total_time)` | 只算无阻挡 |
| `SandboxPanel._track_total()`（`sandbox_panel.py:2217`） | 上面两者取大，再逐只 `arrival_time` | `271.61` 秒 |

三者在同一张 `a001_06` 上实测分别是 **1.0 / 272.61 / 271.61**。
注意 `Timeline.span()` 给的是 272.61、`_track_total()` 给的是 271.61——
**两者还差 1 秒**，因为 `Timeline.span` 末尾 `+1.0` 留了尾巴，
而 `_track_total` 逐只 `arrival_time` 求和没有留。两个面板各用各的，
连「尾巴留不留」都不一致。

**第一条就已经是错的**：`track.span()` 返回 1.0 是因为「没有部署动作时最小值给 1 秒防除零」，
它压根不是「播放时长」的语义，却被 `_track_total` 当成候选值混进来了。

### 2.2 你指出的问题，我复现了

在 `a001_06` 的 `(2,5)` 放一枚阻挡数 1 的近战干员，然后问「播放到最后时刻，
场上还有谁」：

```
_track_total 收尾时刻: 271.61
收尾时刻被钉在 (2,5) 的敌人: 1
   enemy_1001_bigbo       spawn    0.0  在收尾 (2.0, 5.0)  再+300s (2.0, 5.0)
```

那只敌人**被永远钉在 (2,5)**，`+300 秒`后位置一模一样——它这辈子到不了蓝门。
但播放条在 271.61s 就走到头了，画面上它还挂着。

### 2.3 根本原因

`arrival_time()` 算的是「**这条路无阻挡时要走多久**」：

```python
w = t_spawn + head + ra.pre_wait
for seg in ra.segments:
    w = self._advance(...)       # 只吃 buff，不吃阻挡
```

它**完全不看 `_blocking_plan`**。所以：

> 只要有任何一只敌人被挡住，`_track_total` 就会**低估**总时长。
> 挡得越久，低估越多；永久挡住 → 低估到无穷。

### 2.4 你说得对：沙盘和路线分析本来就该是两套口径

路线分析的任务是「这条路线本身有多长」——它**必须**忽略干员，
否则「路线分析」会依赖沙盘状态，两个面板会互相污染。

沙盘的任务是「**复现我当时打到的情况，然后看后面怎么打**」。它的时长必须由
**沙盘状态**决定：干员挡住了，敌人就还没进去，沙盘就不该结束。

所以正确做法不是「修改 `arrival_time`」，而是**给沙盘一个独立的收尾判定**，
让路线分析保持原样。

## 三 沙盘的结束条件应该怎么定义

### 3.1 先明确：什么叫「沙盘结束」

沙盘不是视频播放器，它的结束不该由「时间轴放完了」决定，而该由
**「场上没有还在动的敌人了」**决定。

我建议用**三层判据**，从强到弱：

| 判据 | 含义 | 触发后的行为 |
|---|---|---|
| **A 全部解决** | 所有存活敌人要么**到达蓝门**（漏怪计入扣血），要么**被击杀**（`kicked`） | 正常结束，出结算 |
| **B 全部停滞** | 所有存活敌人都**停在原地**（被挡 / 被永久减速），且未来不会有新敌人出场 | 结束，但标记为「**僵持**」，提示用户这里有死锁 |
| **C 安全上限** | 模拟时长超过 `上限`（建议 `max(600, 3×无阻挡总时长)`） | 强制结束，标记「**超时截断**」 |

判据 B 是必需的：**你举的例子正是 B**。干员卡住一只怪、怪没进去，
沙盘不能「结束」了事，但也不能无限播下去——它应该**停下来并告诉你
「这里卡住了，敌人 X 被 Y 挡在 (r,c)，永远不会到蓝门」**。

这才是沙盘该有的产出：不是「放完了」，而是**「你的布置会导致这个结果」**。

### 3.2 每只敌人的状态机

把「一只敌人在沙盘里的命运」显式化，而不是靠 `pose_at` 返回 `None` 来间接表达：

| 状态 | 判定 | 是否还在动 |
|---|---|---|
| `PENDING` | `t < t_spawn` | 否（还没出场） |
| `MOVING` | 在路线上推进 | **是** |
| `BLOCKED` | 被挡在干员格 | 否 |
| `WAITING` | 路线里的固定罚站 | 否（但会自己恢复） |
| `SLOWED` | 减速但仍在动 | **是** |
| `LEAKED` | 到达蓝门 | 否（终态） |
| `VANISHED` | 走到 `vanish` 路线终点后消失（**不是漏怪**） | 否（终态） |
| `KILLED` | 被 `kick` | 否（终态） |
| `STUCK` | 被永久减速（倍率 ≤ 0 且无结束时刻） | 否（终态） |

**`VANISHED` 这个状态不能省**。我原来漏了它，实测才发现：

```
全库 2629 关里,750 关 (28.5%) 含 vanish 路线
act10mini_03 的 route 6: total_time=25.00
   pose(end-0.1) = (1.05, 4.0)     ← 还在场上
   pose(end)     = None            ← 到终点就消失
   note: "总路程 10.00 格，移动 20.00s + 途中停驻 5.00s（1 次瞬移，中途离场）"
```

`vanish=True` 的路线**终点不是蓝门**，敌人走到那儿就当它离场了（传送 / 潜入类）。
如果不区分，会把它算成 `LEAKED` → **凭空多扣血**，或者算成 `STUCK` → **误报死锁**。
两者都是错的。判据是 `RouteAnalysis.vanish`（`routes.py` 已算好，现成字段）。

判据 A = 所有敌人都在 `{LEAKED, VANISHED, KILLED}`。
判据 B = 所有敌人都在 `{LEAKED, VANISHED, KILLED, BLOCKED, WAITING, STUCK}` 且无 `PENDING`，
其中**至少一只**属于 `{BLOCKED, WAITING, STUCK}`（否则就是 A 了）。

注意 `VANISHED` 在 A 和 B 里都算「已解决」，因为它不扣血、也不卡住。

### 3.3 「全部停滞」的判定不能靠「这一帧没人动」

一个诱人的错误写法：**连续 N 帧所有敌人位置都没变 → 判定停滞**。

这个写法会误判：路线里本来就有 `wait_after` 罚站（`a001_06` 的 segment 里
就有 `wait_after=0.0`，但其他关有非零值），罚站期间敌人确实不动，
但它过几秒就会继续走。用「几帧没动」判会把它当成卡死。

**正确做法是查状态，不是查位移**。状态来自：
* `BLOCKED`：`_blocking_plan` 里有这条记录且当前时刻落在 `[arr_wall, release)`；
* `WAITING`：`ra.wait_span_at(route_secs)` 返回非空；
* `STUCK`：`speed_at()` 返回 ≤ 0 且该 buff 没有结束时刻。

这三个都是**已有函数**（`sandbox.py` 里都有），不需要新算法。

### 3.4 建议新增的接口

```python
def state_at(self, seconds: float) -> dict:
    """沙盘在某时刻的完整状态快照（供 UI 与结论使用）。"""
    return {
        "time": seconds,
        "enemies": [                      # 只含已出场且未终结的
            {"key": str, "enemy_id": str, "enemy_name": str,
             "row": float, "col": float,
             "state": "MOVING|BLOCKED|WAITING|SLOWED|LEAKED|KILLED|STUCK",
             "blocked_by": Optional[int],  # 干员 uid
             "blocked_at": Optional[str],  # "r,c"
             "route_index": int,
             "progress": float,            # 0.0 ~ 1.0
             "eta_goal": Optional[float]}, # 预计到达蓝门还需多少秒
        ],
        "counts": {"moving": int, "blocked": int, "waiting": int,
                   "leaked": int, "killed": int, "stuck": int,
                   "pending": int},
        "verdict": "RUNNING|ALL_RESOLVED|DEADLOCK|TIMEOUT",
    }

def solve_end(self) -> dict:
    """沙盘收尾：算出这场推演到底什么时候结束、为什么结束。"""
    return {
        "end_time": float,
        "verdict": "ALL_RESOLVED|DEADLOCK|TIMEOUT",
        "leaked": int,                  # 漏怪数（真实到达蓝门）
        "vanished": int,                # 中途离场（不计漏怪）
        "killed": int,
        "stuck": [{"key", "enemy_id", "blocked_by", "cell"}],
        "life_lost": int,               # 按 lifePointReduce 累计
        "warnings": [str],
    }
```

`eta_goal` 这个字段值得单独说：**沙盘最有用的产出不是「放完了」，
而是「这只会漏，还有 12 秒到你脸上」**。有了 `eta_goal`，UI 就能在
敌人旁边标「12s」，用户立刻知道该不该现在开技能。

### 3.5 收尾时刻怎么算

不能再用 `max(t_spawn + arrival_time)`。正确算法是**分段求解**：

```
for 每只敌人:
    如果 被挡 且 干员永不撤退:
        → 它永远不会到终点 → 归入 STUCK，不参与 end_time
    如果 被挡 但 干员在 t_r 撤退:
        → 到达时刻 = t_r + 从阻挡格走完剩余路程的时长
    否则:
        → 到达时刻 = t_spawn + arrival_time()（现有逻辑）
end_time = max(所有能到终点的敌人的到达时刻, 最后一只出场时刻)
```

**注意**：`end_time` 应该取「所有敌人**都尘埃落定**」的时刻，
而不是「最后一只到达终点」的时刻——如果有一只被永久挡住，
它虽然不影响 `end_time`（它永远不结束），但会让 `verdict` 变成 `DEADLOCK`。

### 3.6 与「死亡」的关系

现在沙盘没有生命值，所以「漏怪」只是个数字。等 §五（B2）的 `core/dp.py`
做完之后，`leaked` 应该直接扣 `lifePointReduce` 并触发失败判定。

在那之前，`life_lost` 可以先按 `lifePointReduce` 累计**仅作提示**，
不影响播放（因为生命值系统整体还没接）。

## 四 画面表现：除了性能还能改什么

性能是「不卡」，表现是「好看、好读」。分开说。

### 4.1 敌人用图标而不是彩色圆点

现状（`map_render.py:1509`）：

```python
sp = _dot_sprite(ecol, rr, ring=True)
im.alpha_composite(sp, (int(x - sp.width / 2), int(y - sp.height / 2)))
```

所有敌人都是**同款圆形+按名字哈希的随机颜色**。问题：
* 颜色是哈希出来的，**没有语义**——同一个兵种同色，但不同兵种可能撞色；
* 看不出是什么怪（源石虫 vs 重装 vs 无人机）；
* 看不出朝向、看不出是否在攻击。

**而敌人图标已经在本地了**：`akcalc/data/icons/enemy/` 下有
**7192 张 png**（64/96/128/44 四档），`core/enemy_icons.py` 已有 loader
（`EI.load_icon`），`monster_codex.py` / `data_index.py` / `path_panel.py`
都在用。

所以「敌人显示图标」**不需要新下载任何资源**，只需要在 `_draw_enemies` 里
换成 `alpha_composite(icon)`。做法与 §八（干员头像）完全同构：

1. 图标预缩放到当前 `cell` 尺寸，缓存 `(enemy_id, px) → Image`；
2. `im.alpha_composite(icon, (x-w/2, y-h/2))`；
3. 圆形底色保留作为**阵营/状态**指示（减速蓝圈、被挡红圈），叠在图标下面；
4. 名字仍然只在 `cell >= 30` 或悬停时画。

**风险一：首次加载开销。** 实测 `EI.load_icon` 冷 **107.70 ms** / 热 **0.84 ms**。
一关的不同敌人种类实测：`act1multi_football` **35 种**、`main_08-04` 只有 **4 种**。
即便一次只加载本关用到的，35 × 107.7 ms ≈ **3.8 秒**，同步加载必卡死。

**必须走异步**：`EI.load_icon_async(paths, name, px, on_done=...)` 是现成的，
加载期间用 `EI.placeholder_icon(name, px)` 占位。注意它的签名是
`placeholder_icon(name, px)` —— **第一个参数是名字不是尺寸**，
传 `placeholder_icon(64)` 会抛 `AttributeError: 'int' object has no attribute 'strip'`。

**风险二：名字对不上。** 这是更隐蔽的坑。`SpawnEvent.enemy_name` 里存的
**是 ID 不是中文名**：

```
act1multi_football 的 enemy_name 实取样:
['enemy_1021_bslime', 'enemy_1047_sagent_2', 'enemy_1067_snslime', ...]
```

而 `EI.load_icon(paths, name, px)` 是按**中文名**找文件的
（`icons/enemy/64/源石虫.png`）。直接把 `enemy_name` 丢进去会全部 fallback 到占位图。
必须先经 `enemy_icon_alias.json`（`core/enemy_icons.py` 已在用）把
`enemy_id → 中文名` 查一遍——**`path_panel.py` 里已经有这套查表逻辑，可复用**。

**风险三：图标是正方形，圆点是圆的。** 直接 `alpha_composite` 会盖住干员格线，
需要统一裁成圆角（或圆形蒙版），否则 `act1multi_football` 这种 13×9 的小图上
35 种图标挤在一起会糊成一片。

### 4.2 干员棋子显示头像（§八 已规划，这里只说联动）

`docs/沙盘完全模拟与战斗机制规格.md` §八 已经写了完整方案。这里补充一点：
**如果敌人也上图标，干员头像的尺寸基准要跟着调整**，否则会出现
「敌人图标 48px、干员头像 24px」的视觉失衡。

建议统一为 **`cell × 0.42`** 的正方形（干员与敌人同一基准），
而不是现在 §八 里的 `cell × 0.34`。理由：图标有内部留白，
同尺寸下看起来比纯色圆点小一圈。

### 4.3 阻挡关系的可视化

现在「谁被谁挡住」只在悬停时显示。播放时应该**直接画出来**：

* 被挡的敌人到干员之间画一条**短促的红色虚线**；
* 干员脚下显示 **`2/3`**（已挡/容量）的小角标；
* 超容量的敌人（漏过去的）用**半透明**表示「它没被挡住」。

这三条都不需要新数据——`_blocking_plan` 的返回值里全都有
（`cell` / `blocked` / 干员 `block_count`）。

### 4.4 行进方向与速度的视觉编码

敌人圆点现在是个静态圆，看不出朝哪走、走多快。建议：

* 圆点朝前进方向加一个**小三角**（干员棋子已经有这个先例，`map_render.py` 的 facing triangle）；
* 减速中的敌人加**流动的虚线拖尾**（长度 ∝ 1/速度倍率）；
* 停顿（倍率 0）的敌人加**断续闪烁**。

速度信息本来就在 `speed_at()` 里，不需要新算。

### 4.5 时间轴上的「事件密度」条

现在时间轴只有出怪点。建议在时间轴下方再加一条**威胁密度条**：
每个时间窗内的「在场敌人数 × 平均血量」画成热力条。
用户一眼能看出「哪一波最猛」。

这个需要敌人血量（`enemy_database.json` 里有 `hp`），是**纯静态数据**，
可以预计算一次。

| 改动 | 收益 | 成本 | 建议 |
|---|---|---|---|
| 性能修复（§1.4） | **卡→不卡，130×** | 0.5 人天 | **P0，先做** |
| 敌人图标 | 一眼看出兵种 | 1.5 人天 | P1 |

## 五 用户到底应该算什么

这是你问的第三件事，也是最容易被做成「又一个大面板」的地方。
我的建议是：**不要做一个「计算器」，要做三个具体问题的答案**。

### 5.1 问题一：我这套布置，最后会漏几只？

这是**唯一必须回答对**的问题。答案来自 `solve_end()`：

```
漏 3 只（其中 2 只重装，各扣 1 血；1 只 boss，扣 5 血）→ 共扣 7 血
生命 3 → 【必败】
```

判断依据只有一条：**有没有敌人在「没被击杀」的情况下走到蓝门**。
这不需要伤害计算，只需要几何 + 阻挡容量 + 时间。**现在就能算对**。

### 5.2 问题二：如果我漏了，是哪一只、什么时候、从哪漏的？

这是**可行动**的信息。用户拿到「第 47 秒，重装防御者从 (2,5) 漏过，
因为该格干员阻挡数 1 已被占用」才能改。

所以 `solve_end()` 的 `leaked` 不能只给数字，必须给**逐只明细**：

```json
{"enemy_id": "enemy_1001_bigbo", "leak_time": 47.3,
 "route_index": 3, "goal_cell": [6, 5],
 "reason": "block_capacity_exceeded",
 "blocker_uid": 2, "blocker_cell": [2, 5],
 "concurrent_blocked": 2, "blocker_capacity": 1}
```

`reason` 枚举建议：`no_blocker`（路上没干员）、`block_capacity_exceeded`
（有人挡但满了）、`blocker_retreated`（挡的人撤了）、`flying_ignored`
（飞行单位被当地面处理）、`blocked_forever`（永久卡住）。

### 5.3 问题三：要改成不漏，最少动哪一步？

这是**优化问题**，也是用户真正想要的。但**不要做全局最优搜索**——
状态空间是「格 × 干员 × 朝向 × 时刻」的组合爆炸，做出来又慢又不可信。

建议做**三个廉价的定向建议**，每个都能在 100ms 内算完：

| 建议 | 算法 | 输出 |
|---|---|---|
| **补位** | 对每条漏怪路径，找它经过的、当前空着的**可部署地面格**，按「能覆盖最多漏怪路线」排序 | 「在 (3,4) 放一个近战可挡住这 3 只」 |
| **加阻挡数** | 如果漏因是 `block_capacity_exceeded`，找该格换成阻挡数更高的干员 / 加一个相邻阻挡位 | 「把 (2,5) 换成阻挡 2 的干员」 |
| **撤早/撤晚** | 如果漏因是 `blocker_retreated`，算出「最晚可撤退时刻」 | 「(2,5) 的干员至少守到 61.4s」 |

第三个尤其有用：**「最少守到几秒」是沙盘能给出的最精确的答案**，
而且算法极简——把撤退时刻往后推，直到漏怪消失，二分几次就出来了。

### 5.4 明确不要做的

| 别做 | 原因 |
|---|---|
| 全局最优部署搜索 | 组合爆炸，结果不可信，用户也不会信一个「AI 帮我摆好了」 |
| DPS 排行榜 | 沙盘不模拟伤害（用户明确排除），算出来是假精度 |
| 「预计通关率 %」 | 没有任何数据支撑，纯编造 |
| 自动计算技能轴 | 技能效果不模拟，轴算出来对不上实战 |

**沙盘的定位是「验算」，不是「求解」。** 用户自己出方案，沙盘告诉他
这个方案的结果。这比「AI 替你打」有价值得多，也不会给出假答案。

## 七 验收标准

### 7.1 性能

```
act1multi_football 逐帧 ≤ 3 ms（当前 142 ms）
任意关卡 60fps 播放不掉帧
连续播放 5 分钟内存增长 < 50 MB
```

### 7.2 结束机制

```
1. 空场（无干员）→ verdict = ALL_RESOLVED，end_time ≈ 无阻挡总时长
2. 放一个永久阻挡、容量足够 → verdict = DEADLOCK，stuck 列出该敌人
3. 放一个阻挡后 60s 撤退 → verdict = ALL_RESOLVED，
   end_time ≈ 60 + 剩余路程，且该敌人确实最终到达蓝门
4. 放一个容量不足的阻挡 → 超容量的敌人 LEAKED，
   reason = block_capacity_exceeded
5. 路线里有长罚站的关卡（如 H8-4）→ 罚站期间 state = WAITING，
   不得被误判为 STUCK 或 DEADLOCK
6. vanish 路线（如 act10mini_03 route 6）→ 走到终点后 state = VANISHED，
   不计入 leaked、不扣血、不触发 DEADLOCK
7. 同时有 vanish 路线和普通路线的关卡 → 两种终态并存，verdict 正确
```

### 7.3 逻辑一致性

```
1. 沙盘 verdict = ALL_RESOLVED 时，逐只敌人走完的时间
   必须与 solve_end().end_time 一致（误差 < 0.1s）
2. 同一次配置，重复计算 solve_end() 结果必须完全相同（幂等）
3. 加/减一个箱子（不影响阻挡）不得改变任何敌人的 LEAKED 状态
```
