## 零、先纠正三处认知，再谈改法

讨论前必须先把三件事说清楚，否则后面每一行都会建立在错误前提上。

### 0.1 敌人抬手**本来就是逐个体**的，不是全局值

我先把现有数据拆开数了一遍：

| 事实 | 数值 | 说明 |
|---|---|---|
| 有抬手数值的敌人 | **1857** | `data/enemy_attack_timing.json` 的 `by_id` 条目数 |
| 敌人 id 总数 | 2186 | `enemy_database.json` |
| 抬手取值**种类** | **62 种** | 不是 1 个全局常数 |
| 最短 / 最长 | 0.0000 s / 4.8333 s | 相差 **145 帧** |
| 中位数 | 0.5667 s（17 帧） | |
| 有多个攻击动画分支的敌人 | **358** | 例如 `Attack_A` / `Attack_B` 各自一套时间 |

分布长这样（同一抬手值的敌人数）：

```
0.5000s(15帧) 169只    0.4000s(12帧) 135只    0.5333s(16帧) 135只
0.4667s(14帧) 134只    0.4333s(13帧) 108只    0.6000s(18帧) 106只
0.5667s(17帧) 102只    0.3667s(11帧)  76只    0.6333s(19帧)  75只
```

**结论**：数据层没有「统一抬手」这个问题。你的判断对——抬手就该逐个敌人不同，而现有数据也确实是逐个敌人的。
所以「敌人图鉴没有抬手数据」不是**数据缺失**，而是**入口/可见性问题**（见 §1.2）。

### 0.2 敌人图鉴的抬手卡**已经写好了**，但只在未提交的改动里

`akcalc/ui/monster_codex.py` 目前 `git` 状态是 **M（已修改未提交）**，`git diff --stat` 显示 `+74` 行全新增，其中就包含：

| 行号 | 内容 |
|---|---|
| `:18` | `from ..core import enemy_timing as ETIM` |
| `:453` | `def _timing_card(self, master)` |
| `:484 / :490 / :516` | 三处 `self._card(master, "抬手（攻击前摇）", ...)` |
| `:173 / :200` | 两个挂载点（敌库加载 / 未加载都会画） |

也就是说：**代码走的是新分支，如果你跑的是已提交版本或 `dist/` 里的旧 exe，看到的就是没有抬手卡的界面。**
这是「图鉴里没有」最可能的直接原因，需要先确认你实际运行的是哪一个。

### 0.3 抬手**已经进了 MCP**，所以「图鉴没有」与「接口没有」是两件事

`akcalc/mcp/tool_enemies.py` 已经输出这些字段：

```
attack_windup_seconds     抬手秒数
attack_windup_frames      抬手帧数
```

并提供 `enemy_attack_timing` / `attack_timing_convert` 两个工具。`docs/MCP接口说明.md` 里也写了用法。
如果外部 AI 那边能拿到抬手、而你界面上看不到，那就**坐实了问题出在 UI 版本，不在数据**。

## 一、抬手数据：现状审计

### 1.1 数据源与解析链路（这条链是对的）

```
解包 zh_CN/gamedata/bakemuzzledata/enemy/<enemy_id>.json     2109 个文件 / 89MB
        │  原始结构：bakedAnimDatas.<动画组>.bakedEvents.<动画名>.{eventTime[], events[]}
        ▼
构建期解析（只取 OnAttack 的时间点）
        ▼
akcalc/data/enemy_attack_timing.json                          0.22MB / by_id 1857 条 + meta
        ▼
akcalc/core/enemy_timing.py                                   读取 + 秒↔帧换算（FPS=30）
        ├──► akcalc/ui/monster_codex.py::_timing_card        敌人图鉴「抬手（攻击前摇）」卡
        └──► akcalc/mcp/tool_enemies.py                        MCP 字段与两个工具
```

一个敌人的原始条目长这样（`enemy_10001_trslim`）：

```json
{"bakedAnimDatas": {"Default": {
    "bakedEvents": {
        "Attack_A": {"eventTime": [0.5333], "events": ["OnAttack"]},
        "Attack_B": {"eventTime": [0.5333], "events": ["OnAttack"]}
    },
    "bakedMPDatas": {...}
}}, "hash": "..."}
```

派生表里对应：

```json
"enemy_10001_trslim": {
    "a": 0.5333,                       // 抬手秒数（主口径）
    "anim": "Attack_A",                // 取的是哪个动画
    "all": {"Attack_A": 0.5333, "Attack_B": 0.5333},   // 各分支各自的时间
    "track": "Default", "tracks": 1
}
```

`all` 字段就是「逐敌人、甚至逐动画分支不一致」的证据。设计上没毛病。

### 1.2 真正的缺口：346 只敌人查不到抬手（15.8%）

实测交叉核对（`enemy_database.json` 的 2186 个 id × `enemy_attack_timing.json` 的 1857 条）：

| 项 | 数量 | 占比 |
|---|---|---|
| 命中 | **1840** | 84.2% |
| 缺失 | **346** | 15.8% |
| 缺失中「主条目」 | 242 | |
| 缺失中 `_2` / `_3` 变体 | 104 | |

随机翻缺失样例：

```
enemy_10002_trtrsl     浆果虫
enemy_10009_sggem      结晶
enemy_10015_sgbird     “滑翔的玩具”
enemy_10021_vtcar      货运轨道车
enemy_10028_vtswd      未装配刀片
enemy_10035_cnvdnc     热烈舞团独舞者
enemy_10037_cnvpcar    节日零食车
enemy_10040_cnvbln     节日气球
enemy_10063_cjdoor     湮没之口
```

**这里必须区分两种「缺失」，不能混为一谈**：

1. **真没有攻击动画**（箱体、载具、装饰物、纯机制单位）—— 这类没有抬手是正确结果，图鉴应写「该单位没有攻击行为」，而不是「未收录」。
2. **有动画但解析器没认出来** —— 这是 bug，需要补。

我已验证 `enemy_10002_trtrsl`（浆果虫）的 bake 文件**确实存在**（75,281 字节），但其中 `bakedEvents` 里没有 `OnAttack`。这说明它属于第 1 类，不是解析漏了。剩下 345 只需要逐类抽样确认，**不能一次性归因**。

同时 `meta` 里有两处自相矛盾的数字，说明统计口径没对齐：

| 字段 | 值 | 问题 |
|---|---|---|
| `coverage.covered` | 1868 | 比 `by_id` 实际条目 1857 多 11 |
| `with_timing` | 1857 | 与 `by_id` 条目数一致 |
| `files` | 2109 | 源文件数 |
| `no_attack` | 252 | 2109 − 1857 = 252，这个对得上 |

`coverage.covered = 1868` 与 `with_timing = 1857` 冲突，二者必有一个口径错误。**这是需要修的账**。

### 1.3 `stats()` 有 bug：`covered` 恒为 `None`

实测：

```
$ py -c "from akcalc.core import enemy_timing as ET; print(ET.stats()['covered'])"
None
```

原因在 `enemy_timing.py:256-277`：`stats()` 做的是 `out = dict(m)`，把 `meta` 的**顶层**键摊平；但 `meta` 里覆盖率是**嵌套**的：

```json
"meta": {
    "coverage": {"covered": 1868, "enemy_ids": 2186},
    "with_timing": 1857, ...
}
```

`dict(m)` 只拿到 `coverage` 这个**子字典**，没有 `covered` 这个键，所以 `out["covered"]` 取不到 → `None`。
设置页 / MCP 若按 `stats()["covered"]` 展示覆盖率，会显示空白或 `None`。

## 二、我方干员抬手：数据在 `bakemuzzledata`，且**完全没接**

### 2.1 干员 bake 确实存在，目录和敌人平行

```
zh_CN/gamedata/bakemuzzledata/
├── enemy/       2109 个文件（已接入）
└── character/   每个角色至少一个 <charKey>_defaultskin.json（完全没接入）
```

命名规律（我实际拉取目录清单核对过）：

| 情形 | 文件名 | 例子 |
|---|---|---|
| 默认皮肤 | `<charKey>_defaultskin.json` | `char_009_12fce_defaultskin.json` |
| 其他皮肤 | `<charKey>_<charKey>_<皮肤名>#<序号>.json` | `char_002_amiya_char_002_amiya_epoque#4.json` |

注意皮肤是**每个皮肤一份**，不是每个干员一份。所以做表时必须先按 `charKey` 归并、优先取 `_defaultskin.json`。

### 2.2 结构和敌人**几乎一样**，只多了 `Front` / `Back` 两个动画组

实际拉取并解码 `char_263_skadi_defaultskin.json`（48,609 字节）得到：

```
顶层键: ['bakedAnimDatas', 'hash']

[动画组 Front]
   bakedEvents 动画: ['Attack', 'Start']
      Attack       eventTime=[0.866667]   events=['OnAttack']
      Start        eventTime=[0.133333]   events=['OnStart']
   bakedMPDatas 动画: Idle / Attack / Attack_Begin / Attack_End / Die / Start / Default

[动画组 Back]
   bakedEvents: 同上（Attack 0.866667 → OnAttack）
   bakedMPDatas: 同上（少一个 Attack_End）
```

要点：

1. **抬手取 `Attack` 的 `OnAttack` 时间点**，与敌人同一口径。斯卡蒂 = 0.866667 s = **26 帧**。
2. 干员有 `Front` / `Back` 两个组（正面/背面朝向）。同一角色两组数值通常一致，但**不能假设一致**，要分别记录并做一致性检查。
3. 干员还有 `Start`（`OnStart`）事件 —— 这是登场动画的时间点，敌人侧没有。它对「部署瞬间多久开始生效」有用，可以顺手采集。
4. 干员的 `bakedMPDatas` 里**没有** `Skill` / `Skill_Loop` 这类动画名。也就是说：**干员技能施放时的动画不在 bake 数据里**，bake 只覆盖 Idle / Attack / Start / Die 这些通用动作。这一点决定了后面 §三 的可行边界。

### 2.3 干员抬手值同样逐个体不同（预期结论，尚未全量实测）

已确认的样本：12F = 0.3667 s（11 帧）、斯卡蒂 = 0.866667 s（26 帧）。
按敌人侧的经验，干员侧大概率也是几十种取值散布在 0.2–1.5 s，**绝不能用一个全局值**。

> **待办**：全量拉取 `bakemuzzledata/character/` 并统计，得到「多少个 charKey / 多少种抬手值 / 分布」。
> 目录太大（jsDelivr 报 `Package size exceeded the configured limit of 50 MB`），需要分页拉 GitHub tree API 或直接 clone。这一步**要先做，再定表结构**。

### 2.4 现在为什么完全看不到

三个原因叠加：

1. 没有 `operator_attack_timing.json` 这类派生表；
2. `akcalc/core/enemy_timing.py` 只服务敌人，接口签名是 `enemy_id`，无法复用给干员；
3. 干员图鉴（`akcalc/ui/data_index.py::OperatorIndexView`，行 677–1549）的卡片只有：面板数值 / 精英化 / 潜能 / 信赖 / 天赋 / 技能 / 模组，**没有任何时间轴类卡片**。

## 四、技能 → 代码 → 动画：把「指定文件」和「解包代码」接起来

### 4.1 技能对应的「代码」= `prefabId`

这是本次调查最关键的一条。`skill_table_full.json` 里每个技能的**每个等级**都带一个 `prefabId`：

```json
"skchr_skadi2_3": {
  "levels": [ { ..., "prefabId": "skchr_skadi2_3", "blackboard": [...] }, ... ]
}
```

实测统计：

| 项 | 数值 |
|---|---|
| 技能总数 | 1829（`skcom_*` 28 / `skchr_*` 908 / `sktok_*` 893） |
| **有 `prefabId`** | **1787（97.7%）** |
| 无 `prefabId` | 42 |
| distinct `prefabId` | **1503** |
| 其中**被且仅被一个技能使用** | **1485** |

也就是说：**1485 个技能，`prefabId` 与 `skillId` 是 1:1 独占的** —— `prefabId` 就是该技能的实现类名，是「技能 → 代码」的**唯一官方锚点**。

复用的情况也有，且很有信息量：

```
sktok_common_acarm      192 个技能共用   ← 召唤物通用护甲，不是独立技能
sktok_empty              63
sktok_multi_upgrade       5
skcom_charge_cost         3            ← 冲锋号令 α/β/γ
skcom_atk_up              3            ← 攻击力强化 α/β/γ
skcom_def_up              3
```

**结论**：`prefabId` 可以做三级映射：
1. `skillId` → `prefabId`（一对一，97.7% 可解析）；
2. `prefabId` → 语义族（`skcom_*` 通用强化 / `sktok_*` 召唤物 / `skchr_*` 干员专属）；
3. `skchr_*` 且独占 → 直接定位到「这个技能的实现」。

### 4.2 「调用了什么动画」：能拿到哪一层，拿不到哪一层

必须把边界讲清楚，否则会做出一个看起来很全、实际是猜的表。

| 层次 | 数据在哪 | 能不能拿到 |
|---|---|---|
| **普攻动画的 OnAttack 时刻** | `bakemuzzledata/{enemy,character}/*.json` | ✅ 已能拿（敌人已做，干员待做） |
| 普攻动画名（`Attack` / `Attack_A` / `Attack_B`） | 同上 | ✅ 能 |
| 登场动画时刻（`OnStart`） | 同上（仅 character） | ✅ 能 |
| **技能施放时的动画名** | ✅ 在 bake 里（`bakedMPDatas` 的 `Skill*` 键） | ✅ **能拿到**（见下方更正） |
| 技能动画的时长 / 关键帧 | bake 的 `trsData` 数组里有，但体积巨大 | ⚠️ 技术上能，实际不划算 |
| 技能逻辑的源码（Lua / C#） | ✗ 官方仓库只有 UI 层 `[uc]lua/feature/*` | ❌ **拿不到** |

我把 `[uc]lua` 的完整 tree 递归拉下来逐层看过：
- `base/battle/` → `BattleAbilityBehaviourBase.lua`(543B) / `BattleActionBase.lua`(305B) / `BattleMgr.lua`(2.1KB) —— 都是**框架基类**，几百字节，没有具体干员逻辑。
- `battle/abilitybehaviours/` → 只有 `TestAbilityBehaviour.lua`(309B)。
- `battle/actions/` → 只有 `TestAction.lua`(178B)。

**这说明**：干员技能的**逻辑实现**（`skchr_*` 那些 prefab 行为）是**编译进引擎的**，解包里没有源码。

> **⚠️ 更正（v1.1）**：本文初稿写过「解包里没有技能动画」，**该结论错误**，仅基于斯卡蒂 / 12F 两个样本，样本过窄。
>
> 实测 `char_002_amiya_defaultskin.json` 的 `Front` 组：
> ```
> bakedMPDatas 含: Skill_Begin / Skill / Skill_End / Skill_2_Begin / Skill_2 / Skill_2_End
> bakedEvents 含:  Attack  → OnAttack @ 0.633333
>                  Start   → OnStart  @ 0.133333
>                  Skill   → OnAttack @ 0.0
>                  Skill_2 → OnAttack @ 0.0
> ```
> 敌人侧同样存在：1857 条里 **59 只**的主取动画是 `Skill` 系列，全量动画词表 104 种中 **32 种含 `Skill`**。
>
> 所以**技能动画名和它的 `OnAttack` 时刻是能拿到的**；拿不到的只有「技能逻辑怎么判定」。
> 另外注意：阿米娅的 `Skill` / `Skill_2` 抬手确实是 **0.0**（瞬发无前摇），这是真实值，不是缺数据。

### 4.3 那「怎么判定」能答到什么程度

「判定」拆成三类，可行性完全不同：

| 判定类型 | 数据来源 | 可行性 |
|---|---|---|
| **SP 回转判定**（何时能开、开多久、几秒一轮） | `spData`（`spType`/`spCost`/`initSp`/`increment`）+ `durationType` + `duration` | ✅ **完全可算**，`statemachines` 已做 525 条 |
| **数值判定**（加攻多少、打几下、倍率多少） | `blackboard` + `codex_fields.json` 的 200 个 token 释义 | ✅ **可算**（token 释义已有） |
| **行为判定**（打谁、怎么选目标、是否穿透、召唤物怎么走） | ✗ 无源码、无表 | ❌ **不可算**，只能人工写描述 |

第三类正是「详细机制」里最难的部分。目前 `statemachines` 的 `impl` / `pitfall` 字段是靠**人工归纳**填的，不是从代码里抽的 —— 这也是为什么只有 525 条：人工写不动 1829 条。

## 五、修正方案：分四块，按可行性排序

### 5.1 改动总览

| 编号 | 内容 | 数据 | 代码 | 风险 |
|---|---|---|---|---|
| **P1** | 修 `stats()['covered']` 恒 None + `meta` 自相矛盾 | 改 meta | 1 行 | 极低 |
| **P2** | 敌人抬手补 346 只的**归因**（真无攻击 vs 解析漏） | 新增归因表 | 解析器小改 | 低 |
| **P3** | 干员抬手：新建 `operator_attack_timing.json` + 图鉴卡片 | 新表 | 新模块 + 新卡 | 中 |
| **P4** | 技能机制：`prefabId` 三级映射 + 覆盖率从 28.7% 往上推 | 扩 statemachines | 图鉴加字段 | 中 |

### 5.2 P1：先把账修对（半小时的活）

**问题**：`stats()['covered']` 返回 `None`；`meta.coverage.covered=1868` 与 `with_timing=1857` 冲突。

**改法**：
1. `enemy_timing.py::stats()` 里把嵌套的 `coverage` 摊平，或显式读 `m.get("coverage", {}).get("covered")`；
2. 重新生成 `meta`，让 `coverage.covered` 与 `with_timing` **同口径**（建议都用「实际写入 `by_id` 的条目数」= 1857）；
3. 补 `no_attack` 的**名单**，而不只是数字 —— 这样图鉴才能区分「真没攻击」和「解析漏了」。

**验收**：`ET.stats()["covered"] == len(ET.load())`，且 `meta.coverage.covered == meta.with_timing`。

### 5.3 P2：346 只缺失的归因（这是「图鉴没有数据」的真正修法）

不要直接去补数据，先**归因**。建议解析时对每个敌人产出三态，而不是二态：

```json
"enemy_10002_trtrsl": {"state": "NO_ATTACK",   "reason": "bakedEvents 无 OnAttack 事件"},
"enemy_1021_bslime":  {"state": "OK",          "a": 0.4667, "anim": "Attack"},
"enemy_XXXX_yyyy":    {"state": "PARSE_FAIL",  "reason": "文件存在但结构异常"}
```

图鉴卡片按三态显示不同文案：

| state | 卡片显示 |
|---|---|
| `OK` | 抬手 14 帧（0.467 秒）@30fps 14 帧 ｜ @60fps 28 帧 ｜ @120fps 56 帧 |
| `NO_ATTACK` | **该单位没有攻击行为**（箱体 / 载具 / 装饰 / 纯机制） |
| `PARSE_FAIL` | **数据解析失败**（附原因，可上报） |

现在 `_timing_card` 把前两种都写成「未收录」，理由是「多为装置 / 召唤物 / 剧情单位」—— **用词糊了**，用户看到「未收录」会以为是自己没装数据。这是要改的文案。

**工作量**：解析器加三态判定 + 图鉴文案分支，约 1 个文件、几十行。

### 5.4 P3：干员抬手（本方案的主体新增）

#### 5.4.1 数据表设计

新建 `akcalc/data/operator_attack_timing.json`，**沿用敌人的 schema**，便于复用换算逻辑：

```json
{
  "meta": {
    "source": "zh_CN/gamedata/bakemuzzledata/character/*.json",
    "repo": "Kengxxiao/ArknightsGameData",
    "unit": "second", "fps": 30,
    "field_a": "抬手秒数（Attack 动画里 OnAttack 的时间点）",
    "field_start": "登场秒数（Start 动画里 OnStart 的时间点）",
    "skins_seen": 0, "char_keys": 0,
    "with_timing": 0, "no_attack": 0
  },
  "by_char": {
    "char_263_skadi": {
      "a": 0.866667,
      "anim": "Attack",
      "start": 0.133333,
      "skin": "defaultskin",
      "front_back_consistent": true,
      "all": {"Front": 0.866667, "Back": 0.866667}
    }
  }
}
```

设计要点：

1. 键用 **`charKey`（`char_263_skadi`）**，不是中文名 —— 与 `operators.json` 的 `char_id` 对齐；
2. 皮肤按 `charKey` 归并，**优先 `_defaultskin.json`**，其余皮肤只做一致性校验；
3. 保留 `Front` / `Back` 两组原值在 `all` 里，`front_back_consistent` 标记是否一致（不一致的要人工看，可能是解包噪声）；
4. 顺手采 `start`（`OnStart`）—— 它回答「部署后多久进入可攻击状态」，对沙盘开场很有用，边际成本几乎为零。

#### 5.4.2 模块复用策略（关键决策点）

**方案 A（推荐）：把 `enemy_timing.py` 抽成通用 `timing.py`**

```
akcalc/core/timing.py          ← 通用：load / sec_to_frames / frames_to_sec / convert / at_fps_table
akcalc/core/enemy_timing.py    ← 保留，内部转调 timing，签名不变（向后兼容）
akcalc/core/operator_timing.py ← 新增，同样转调 timing
```

好处：帧换算、30/60/120 三档、`convert()` 的语义**只有一份实现**，不会出现「敌人 14 帧 / 干员 15 帧」这种两边算法不一致的事故。
代价：要动一个已经在跑的文件（但只是抽函数，签名不变）。

**方案 B：直接复制一份 `operator_timing.py`**

快，但帧换算逻辑会出现两份，将来改 FPS 或改取整规则必然漏一边。

> **这条需要你拍板**：要不要为了「零风险」容忍两份换算逻辑？

#### 5.4.3 干员图鉴的卡片

`data_index.py::OperatorIndexView`（行 677–1549）需要新增一张卡。放在**「面板数值」之后、「天赋」之前**最合理，因为抬手是「基础属性」不是「技能效果」。

卡片内容建议：

```
┌─ 攻击时序 ────────────────────────────────
│ 抬手 26 帧（0.867 秒）
│ @30fps 26 帧 ｜ @60fps 52 帧 ｜ @120fps 104 帧
│ 登场 4 帧（0.133 秒）
│ 取自动画：Attack（皮肤 defaultskin，正/背面一致）
└──────────────────────────────────────────
```

同时 `damage_panel.py`（伤害计算面板）里如果用到攻击间隔，应该把抬手也接进去 —— 因为「攻击间隔 1.5 秒」和「抬手 0.87 秒」是两回事，DPS 计算时段如果按间隔算会高估。**这一条属于后续，不在本次范围**。

### 5.5 P4：技能机制补全（最重，要分期）

#### 5.5.1 立刻能做的：`prefabId` 进图鉴

现在干员技能卡（`data_index.py:1146 _render_skills`）显示：技能名 / 类型 / 各级描述 / 数值 / 「查看原代码」按钮。
**没有 `prefabId`**。加一行即可：

```
■ 潮涌，潮枯    自动回复  手动触发
  实现：skchr_skadi2_3        ← 新增
  查看原代码 ▾ [专三]
  1  攻击力+20% ...
```

这一行的价值：**外部 AI 拿到 `prefabId` 就能判断这是通用技能还是专属技能**，也才能去对照 `statemachines` 里的条目。

#### 5.5.2 中期：`statemachines` 从 525 往上推

现在 525/1829 = 28.7%。提升路径按性价比排序：

| 阶段 | 做法 | 可覆盖 | 成本 |
|---|---|---|---|
| **① 通用技能批量化** | `skcom_*` 只有 28 个，但被大量技能复用（`sktok_common_acarm` 一个就 192 个技能）。按 `prefabId` 族写模板，一次覆盖一大片 | +数百 | 低 |
| **② 纯数值技能** | 只需 `blackboard` 就能完整描述（加攻/加防/加攻速）的技能，`impl` 可以自动生成 | +数百 | 低 |
| **③ 状态机自动推导** | 从 `spData` + `durationType` + `duration` **纯计算**出 states/metrics，不用人工写 | 覆盖全部有 `spData` 的 | 中 |
| **④ 行为类人工归纳** | 召唤 / 位移 / 传送 / 特殊判定，必须人工 | 剩余长尾 | 高 |

其中 ③ 是最值得做的：`spType` / `spCost` / `initSp` / `increment` / `duration` 全是结构化数字，**状态机可以完全自动生成**，`statemachines` 里 525 条手写的 `states` 和 `metrics` 本质就是这个计算的手工版。

> 但注意：`statemachines` 现有的 `impl` / `pitfall` 是**人工洞察**（比如「spType 为整数 8 时表示不回复，用 == "..." 判断会漏」），自动生成替代不了这部分。建议**自动生成 `states`/`metrics`，保留人工 `pitfall`**。

#### 5.5.3 技能动画：能做「时刻」，不做「关键帧」

见 §4.2 更正。分两件事：

| 想要什么 | 能否做 | 说明 |
|---|---|---|
| **技能抬手时刻**（`Skill*` 的 `OnAttack`） | ✅ **应当做**，且本轮就做 | 已在「工作指令_干员抬手接入.md」任务 B 中 |
| 技能动画的逐帧姿态（`trsData`） | ⚠️ 能读但**不做** | 每帧一个浮点数组，单文件几十到几百 KB，对算伤害/回转没有增量价值 |
| 技能动画的**时长** | ⚠️ 可做，但需谨慎 | 要数 `frameCount` 累加，且 `Skill_Loop` 是循环体、`Skill_End` 是收招，边界容易数错，本轮不碰 |

**本轮不做**：`trsData`、动画时长、关键帧。
**本轮要做**：技能抬手的**时刻**（一个数字），因为它直接影响「技能开出去多久才开始产生效果」，这正是沙盘要算的东西。

**技能逻辑判定**仍然不可得（无源码），只能靠 `blackboard` + 人工归纳。

## 七、一句话总结

- **敌人抬手**：数据是逐个体的（62 种取值），图鉴卡片已写好但在未提交改动里，MCP 也已接入。
  真正的坑是 **346 只查不到（15.8%）被笼统写成「未收录」**，以及 `stats()['covered']` 恒 `None`。
- **干员抬手**：数据在 `bakemuzzledata/character/`，**结构和敌人几乎一样**（多 `Front`/`Back` 和 `OnStart`），
  但**一行代码都没接**，需要新建派生表 + 图鉴卡片。
- **技能代码**：`prefabId` 是「技能 → 代码」的唯一官方锚点，**1787/1829 有值，1485 个是 1:1 独占**。
- **技能动画**：解包**有**（`bakedMPDatas` 的 `Skill*` + `bakedEvents` 的 `OnAttack`；阿米娅 `Skill`/`Skill_2` 抬手均为 0.0）。
  **抬手的时刻能拿到**，逐帧姿态和技能逻辑拿不到 —— 这条边界要写死。
- **详细机制**：`codex_fields.json` 的 `statemachines` 是那份「指定文件」，但只覆盖 **28.7%**，且**零动画维度**；
  `states`/`metrics` 可以从 `spData` 自动生成，`impl`/`pitfall` 只能人工。
