## 一 需求拆解、边界与结论

### 1.1 需求原文与我做的拆解

### 1.2 边界：明确不做（写下来是为了以后不回退）

* 不做**攻击动画**（骨骼、序列帧）。只保留「抬手时刻」这一个标量。
* 沙盘**不判死、不扣血**。伤害公式本身作为独立接口给出去（§九 / §十），
  但不回灌进沙盘时间轴 —— 因为伤害结算依赖「谁在打谁」，而沙盘不模拟
  目标选择；强行接上会得到一个看起来精确、实际全靠猜的数。
* 不做**技能效果**（增幅、位移、召唤、减速的技能来源）。只做
  「SP 攒满 → 技能开始 → 技能结束」这一段回转。
* 不做联机、录像、重写寻路。

### 1.3 一句话结论

> 寻路是对的（解包驱动、2923/2923 路线可达）；
> **战斗层是「粗轴示意」，不是「模拟」**。
> 缺的不是算法，是**七处数据/模型没接线**：阻挡几何、攻击间隔、敌人移速、
> 攻击范围、部署费用经济、生命值、棋子头像。
>
> 其中**阻挡几何与伤害公式都是「已经写好、数值正确、但零调用者」**——
> 这类问题只需接线，不需要重新设计。

现有 `core/blocking.py` 已经把游戏的阻挡几何**完整实现**（平方距离、
0.707 半径、0.5 偏移、绕行力），但 **`core/` 和 `ui/` 里没有任何一处调用它**。
沙盘实际用的是另一套「整数格取整」的简化。这是本次最大的单点收益。

## 四 阻挡（B1）

### 4.1 已有几何模型：完整、经数值验证、但零调用

`core/blocking.py` 已实现游戏的阻挡几何，常量与 `core/constants.py` 同源：

```python
BLOCK_RADIUS_GROUND       = 0.70709997    # 地面阻挡半径（格）
BLOCK_RADIUS_GROUND_SQ    = 0.49999037    # 其平方，比较时省一次开方
BLOCK_RADIUS_FLY_COEF     = 0.8944        # 对空系数（乘在半径上）
BLOCK_RADIUS_FLY_SQ_COEF  = 0.79995137
OPERATOR_COLLISION_RADIUS = 0.25
BLOCK_OFFSET_RADIUS       = 0.5           # 被挡敌人被推到的圆半径
CENTER_EPSILON            = 0.00001
SECONDARY_OFFSET_CHECK_RADIUS = 0.1
SECONDARY_OFFSET_MAX      = 0.2
AVOID_FORCE_MIN           = 0.5
AVOID_ACCEL_COEF          = 8.0
```

**判定口径**：取「干员位置 → 敌人位置」的中点，算它到干员的距离平方，
与半径平方比较。本次现场复算：

```
is_blocked((0,0), (0.50,0))  -> True           # 恰在半径内
is_blocked((0,0), (0.75,0))  -> False          # 已出半径
apply_block_offset((0,0), (0.40,0)) -> final=(0.5,0.0), distance=0.100
apply_block_offset((0,0), (0.75,0)) -> final=(0.5,0.0), distance=0.250
```

即敌人走到**距干员 0.5 格**时被拦下，并被推回半径 0.5 的圆边界上。

### 4.2 现在实际用的是「整数格取整」

`core/sandbox.py:899 blocked_by()` 把浮点坐标四舍五入成格子再比格子号；
`_blocking_plan` 用 `_route_cell_arrivals` 的**格中心到达时刻**。

两套口径的差别：真实模型在「距干员 0.5 格」拦下，取整模型在
「进入该格中心 ±0.5 格」才算。**最大偏差 0.5 格**。
按 `actual_move_speed(0.5, 0.5) = 0.25 格/秒` 折算，就是 **2 秒**；
按 `1.0` 速度折算 **1 秒**。足以让「这波卡不卡得住」的结论翻转。

### 4.3 现状里的四个真 bug（读代码确认，不是推测）

读 `sandbox.py:483-562`（`_blocking_plan`）与 `:354-405`（`pose_at`）：

**bug A — 没拿到票的敌人整只漏到全场。**
第 517-543 行的循环：对每只敌人，沿路线找**第一个**站着近战干员的格子，
登记后 `break`。若该格子容量已满（第 549 行 `it["blocked"] = i < cap`），
这只敌人在 `best_by_key` 里根本没有条目，于是**按无阻挡轨迹走完全程**——
它会径直穿过路线上**第二枚干员**的格子。

```
if dep is None:
    continue
...
cands.setdefault((cell, dep.uid), []).append({...})
break            # ← 只看第一个干员格
```

正确行为：第一格满票 → 继续看下一格，直到走完路线。

**bug B — 容量永不复原，长轴必然退化。**
第 534-535 行：`release = dep.retreat_time or inf`。
也就是说「腾位置」只有**干员撤退**一个途径。沙盘刻意不判死，
于是被挡的敌人永远占着票：`cap=1` 的干员挡下第一只之后，
**后面所有敌人全部穿过去**。

这与游戏反差极大（游戏里挡下的怪会死，下一只接着被挡）。
这也是为什么现在的沙盘在长轴上「看起来挡不住」——不是算错，
是**没有腾位置的事件源**。

修法：引入 `Sandbox.kill_event(ev)`（只影响阻挡容量与 pose，
不影响路线分析），`release` 取值优先级
`kill_event_time → dep.retreat_time → inf`。UI 上右键敌人 →「判定击杀」。
这是**最小代价**的做法：不引入伤害结算，却让阻挡语义正确。

**bug C — 被挡的敌人全部钉在格中心，互相重合。**
`pose_at` 第 392 行直接 `return (float(cell[0]), float(cell[1]))`。
三只怪挡在同一个盾上时，画面上完全重叠成一个点。
游戏里它们会分散在半径 0.5 的圆上。

修法：改用 `BL.apply_block_offset(operator_pos, enemy_pos, existing_blockers=...)`，
多只时走 `secondary_mode="total"` 避免两点重合。

**bug D — 对空阻挡靠 `can_block_fly` 手点，且默认 False。**
解包数据里**确实没有**「干员能否挡空中单位」这个字段
（`enemy.motion == "FLY"` 是敌人侧的）。所以只能让用户点，
这一点保持不变，但要在文档里写清「这是我们补的，不是游戏数据」。

### 4.4 改法（四个 bug 对应四处）

**改法 1 · 阻挡判定换模型**
`sandbox.py:899`：

```python
def blocked_by(self, row, col, enemy_flying=False, seconds=None):
    for pc in self.blockers(seconds):
        if enemy_flying and not pc.can_block_fly:
            continue
        if BL.is_blocked((pc.row, pc.col), (row, col), flying=enemy_flying):
            return pc
    return None
```

**改法 2 · 落点分散**
新增 `Sandbox.block_anchor(event, seconds)`，命中后求
`BL.apply_block_offset(...)` 的 `final`，`pose_at` 用它代替格中心。

**改法 3 · 票券可回收 + 不整只漏过**
重写 `_blocking_plan` 的内层循环（伪代码）：

```
for ev in live_events:
    if kicked(ev): continue
    held = {}                      # (cell,uid) -> 已占票数（按时间推演）
    for (cell, arr_eff) in route_cell_arrivals(ra):
        arr_wall = t_spawn + wall_elapsed(ev, ra, arr_eff)
        dep = 该格上 arr_wall 时刻在场的近战干员（含对空过滤）
        if dep is None: continue
        if held.get((cell, dep.uid), 0) >= dep.block_count:
            continue               # ← 满票：继续看下一格（原为 break 整只丢弃）
        held[(cell, dep.uid)] = held.get((cell, dep.uid), 0) + 1
        plan[key] = (cell, arr_wall, release_of(dep, ev), arr_eff, True)
        break                      # 被挡下，不再往后走
```

`release_of(dep, ev)`：`kill_event_time(ev)` → `dep.retreat_time` → `inf`。

**改法 4 · 阻挡容量上限的来源不变**
容量仍取 `OperatorPiece.block_count`（源 `phases[e][lv].block`）。
实测 463 名干员（取最高精英化最高等级）：

| block | 人数 |
|---|---|
| 1 | 311 |
| 2 | 113 |
| 3 | 32 |
| 0 | 7 |

**不能**拿 `enemy.blockCnt` 当容量——实测 2450 行里 2449 行是 `0`。

### 4.5 阻挡与寻路的边界（铁律，改的时候不许越线）

**干员永远不进 `blocked`。** `recompute()` 现在只传
`blocked=self.boxes_only()`，必须保持。理由不是省事，是游戏行为：
敌人不会因为前面站了人而提前绕路，它按原路线走过来、撞上才停。
把干员塞进 `blocked` 会画出「敌人绕开干员」的假路线——
在 `main_16-11` 上肉眼可见是错的。

**推论**：`arrival_time(ev)` 返回的是**无阻挡**到达时刻。
所有被挡信息只从 `_blocking_plan` / `pose_at` 取。现有代码这一点是对的，
改阻挡时别破坏。回归里要锁死「改阻挡不改变任何关卡可达性」。

### 4.6 验收

`test_full_regression.py` 新增：

1. 干员放路线正中 → 敌人停在距干员中心 `0.5` 格（容差 0.02）。
2. 阻挡数 1，两只敌人同帧到达 → 第二只不停，且**继续走到下一枚干员处被挡**（验 bug A 修复）。
3. 干员撤退 → 第二只立刻前进，且从被挡处接着走，不跳回起点。
4. 三只敌人被同一干员挡住 → 三点互不重合，且都在半径 0.5 圆上（验 bug C）。
5. `cap=1` + 长轴 60 秒 + 手动判定击杀 → 后续敌人能被接着挡（验 bug B）。
6. 不变量：全部 2629 个关卡的路线可达性数字不变（2923/2923）。

## 五 部署 / 撤退 / 部署费用 / 生命值（B2）

### 5.1 为什么 DP 是必需品而不是附加项

明日方舟的战术节奏由部署费用驱动：第一个干员什么时候能下、
第二波前够不够攒出费、撤退反费能不能撑起再部署。
现在沙盘是「不花钱随便放」，等于把 RTS 玩成了沙盒编辑器。
用户要「完全模拟运行情况」，DP 是主循环，绕不过去。

### 5.2 数据（解包 `options`，2629 个关卡全扫）

| 字段 | 含义 | 实测分布 |

### 5.3 费用公式（PRTS「部署费用」，现场 HTTP 200 核对）

```
部署费用（属性） = (初始部署费用 + 基础费用增减) × 费用倍率 + 实时费用增减
```

* **初始部署费用**：面板费用，已含精英化 / 潜能 / 模组。取
  `operators.json` 的 `phases[e][lv].cost`。
* **基础费用增减**：加算（换费、自我减费）。
* **费用倍率**：默认 1.0，主要由再部署惩罚提供。
* **实时费用增减**：最终加算（多数减费效果）。

**再部署惩罚**：每次退场（**撤退与击倒都算**）累积一层，**上限 2 层**，
每层给自己的待部署费用提供 **0.5 倍率**：

```
0 层 → ×1.000    1 层 → ×0.500    2 层 → ×0.250（封顶）
```

**费用回复**：每 `costIncreaseTime` 秒 +1；当前费用 == `maxCost` 时
冷却条显示 MAX，**停止回复、溢出丢弃**。

**下限与负费**：通常 0。可露希尔后可低于 0，**负费期间回复速度减半**
（乘算），其余照常（可透支部署）。沙盘做开关 `allow_negative_dp`（默认关）。

**撤退反费**：返还本次**实际消耗**（不是面板费用）。
所以 `Deployment.cost` 存部署那刻算出的属性费用即可，`refund(dep.cost)`
天然正确，不必重算。子规则「可返费 / 无视返还上限」用一个
`refund_ratio`（默认 1.0）覆盖。

**费用不足不能拖选**：当前费用 < 该干员费用时**既不能选也放不下**。
必须体现在 UI（`_fill_picker` 置灰 + 提示），否则用户当 bug 报。

### 5.4 新增 `core/dp.py`（约 200 行，headless）

```python
class DPEconomy:
    initial: float            # options.initialCost
    cap: float                # options.maxCost
    interval: float           # options.costIncreaseTime；>=1000 → 停回
    regen_disabled: bool
    allow_negative: bool = False
    refund_ratio: float = 1.0
    current: float
    _last_settle: float = 0.0

    def settle(self, t: float) -> float      # 结掉 [_last_settle, t] 的回复
    def can_afford(self, cost: float) -> bool
    def spend(self, cost: float) -> bool     # 不足则 False 且不改状态
    def refund(self, cost: float) -> float
    def curve(self, t0, t1, step=1.0) -> list
```

**关键约束：`settle()` 必须支持任意跳时，不能像实时游戏那样「往前走一格」。**
沙盘时间轴可以被游标拖动、被粗轴点击、被撤销/重做，所以 DP 也要
闭式求解。难点是「负费期间半速」会让区间内穿越零点，需要分段积分：

```python
def settle(self, t):
    if self.regen_disabled:
        self._last_settle = t
        return self.current
    t0, cur = self._last_settle, self.current
    while t0 < t - 1e-12:
        if cur < 0 and not self.allow_negative:
            cur = 0.0
        if cur < 0:
            rate = 0.5 / self.interval          # 负费：半速
            need = -cur
            dt_need = need / rate
            if t0 + dt_need <= t:
                t0 += dt_need; cur = 0.0
            else:
                cur += rate * (t - t0); t0 = t; break
        else:
            rate = 1.0 / self.interval
            room = self.cap - cur
            if room <= 0:                        # 已 MAX，冷却暂停
                t0 = t; break
            dt_need = room / rate
            if t0 + dt_need <= t:
                t0 += dt_need; cur = self.cap
            else:
                cur += rate * (t - t0); t0 = t; break
    self.current, self._last_settle = cur, t
    return cur
```

> `settle` 只允许**向后**跳。撤销/重做走整体快照还原——
> `Sandbox` 已有 `_undo_stack` / `_redo_stack`，把 `dp` 一起塞进快照。

### 5.5 部署 / 撤退判定链路

```python
def deploy_check(self, row, col, is_ranged, cost=0.0, now=None):
    # 1) 地形  2) 占格  3) 不堵蓝门      —— 原有
    alive = len(self.operators_alive(now))

```

### 5.7 敌人移动速度（看着小，影响最大）

`recompute()` 目前所有路线共用 `analyze_all(gm, blocked=...)`，
`move_speed` 默认 1.0。真实数据里 **1798 个 id（84.3%，分母 2134 = 排除不可移动）** ≠1.0。

实测误差（`a001_06`）：

| 路线 | 敌人 | 真实速度 | 沙盘（1.0） | 真实 |
|---|---|---|---|---|
| R1 | `enemy_1001_bigbo` | 0.5 | 75.8 s | **129.6 s** |
| R12 | `enemy_1000_gopro` | 1.9 | 27.31 s | **14.38 s** |

**但不能每只敌人算一遍**——实测 `analyze_all` 耗时：

| 关卡 | 路线数 | `analyze_all` 耗时 |
|---|---|---|
| `a001_06` | 44 | 8.9 ms |
| `main_04-04` | 26 | 2.0 ms |
| 中位关卡 | 26 | ≈2–5 ms |
| **`act1multi_football`（最坏）** | **1361** | **288 ms** |

> 冷启动首次调用会明显更慢（含依赖导入），上表为热态复测值；
> 若按首次冷测口径，最坏关卡可见到 600 ms 以上。

**方案：按 `(route_index, move_speed)` 缓存。**

```python
def recompute(self):
    blocked = self.boxes_only()
    self._speed_cache = {}
    for ev in self.live_events():
        sp = self.enemy_move_speed(ev)                 # EnemyLibrary
        k = (ev.route_index, round(sp, 4))
        if k not in self._speed_cache:
            ra = self._route_by_index(ev.route_index)
            self._speed_cache[k] = RT.analyze_route(
                self.game_map, ra, move_speed=sp,
                blocked=blocked, allow_diagonal=True)
```

**这里必须纠正一个直觉错误**：去重的收益**远没有想象中大**。
实测 `a001_06` 共 97 个出怪、只有 **4 种** moveSpeed
（1.9×65、1.2×18、0.9×13、0.5×1），但 `(route, speed)` 组合有
**43 组 / 44 条路线** —— 因为**一条路线通常只走一个速度档位**。
所以去重后的实际计算量≈「每条路线各算一次」。

好消息是那正是 `analyze_all` 本身的工作量。三关实测（本机）：

| 关卡 | 路线数 | `analyze_all` | 逐 `(route,speed)` | 速度档数 |
|---|---|---|---|---|
| `a001_06` | 44 | 8.9 ms | **7.4 ms** | 4 |
| `main_04-04` | 26 | 2.0 ms | **2.1 ms** | 5 |
| `act1multi_football` | 1361 | 288 ms | **296 ms** | 10 |

结论：**逐敌人精确移速不会带来数量级膨胀**（最坏 1361 路线 ≈ 0.3 秒，
且只在拖动粗轴时触发，不在每帧的 `pose_at` 路径上）。
之前的「44 条路线只用到 4 种速度所以能砍到 4 组」是错的——
速度种类少不等于组合少。

`analysis_for(ev)` 改从 `_speed_cache` 取，`arrival_time` / `pose_at` /
`_route_cell_arrivals` 自动跟着对。若性能仍不够，再考虑
「同速度档批量分析」的备选优化，而不是牺牲精度。

**仍不精确的地方（如实记下）**：`MOVE_SPEED_MIN=0.1` 会把
`moveSpeed=0` 抬成 `0.05` 格/秒（52 个 id 是 0）。这与游戏一致——
罚站型单位靠 `WAIT_*` 检查点实现，不是靠 0 速度，所以不改。

### 6.3 阻回（技能期间停回）与它的两个例外

PRTS「技能」页的权威口径（现场 HTTP 200）：

> 触发技能后**消耗 SP 并进入「阻回」**——技能持续期间**停止**技力回复；
> 技能结束后 SP 从 0 开始。

现存 `SkillSim.cycles()`（`sandbox_track.py:196-235`）**已经正确实现了
阻回的默认情形**：第 226-227 行 `t = active_to; sp = 0.0`，
即技能期间不回 SP、结束后从 0 攒。用 `sp_cost=20, dur=30, iv=1.6`
验算，得 `[(32,32,62), (94,94,120)]` —— 32 攒满、62 结束、再到 94，
正是「阻回」的结果。

**但有两个例外没有建模**（PRTS 原文明确写了）：

1. **攻击回复 / 受击回复的技能，在技能持续期间仍然回 SP。**
   验算对照：同一组参数下，
   * 阻回（现存实现）→ ready 在 `32, 94`
   * 技能期间照常回 → ready 在 `32, 64, 96`
   两者在**第二轮起就分叉**，长轴上会明显少一次技能。

2. **可充能技能（`maxChargeTime > 1`）不进入阻回**，
   它把 SP 上限抬到 `spCost × 次数`，且**技力流失时次数实时降低**。

改法：

```python
def cycles(self, sk, end_time, start=0.0, boost=0.0, recover_in_skill=False):
    ...
    if ready:
        out.append((ready, ready, active_to))
        carry = (active_to - ready) * rate if recover_in_skill else 0.0
        t, sp = active_to, min(sk.sp_cost, carry)   # ← 唯一的差别
```

`recover_in_skill = (recover == SP_ATTACK or recover == SP_DEFENSE)`。

### 6.5 弹药技能（`durationType == "AMMO"`）

### 6.6 光环 / 技力回复加成：取最大，不取和

`sp_boost_of_text()` 只解析两种文本模式（如「技力回复速度 +0.33」），
其余返回 0.0。**且同名光环叠加取 `max` 而不是求和**——
白面鸮 0.33 与陈 0.30 同时在场，结果是 **0.33**，不是 0.63。
只有 `SP_AUTO` 受益于这个加成；`SP_ATTACK` / `SP_DEFENSE` 不受影响。
现存实现这一点是对的，改的时候别顺手「优化」成求和。

### 6.7 SP 的数值口径（写进 §九 给外部 AI）

* SP **最小单位是 1 点，无小数**。游戏内部虽按浮点累加，但显示与判定
  按整点。沙盘的 `cycles()` 用浮点是精度余量，不影响语义。
* SP 上限 = `spCost`（普通）或 `spCost × maxChargeTime`（可充能）。
* 入场预充 = `spData.initSp`（「初始技力」）。
* 被动技能 `spType == 8`（1775 个等级）→ `SkillCycle.is_passive`，不进回转。

解包 `spType` 分布（注意它是**字符串**，不是数字枚举）：

| spType | 等级数 | 语义 |
|---|---|---|
| `INCREASE_WITH_TIME` | 7941 | 自动回复，1 SP/秒（有隐藏冷却槽） |
| `8` | 1775 | 被动 |
| `INCREASE_WHEN_ATTACK` | 1186 | 攻击回复 |
| `INCREASE_WHEN_TAKEN_DAMAGE` | 202 | 受击回复 |

> **口径陷阱**：`core/skilldata.py` 只处理数字 `8`，
> 不认识 `INCREASE_WITH_TIME` 等字符串；`SkillCycle.recover` 是由
> `tree_type` 的**中文文本**（「攻击/受击/被动/自动」）推出的。
> 两条链路各走各的，改一处必须核对另一处，否则会出现
> 「技能表说是攻击回复、沙盘按自动回复算」的静默不一致。

### 6.8 受击回复的硬约束（必须承认）

`SP_DEFENSE`（受击回复，202 个等级）需要知道「这一秒有谁在打这个干员」。
沙盘不模拟攻击结算（这是用户明确的边界），所以：

* **能做**：把受击回复技能标出来，并在 UI 上提供手动「受击 N 次」入口
  （右键干员 → 受击 +1），让用户按需推进 SP。
* **不能做**：自动推算受击节拍。任何「按敌人数量估算」的做法都是编造。

`state_at()` 对 `SP_DEFENSE` 现在返回速率 0.0（即永不攒满），
这是**诚实的**默认；不要为了「看起来能动」而硬塞一个假速率。

### 7.2 数据在两个本地没有的表里

`cache/operators.json` 里**没有**范围信息（实测顶层字段只有

### 7.3 改法

1. **加缓存下载**：`range_table.json` 已在本次验证时落到
   `akcalc/data/range_table.json`（18 704 B，73 id），实施时把它挪到
   `data/cache/` 并在 `Paths` 上加一个访问器即可（对齐
   `enemies_cache` / `operators_cache` 的写法）。
   还缺的是 `character_table.json` 的 `phases[].rangeId` 摘要——
   只需抽 `char_id -> {elite -> rangeId}` 的小字典，约几十 KB。
2. **填死字段**：`core/enemies.py` 式地做一个
   `core/ranges.py`：`load() / get(range_id) / cells(range_id, facing)`。
3. **接进棋子**：`_pick_operator` 时按当前精英化取 `rangeId`，
   `_deploy_pending` 里算 `range_cells = RANGES.cells(range_id, facing)`，
   写进 `OperatorPiece.range_cells`。
4. **朝向变换**：`direction=1` 是朝右基准。四个朝向的变换
   （`RIGHT` 原样、`DOWN` 转 90°、`LEFT` 转 180°、`UP` 转 270°）：

```python
def rotate(cells, facing):
    """cells: 以自身格为原点的 (row, col) 集合，基准朝右。"""
    if facing == "RIGHT": return set(cells)
    if facing == "DOWN":  return {( c, -r) for r, c in cells}   # 顺时针 90°
    if facing == "LEFT":  return {(-r, -c) for r, c in cells}   # 180°
    if facing == "UP":    return {(-c,  r) for r, c in cells}   # 顺时针 270°
```

`LEFT` 必须写成 **`(-r, -c)`（180° 旋转）**，不是 `(r, -c)`（左右镜像）。
语义上后者是错的——朝左应该是「把人转过去」，不是「照镜子」。

**但要如实说明一件事**：我实测了全部 73 个 id，
**它们全部左右对称**（对每个 id，`{(r,-c)}` 与 `{(-r,-c)}` 集合相同），
所以在**当前这份数据上**两种写法结果一致，写错不会立刻暴露。
仍应写成旋转，理由：①语义正确；②`skill_table_full.json` 的 `rangeId`
引用的 `x-*`/`y-*` 里已有 25 格的复杂形状，未来数据一旦出现不对称范围，
镜像写法会静默出错；③这条和 §7.4 的「格子数不变」验收一起当回归护栏。

实测同时确认了两条不变量（73/73 通过，无重复格、无旋转后格数变化）：
* 每个 id 的 `grids` 内部**无重复格**；
* 四朝向旋转后**格子数不变**。

`facing` 的取值与 `Deployment.facing` 一致（`RIGHT` / `DOWN` / `LEFT` / `UP`），
基准 `direction=1` = `RIGHT`。

   `_set_facing()` 现在把 `range_cells = None` 直接丢掉，
   改成**按新朝向重算**（保留 `range_id` 在 `OperatorPiece` 上）。
5. **技能范围**：`skill_table_full.json` 的 `levels[i].rangeId` 是技能
   自定义范围（51 个不同值，如 `x-4`×461、`x-1`×281、`4-1`×172）。
   技能开启期间用技能范围，否则用基础范围。**这是「技能效果」的一部分，
   属于明确不做的边界**——但范围显示本身无害，建议一并做上，
   否则用户会以为技能没生效。

### 7.4 验收

* 能天使（`3-1`，朝右）范围应为 3 列渐宽的狙击排布，不是 3×3。
* 同一干员朝上/下/左/右，格子数不变、形状旋转 90° 的整数倍。
* `x-*` 范围 id 落到兜底时打日志，不要静默变成 3×3。
* 范围与阻挡无关（范围只是显示 + 未来伤害判定的输入），
  改范围**不得**改变任何可达性数字。

### 8.3 改法

**第 1 步 · 把 `paths` 进渲染器。**
`MapRenderer.__init__` 现在不收参数、也没有 `paths` 属性；
`MapCanvas.__init__`（`ui/map_canvas.py:47`）也是 `self._r = MapRenderer()`，
两者都拿不到 `app.paths`。做法：

```python
# map_render.py
class MapRenderer:
    def __init__(self):
        ...
        self.paths = None               # 新增属性

    def set_paths(self, paths):
        self.paths = paths
        _AVATAR_CACHE.clear()           # 换数据目录后必须清
        _SPRITE_CACHE.clear()           # 圆点精灵一并清（配色可能不同）

# map_canvas.py
def set_paths(self, paths):
    self._r.set_paths(paths)
    self.invalidate()
```

`MapCanvas` 只有两个实例化点（实测 `grep`）：
`ui/sandbox_panel.py:213` 与 `ui/path_panel.py:465`，都是 `MapCanvas(left)`。
`MapCanvas` 自身**没有** `app` / `paths` 属性（`__init__` 只有 `self._r = MapRenderer()`）。

所以在 `sandbox_panel.py` 里 `self.app.paths` 是现成的
（`:114` 存了 `self.app = app`），构造 `MapCanvas` 之后调一次
`self.canvas.set_paths(self.app.paths)`；`path_panel.py` 那边同样按它自己的
`app` 传一次，否则寻路面板的干员棋子不显示头像（不影响功能，只是没头像）。

`MapCanvas.set_paths()` 内部必须再调 `self._r.invalidate()`
（`map_render.py:430`，清静态层），否则换了数据目录但主图仍是旧的。

**第 2 步 · 头像精灵缓存（照抄 `_dot_sprite` 的成熟写法）。**

现有 `_SPRITE_CACHE`（`map_render.py:312`）+ `_dot_sprite()`（`:324`）已经是
「按 key 缓存预渲染图」的正确范式，头像直接沿用同一模式：

```python
_AVATAR_CACHE: Dict[Tuple, Image.Image] = {}
_MASK_CACHE: Dict[int, Image.Image] = {}

def _circle_mask(d: int) -> Image.Image:
    m = _MASK_CACHE.get(d)
    if m is None:
        s = 4                                    # 4x 超采样，边缘不锯齿
        big = Image.new("L", (d * s, d * s), 0)
        ImageDraw.Draw(big).ellipse([0, 0, d * s - 1, d * s - 1], fill=255)
        m = big.resize((d, d), Image.LANCZOS)
        _MASK_CACHE[d] = m
    return m

def _avatar_sprite(paths, name: str, d: int) -> Optional[Image.Image]:
    """圆形头像。取不到图标返回 None，由调用方退回画首字。"""
    key = (name, d)
    sp = _AVATAR_CACHE.get(key)
    if sp is not None:
        return sp
    if paths is None:
        return None
    ic = OI.load_icon(paths, name, d)            # 已按 (name, d) 缓存，返回 copy
    if ic is None:
        return None
    if ic.mode != "RGBA":
        ic = ic.convert("RGBA")
    base = Image.new("RGBA", (d, d), (0, 0, 0, 0))
    base.paste(ic, (0, 0), _circle_mask(d))
    _AVATAR_CACHE[key] = base
    return base
```

**缓存必须包含 `paths`**（不同数据目录的图可能不同）。
省事的办法是像上面那样在 `set_paths()` 里 `clear()`，
而不是把 `id(paths)` 塞进 key——`id` 会被回收复用。

**第 3 步 · 改第 4 段绘制。**

```python
# 棋子：先铺底圆（保留可读的对比底），再叠圆形头像，再画朝向三角
d.ellipse([x - rad, y - rad, x + rad, y + rad],
          fill=_rgba(PIECE_OPERATOR_DIM, 245),
          outline=_rgba(PIECE_OPERATOR if not sel else (255, 255, 255), 255),
          width=max(2, cell // 12))

dia = int(rad * 2) - 3                    # 直径，留 3px 给外圈白边

if sp is not None:
    im.alpha_composite(sp, (int(x - dia / 2), int(y - dia / 2)))
else:
    # 只有 2/463 会走这里，退回首字，绝不能留白
    if name and cell >= 22:
        d.text((x, y - rad * 0.15), name[0], font=_font(fs, True),
               fill=_rgba((255, 255, 255), 255), anchor="mm")

```

三个必须保留的视觉层（否则信息丢失）：

1. **朝向三角** —— 头像圆里看不出朝哪，这是部署模拟的核心信息。
2. **选中白环** —— `sb["selected_op"] == pos` 时描边转白，别被头像盖掉。
3. **名字首字退回** —— 461/463 有图，剩 2 个必须有退化路径。

**第 4 步 · 不要碰静态层。**
`_master_static_key()`（`:534-547`）最后一项是
`self.sandbox is not None`——**只这一个布尔量**。`_draw_sandbox` 全部

### 8.5 尺寸自适应

`cell` 会随缩放变化（`set_zoom` / `fit`）。必须用 `dia` 作缓存 key，
**不能**固定某个像素值——否则放大后头像糊成马赛克。
实测各档冷启动耗时（单枚）：`24px 2.9ms / 32px 2.4ms / 48px 2.1ms /
64px 2.1ms / 96px 2.6ms`，差异可忽略，可直接按 `dia` 取。

`dia < 14`（极小缩放）时**不要画头像**——缩到那个尺寸只剩色块，
反而比纯色圆更乱。阈值定 `dia >= 14`，否则退回纯色圆 + 三角。

* 缩放 0.5× ~ 3×，头像清晰、不糊、不串位。

* 拖动箱子 / 拖游标时帧率不下降（对比改前）。
* 静态层重烘焙次数不因头像增加（可在 `_ensure_master` 打点确认）。

## 九 完整战斗机制规格（D1 · 给外部 AI 的权威定义）

> 本节是**规格**，不是实现描述。§9.4 起每个公式都附一组
> **本项目实测过的数值向量**；外部 AI 照此实现后，应用同一组向量
> 自检，结果必须逐位一致（除明确标注的浮点容差外）。

### 9.1 伤害类型

| 代码 | 中文 | 吃防御 | 吃法抗 | 吃元素抗 | 吃穿透 |
|---|---|---|---|---|---|
| `PHYSICAL` | 物理伤害 | ✅ | — | — | ✅ 物穿 + 减防 |
| `MAGICAL` | 法术伤害 | — | ✅ | — | ✅ 法穿 |
| `ELEMENTAL` | 元素伤害 | — | — | ✅ | ❌ 不吃穿透 |
| `TRUE` | 真实伤害 | — | — | — | — |
| `HEAL` | 治疗 | — | — | — | — |

常量：`MIN_DAMAGE_RATIO = 0.05`（5% 保底）、
`ELEMENT_RATIO = 0.01`、`RESIST_BASE = 100`。

### 9.2 基本伤害 A

```
A = 攻击力 × 攻击力倍率 + 附加攻击力
```

`攻击力` 是干员面板攻击力（已含信赖、潜能、模组、等级）。
`攻击力倍率` 是技能/天赋给的乘算（如真银斩 3.0）。
`附加攻击力` 是加算项。

### 9.3 结算顺序（不可调换）

```
① 减防     D' = (1 - 减防%) × D                —— 只作用于物理
② 穿透     E  = (1 - Ip) × max(0, D' - Iv)     —— 先减固定、再乘百分比
③ 原始伤害 raw —— 按伤害类型分支（见 9.4）
④ 5% 保底  raw = max(raw, 0.05 × A)            —— 除 ignore_min_damage 外必过
⑤ 增伤     raw = raw × (1 + damage_boost)
⑥ 最终倍率 raw = raw × final_scaler
⑦ 连击     total = raw × hit_count
```

**注意 ② 的括号位置**：是 `(1-Ip) × (D' - Iv)`，
即**先扣固定值再乘百分比**，不是先乘再扣。写成
`(1-Ip)×D' - Iv` 会算错。

**注意 ④ 的位置**：保底在**穿透之后、增伤之前**。所以
「630 攻打 1000 防」先得 `raw = -370`，过保底得 `31.5`，
再被增伤 0.3 抬到 `40.95`。**保底不参与增伤的基数放大**以外的修正。

### 9.4 各类型公式

**物理**
```
E   = (1 - Ip) × max(0, D' - Iv)
raw = A - E
```

**法术**
```
E   = (1 - pen_pct) × max(0, R - pen_flat)
raw = 0.01 × A × max(0, 100 - E)
```
其中 `R` 是目标法抗。`pen_pct` / `pen_flat` **优先取 `res_pen_*`；
若未提供则回退到 `def_pen_*`**（历史兼容行为，必须保留，
否则旧调用方会静默变成「没法穿」）。

**元素**
```
raw = 0.01 × A × max(0, 100 - ERE)
```
`ERE` = 元素抗性。**不吃任何穿透**。

**真实 / 治疗**
```
raw = A
```
不吃防御、不吃抗性、不吃穿透。

### 9.5 实测数值向量（外部 AI 的自检基准）

攻击力单位、防御值单位均按游戏面板。全部由 `core/damage.py` 现场复算：

| # | 输入 | 期望 `final_damage` | 期望 `floored` |
|---|---|---|---|
| 1 | 物理 A=630, D=1000 | **31.5** | True |
| 2 | 物理 A=1000, D=2000 | **50.0** | True |
| 3 | 物理 A=1000, D=500 | **500.0** | False |
| 4 | 物理 A=1000, D=1000, `def_pen_percent=0.5` | **500.0** | False |
| 5 | 物理 A=1000, D=1000, `def_down_percent=0.5` | **500.0** | False |
| 6 | 物理 A=1000, D=1000, `damage_boost=0.3` | **65.0** | True |
| 7 | 物理 A=1000, D=1000, `damage_boost=0.3, final_scaler=0.8` | **52.0** | True |
| 8 | 法术 A=1000, 法抗=100 | **50.0** | True |
| 9 | 法术 A=1000, 法抗=100, `res_pen_flat=30` | **300.0** | False |
| 10 | 法术 A=1000, 法抗=200, 只给 `def_pen_flat=50` | **50.0** | True |
| 11 | 真实 A=1000, D=5000 | **1000.0** | False |
| 12 | 物理 A=1000, D=500, `hit_count=3` | final **500.0**，total **1500.0** | False |

派生函数：

| 函数 | 定义 | 实测 |
|---|---|---|
| `break_defense_threshold(A)` | 使伤害**恰好**触到 5% 保底的防御临界值：`D* = A × (1 - 0.05) = 0.95A` | `break_defense_threshold(630) = 598.5` |
| `compute_dps(dph, interval, hit_count=1)` | `dph × hit_count / interval` | `compute_dps(630, 1000, 1.0) = 0.63` |

> 第 6 条容易算错，单独说明。A=1000 打 D=1000：有效防御 `E = 1000`，
> 原始伤害 `raw = 1000 - 1000 = 0` → 过 5% 保底抬到 `0.05 × 1000 = 50`
> → 再乘增伤 `50 × 1.3 = ` **65.0**。
> 也就是说**保底先落地，增伤再作用在保底值上**（顺序是 ④→⑤）。
> 若把顺序写成「先增伤再保底」，会得到 `max(0.05A, 0×1.3) = 50`，
> 与实测差 15 点。外部 AI 必须照抄 §9.3 的次序。
>
> 同理第 7 条：`50 × 1.3 × 0.8 = 52.0`，证明 `final_scaler` 排在
> `damage_boost` **之后**。

### 9.6 混伤（多类型分量）

一只干员的单次攻击可以同时含多个分量（如「造成 30% 物理 + 70% 法术」）。

```
每个分量独立走 §9.3 全流程；
target 按分量类型选：物理→防御  法术→法抗  元素→元素抗  真实→无；
damage_boost 与 final_scaler 对全部分量各乘一次（不是分完后统一乘）。
```

`MultiTypeInput` 字段：`attack, components, target_defense, target_res,
target_eres, damage_boost, final_scaler, label`。

`multi_dps(res, interval) = res.total_damage / interval`。
`multi_per_hit(res) = Σ 各分量 final_damage`（不含连击）。

### 9.7 攻击间隔与攻速

```
攻速 S 的有效值 = clamp(S, 10, 600)          # ATTACK_SPEED_MIN / MAX
有效攻击间隔    = 基础攻击间隔 t0 / (S / 100)
```

实测：

| `t0` | `S` | 有效间隔 |
|---|---|---|
| 1.3 | 10 | 13.0 |
| 1.3 | 20 | 6.5 |
| 1.3 | 100 | **1.3** |
| 1.3 | 600 | 0.21666… |
| 1.3 | 700 | 0.21666…（被 600 钳住） |
| 1.3 | 0 | 13.0（被 10 钳住） |

> **口径缺陷（如实记录）**：代码里还有一个
> `ATTACK_SPEED_HARD_MIN = 20`，但**在 `constants.py` 之外从未被引用**。
> 也就是说「攻速下限 20」这条规则**没有生效**，实际用的是 10。
> 外部 AI 若要严格对齐游戏，应自行决定采信哪个；
> 本文按**现有实现（10）**给向量，并标注此处存疑。

**攻速与 SP 的关系**：攻击回复技能的 SP 速率 `= 1 / 有效攻击间隔`
（见 §6.1）。所以攻速 buff 会同时改变 DPS 与技能回转节奏。

### 9.8 抬手（攻击前摇）

**定义**：从攻击动画第 0 帧到 `OnAttack` 事件发生的时间点，单位「秒」。
这是「敌人抬手到打出伤害」的延迟，**不是**攻击间隔。

数据来源：`data/enemy_attack_timing.json`，由解包
`zh_CN/gamedata/bakemuzzledata/enemy/*.json` 的
`OnAttack` 事件时间点抽取。**PRTS / wiki 的 API 不提供这个数据。**

实测覆盖：

| 项 | 数值 |
|---|---|
| 有抬手数值的敌人 | **1857** |
| 敌人 id 总数 | 2186 |
| 覆盖 | 1868（含只有单一动画者） |
| 无攻击动画 | 252 |
| 源文件数 | 2109 |
| 解析错误 | 0 |
| 有多个攻击动画的敌人 | **358** |

分布（n=1857）：`min 0.0` / `max 4.8333` / `mean 0.6591` / `median 0.5667`。

| 区间 | 数量 |
|---|---|
| ≤ 0.2 s | 34 |
| 0.2 – 0.5 s | 733 |
| 0.5 – 1.0 s | 882 |
| 1.0 – 2.0 s | 182 |
| > 2.0 s | 26 |

**动画选择优先级**（多动画时必须按此取）：
```
Attack > Combat > Attack* > *_Attack > Skill 上的 OnAttack
```

**单位换算**：`FPS = 30`，`秒 = 帧 / 30`，`帧 = 秒 × 30`。
对外接口同时支持两种入参（`attack_timing_convert`）。

### 9.9 状态：阻挡、对空、嘲讽

**阻挡几何**（权威模型，`core/blocking.py`）：

```
地面阻挡半径  R_g = 0.70709997 格      (R_g² = 0.49999037)
对空半径系数  0.8944  →  R_f = R_g × 0.8944
判定：取「干员位置 → 敌人位置」的中点 M，
      若 |M - 干员位置|² ≤ R² 则被挡
被挡后被推至距干员 BLOCK_OFFSET_RADIUS = 0.5 格的圆边界上
```

实测：
```
is_blocked((0,0),(0.50,0)) → True
is_blocked((0,0),(0.75,0)) → False
apply_block_offset((0,0),(0.40,0)) → final=(0.5,0), distance=0.100
apply_block_offset((0,0),(0.75,0)) → final=(0.5,0), distance=0.250
```

**阻挡容量**：取干员 `block` 属性（1/2/3）。实测 463 名干员：
`block=1` 311 人、`2` 113 人、`3` 32 人、`0` 7 人。

> **`enemy.blockCnt` 不能当容量用**：2450 行里 2449 行是 `0`，
> 唯一非零是 `enemy_2092_skzamy`（1）。它是敌人的「被阻挡相关」字段，
> 不是干员的阻挡数。

**飞行**：`enemyData.motion` 实测 `WALK` 2267 / `FLY` 183。
飞行单位忽略地面阻挡。

**嘲讽**：`tauntLevel` 实测 `0`×2345、`1`×61、`-1`×21、`2`×16、`-2`×7。
**`core/damage.py` 没有实现嘲讽选敌**——沙盘不模拟目标选择，
所以这一项只作为数据提供，不承诺计算。

### 9.10 明确未实现、不得假装实现的四项

外部 AI 接进来时最容易踩的坑，逐条写清：

**① `damageHitratePhysical` / `damageHitrateMagical` **不是闪避**。**
实测：这两个字段默认 `0.0`，**恰好 447 个 id 是 `(1.0, 1.0)`**，
且全部是花/树家族（`enemy_10064_ftyzss` 巡游草叶、`_ftzlc` 卷心籽、
`_ftxjl` 巢穴、`_ftsjc` 灼藤、`_ftxsr` 指路芽、`_ftlsj` 树盾 …）。
`1.0` 的含义是「有命中框 / 可被命中」，`0.0` 是默认值。
**把它当闪避率会得出「所有花树百分百闪避」的荒谬结论。**

**② 元素「爆条」未实现。**
`damage.py` 有 `ELEMENTAL` 类型（按元素抗性线性折算），
但**没有**「元素损伤累积 → 爆条 → 额外伤害」这条链路。
`enemy_codex.py` 能识别 `epResistance` / `epDamageResistance` 字段，
仅作展示。元素伤害只能算「直伤」，不能算爆条。

**③ 闪避与命中：数据里没有可推导的模型。**
全库 blackboard 里与命中/闪避相关的键只有
`damage_hitrate_physical` / `damage_hitrate_magical`（各 1 处）和
`prob`（5 处）。不足以支撑一个通用闪避模型。

**④ 击杀不返费。**
实测 2450 行敌人的 `attributes.cost`（击杀获得费用）**全为 `0`**。
所以沙盘的 DP 只有「时间回复 + 撤退返还」，没有「击杀获得」。
外部 AI 若从别处读到「击杀给费」，那是关卡脚本效果，不是敌人属性。

### 9.11 敌人其它属性（供推算用，实测分布）

`baseAttackTime`（基础攻击间隔）：3.0×336、**0.0×327**、1.0×254、4.0×234、
5.0×228、2.0×193、3.5×142、2.5×137。
> `0.0` 的那 327 行是**不普攻**的单位（召唤物、纯机制怪），
> 不能当成「无限快」。

`moveSpeed`（移动速度倍率）：1.0×337、**0.0×307**、0.7×287、0.8×278、
0.5×204、0.6×189、0.9×122、0.4×83。
按 id 统计（2186 个，排除 speed=0 后 2134 个）：**1798 个（84.3%）既不是 1.0 也不是 0.0**。

`attackSpeed`：`100.0`×2075、`0.0`×374、`200.0`×1。
> `0.0` 且 `baseAttackTime` 非零的 66 行、以及 `baseAttackTime=0`
> 而 `attackSpeed` 非零的 19 行，都是数据侧的边界情形；
> 后者说明该单位用别的机制出伤，不是「0 间隔」。

`lifePointReduce`（漏怪扣生命）：1×1574、**0×634**、2×98、5×62、
3×42、30×32、50×5、15×1。
> `0` 的 634 行是**不计生命**的单位，别当 1 算。

`levelType`：含 `BOSS` 等。`applyWay`：`MELEE` 等。

### 9.12 取整口径

全项目统一用**银行家舍入**（round-half-even），实现于
`core/constants.py: banker_round(x)`。外部 AI 若用 Python 默认
`round()` 会一致；若用 `Math.round()`（half-up）会在
`.5` 边界上出现 1 点偏差。

## 十 MCP 接口规格（D2 · 给外部 AI 的机器可读接口）

### 10.1 现状

`akcalc/mcp/` 是 stdio JSON-RPC（`PROTOCOL_VERSION="2024-11-05"`，
`SERVER_NAME="feiniu-akcalc"`，`SERVER_VERSION="2.3.0"`）。
当前**在线 19 个工具**（由 `server.tools()` 实测）：

| 分组 | 工具 |
|---|---|
| 敌人（5） | `enemy_list` `enemy_get` `enemy_search` `enemy_library_status` `enemy_attack_timing` |
| 干员（5） | `operator_list` `operator_get` `operator_search` `operator_professions` `operator_library_status` |
| 地图（4） | `map_list` `map_get` `map_search` `map_catalog_status` |
| 路线（4） | `route_list` `route_summary` `route_at_second` `route_pose` |
| 换算（1） | `attack_timing_convert` |

**缺口**：有数据查询，**没有计算**。外部 AI 拿到攻击力/防御力/伤害类型，
仍然得自己实现 §9 的全部公式与结算次序——而这正是最容易算错的部分
（见 §9.5 向量 6、§9.3 的括号位置）。

### 10.2 新增 7 个工具（全部纯计算，无副作用）

统一约定：
* 入参 `"type": "object"`，`"additionalProperties": false`；
* 必有 `required`，不许「什么都不传也算成功」；
* 返回 `ok(payload)`（`json.dumps(indent=2, ensure_ascii=False)`）；
* 单位一律「秒」「点」「格」，不做隐式转换；
* 无本地数据依赖的工具（`battle_damage_calc` 等 3 个）**不查缓存**，
  冷启动也能秒回。

```json
    "count": 3,
    "state_at": {"ready": false, "sp": 1.875, "need": 20.0,
                 "active": false, "next_in": 29.0,
                 "cycle_index": 1, "passive": false}

```

上表数字全部取自现状实现（`sp_cost=20, duration=10, recover=ATTACK,
attack_interval=1.6`）：`sp_rate = 1/1.6 = 0.625`，首轮在第 `20/0.625 = 32.0` 秒
攒满；`cycles` 每项是 `(ready, active_since, active_to)`；第三轮被
`end_time=120` 截断。`state_at` 的键**恰好**是
`ready / sp / need / active / next_in / cycle_index / passive`
——**现状没有 `charges` 字段**（§6.4 要加充能时必须同步补进 `state_at`，
否则外部 AI 拿不到充能层数）。

**必填 `attack_interval`（当 `recover=ATTACK`）**：不给速率就算不出来。
这正是当前沙盘写死 1.0 的根因（§6.1），接口层面必须强制。

`recover=DEFENSE` 与 `recover=NONE` 实测返回 `cycles: []`（速率 0.0），
这是故意的诚实默认，见 §6.8。

## 十一 实施顺序、回归与风险

### 11.1 实施顺序（按「依赖 + 用户感知」排，不是按章节）

| 序 | 内容 | 前置 | 为什么排这里 |
|---|---|---|---|
| 1 | **§6.2 接真实攻击间隔** | 无 | 一行字段 + 一行传参，改动最小、收益最大（修 89.4% 干员） |
| 2 | **§8 棋子头像** | 无 | 纯渲染，零逻辑风险，用户立刻看得见 |
| 3 | **§5.7 逐敌人移速** | 无 | 修 84.3% 敌人，但要先做缓存结构 |
| 4 | **§7 攻击范围** | 需下两张表 | 范围是阻挡之外唯一「看得见」的错 |
| 5 | **§4 阻挡换模型 + 票券** | 无 | 会改变到达时间，要有回归兜底 |
| 6 | **§5 部署/撤退/DP/生命** | 阻挡稳定后 | 独立状态机，但依赖阻挡时序 |
| 7 | **§6.3-6.5 阻回/充能/弹药** | 序 1 | 依赖真实攻击间隔 |
| 8 | **§9 §10 文档 + MCP 工具** | 前面定型 | 规格必须跟实现一致，不能先写 |

**理由**：序 1、2、3 都是「接线」而非「重构」，风险低、可独立回滚。
把高风险项（序 5）夹在中间，前后都有可发布的版本。

### 11.2 回归测试清单

现有 `test_full_regression.py`（103 KB，31+ 节）必须**全部继续通过**。
新增测试按块组织：

**阻挡（§4）**
1. 敌人停在距干员中心 0.5 格（容差 0.02）。
2. 阻挡数 1 + 两只同帧到达 → 第二只不停，且走到下一枚干员处被挡（bug A）。
3. 撤退后敌人从被挡处继续，不跳回起点。
4. 三只敌人被同一干员挡住 → 三点互不重合且在半径 0.5 圆上（bug C）。
5. `cap=1` + 手动击杀 → 后续敌人能被接着挡（bug B）。
6. **不变量**：2629 个关卡可达性数字不变。

**部署/DP（§5）**
7. `initialCost=10` + `costIncreaseTime=1.0` → 第 10 秒有 20 费。
8. `costIncreaseTime=999999` → 永不回复（不是「很慢」）。
9. 费用不足 → `deploy_check` 返回 False 且**状态不变**。
10. 撤退 → 返还实际消耗；再部署费用 ×0.5；两次后 ×0.25 封顶。
11. `maxCost` 到顶 → 停回且溢出丢弃。
12. 负费开关开启 → 负费期间回复减半。
13. 漏 50 只 vs 漏 0 只 → 生命值差异符合 `lifePointReduce` 之和。

**技能 SP（§6）**
14. 攻击间隔 1.6 的攻击回复技能 → 首轮 SP 满在 32.0 秒（不是 20.0）。
15. 攻击间隔 2.85 → 57.0 秒。
16. 阻回：技能期间不回 SP；`recover_in_skill=True` 时第二轮提前到 64.0。
17. `maxChargeTime=2` → SP 上限 = `2 × spCost`，`charges` 正确。
18. `durationType=AMMO` → 不按持续时间退出，按弹药数。

**范围（§7）**
19. 能天使 `3-1` 朝右 → 非 3×3。
20. 四朝向旋转后格子数不变。
21. `x-*` 落兜底时**打日志**（不能静默）。

**头像（§8）**
22. 8 个不同干员 → 8 个头像互不相同。
23. 缩放 0.5×~3× 头像清晰。
24. `暮落(集成战略)`、`真言` → 首字退化，不是白块。
25. 静态层重烘焙次数不因头像增加。

**移速（§5.7）**
26. `a001_06` R1（速度 0.5）→ 总时长 129.6 秒（原 75.8）。
27. `a001_06` R12（速度 1.9）→ 14.38 秒（原 27.31）。
28. `act1multi_football`（1361 路线）→ 重算耗时 < 1 秒。

**MCP（§10）**
29. 上表 §9.5 全部 12 条数值向量逐条比对。
30. `tools()` 返回 26 个，且 `--list-tools` 一致。
31. 每个新工具的 schema 都 `additionalProperties: false` 且有 `required`。

### 11.3 已知风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **阻挡换模型会改历史结果** | 用户此前调好的时间轴会变 | 在导出 JSON 里写 `version`，加载 v1 文件时按旧模型复现并提示「旧档用旧算法」 |
| **逐敌人移速拖慢最坏关卡** | `act1multi_football` 1361 路线，热态 288 ms（冷态 >600 ms） | 按 `(route, speed)` 去重（§5.7）；必要时加「固定速度」开关退回 v1 行为 |
| **`ATTACK_SPEED_HARD_MIN` 口径不一致** | 常量 20 从未生效，实际用 10 | 文档如实标注（§9.7），**不擅自改代码**——改了会静默改变所有既有数值 |
| **`damageHitrate*` 被误当闪避** | 447 个花树单位是 1.0 | 文档显式警告（§9.10①），MCP 返回里加 `"note"` 字段 |
| **`spType` 双链路不一致** | `skilldata.py` 认数字 8，`SkillCycle.recover` 认中文文本 | 改一处必须核对另一处（§6.7 已标陷阱） |
| **头像进静态层** | 会把拖动变成幻灯片（60 ms/次） | `_master_static_key()` 只留布尔（§8.3 第 4 步），代码评审时当红线 |
| **`PhotoImage` 被 GC** | 渲染成白块 | 本次全用 `alpha_composite`，不新增 `PhotoImage`（§8.3） |
| **充能语义只对一半** | `maxChargeTime` 有值但「蓄力」变种另有规则 | 先只做次数上限 + 计数，蓄力特例标注为未做（§6.4） |
| **受击回复无法自动推进** | 需要伤害判定，与「不模拟结算」冲突 | 提供手动「受击 +1」入口，不编造速率（§6.8） |

### 11.4 与现有文档的关系

| 文档 | 关系 |
|---|---|
| `docs/沙盘数据修复记录.md` | **数据层**的坑与修法（31+ 节）。本文是**机制层**，两者正交；本文所有「已达成」项都引它作证据 |

### 11.5 一句话总结

> 沙盘的**寻路**已经是「解包数据驱动的正确答案」，
> 要补的是**战斗层的四处接线**：攻击间隔、攻击范围、费用经济、棋子头像。
> 战斗机制那部分不该塞进沙盘——它属于**规格 + MCP 工具**，
> 让外部 AI 按同一套公式算，才不会出现「沙盘一套、外挂一套」的分裂。
