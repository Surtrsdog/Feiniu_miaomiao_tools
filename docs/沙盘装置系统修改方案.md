# 沙盘装置系统修改方案

> 版本 v1.0 · 纯方案文档 · 不含任何代码改动
> 面向对象：接手实现的 AI / 工程师
> 数据基线：`akcalc/data/cache/levels/` 全量 2629 个关卡文件 · 2147 张唯一地图
> 关联文档：`沙盘数据修复记录.md`（现象/根因体例）、`沙盘完全模拟与战斗机制规格.md`（战斗层）、`工作指令_沙盘画面与结束机制.md`（画面层）

---

## 零、一句话结论

**沙盘的地图与寻路完全没有读取 `predefines.tokenInsts`，也就是完全没有读「地图上原有的装置」。**
`akcalc` 全仓对 `tokenInsts` 的引用只有 2 处，且都是注释/文档字符串，**零处功能代码**。
所以「好梦在何方」上方那排碎石在沙盘里根本不存在，敌人自然直接穿过本应被堵住的走廊——这不是路线算法错，是**装置数据整层缺失**。

实测：给「好梦在何方」补上那 11 个碎石后，**47 条路线里有 42 条长度改变**（最多的 R10 从 4.83 格变成 19.66 格，4.07 倍），全图总路程 +30%。这与用户描述的「几乎全部敌人的路线偏移」完全吻合。

## 一、问题实证

### 1.1 用户报告的现象

> 「目前地图缺少大量地图原有的大量装置，有些装置是可以操作的，地图中也没有出现，导致路线很奇怪。比如好梦在何方的上方石箱子缺失导致几乎全部敌人的路线偏移。」

拆成三个可验证的子命题：

| # | 子命题 | 验证结果 |
|---|---|---|
| P1 | 地图缺少关卡原有的装置 | **成立**。11458 个装置实例，代码一个都没读 |
| P2 | 有些装置可以操作，但地图里没出现 | **成立**。可操作装置同样在 `tokenInsts` 里，同样没读 |
| P3 | 装置缺失导致路线偏移 | **成立**。好梦在何方 42/47 条路线受影响，见 §1.4 |

### 1.2 数据在，只是没人读

**关键事实一：本地关卡数据与官方上游逐字节一致。**

```
本地 akcalc/data/cache/levels/levels_obt_roguelike_ro2_level_rogue2_5-5.json   147298 B   md5=72a417c7167ca61250bd394d3775d34a
上游 zh_CN/gamedata/levels/obt/roguelike/ro2/level_rogue2_5-5.json             147298 B   md5=72a417c7167ca61250bd394d3775d34a
完全相同: True
```

所以**不是数据缺失、不是解包不全、不是缓存过期**。装置数据完整地躺在每一个关卡 JSON 里。

**关键事实二：装置在 `predefines` 里，而代码从不读 `predefines`。**

`predefines` 是一个 dict，含 4 个 list：

| 键 | 含义 | 有关卡的占比 |
|---|---|---|
| `tokenInsts` | 预置装置（部署物 / 陷阱 / 障碍 / 可操作设施） | 1847 / 2629 = **70.3%** |
| `characterInsts` | 预置干员（友方 NPC） | 122 / 2629 = 4.6% |
| `tokenCards` | 可调用装置卡 | 少 |
| `characterCards` | 可调用干员卡 | 少 |

全仓检索结果（`grep -n 'predefines\|tokenInsts\|characterInsts' akcalc/**/*.py`）：

| 文件:行 | 内容 | 是否功能代码 |
|---|---|---|
| `akcalc/core/extra_mechanics.py:96` | `"-> branches.bsnake_flame 与 predefines.tokenInsts"` | ❌ 注释字符串 |
| `akcalc/ui/path_panel.py:1197` | `` ``predefines`` 里预置好的敌人一次性激活 `` | ❌ docstring |

**零处功能代码。** `GameMap` 里也没有任何 `devices` 字段（全仓 `\bdevices\b` 零匹配）。

### 1.3 装置实例的数据形状

以一个碎石为例，`predefines.tokenInsts[0]`：

```json
  "direction": "UP",
  "hidden": false,

  "uniEquipIds": null,

```

**注意它只有「位置 + 是谁 + 几级」，没有任何「是否阻挡 / 是否可操作 / 血量」的字段。**
这些语义必须从外部表查——这是后面 §2、§3 全部工作的根源。

顺带一个重要坑：`position.row` 是**自上而下**的行号，与 `GameMap.tiles[row][col]` 一致（因为 `maps.py:184` 做了 `matrix = list(reversed(matrix))`）。已实测：11 个碎石全部落在 `tile_road` 可通行格上；若按 `mapData.map` 原始行序摆放，会全部落到 `tile_wall` / `tile_forbidden` 上。**这条不能想当然，见 §6 红线 R1。**

### 2.2 `hidden: true` 不等于「不存在」

这是最容易做错的一处。`hidden` 的本义是**「同一格上的 N 选 1 备选」**，典型是随机箱子三选一：

| 同格隐藏堆叠数 | 格子数 |
|---|---|
| 2 | 243 |
| 3 | **545** |
| 4 | 91 |
| 7 | 1 |
| 13 | 1 |

也就是说，约 49% 的「装置实例」是**同一格的备选项**，不是同时存在的实体。
**渲染时必须按格聚合，只画一个；阻挡判定时也只能算一个。**

同时，`hidden` **不能按类型判定**：`trap_027_stone` 共 135 个实例，其中 132 可见、3 隐藏——同一类型两种用法都有。**必须逐实例读 `hidden`，绝不能按类型猜。**（详见 §6 红线 R3。）

| `char_` | 预置友方干员（在 `characterInsts` 里） | 少数 |

## 三、装置分类：到底哪些会挡路

### 3.1 为什么不能只看 `blockCnt`

直觉上「会挡路的装置」= `blockCnt > 0`。**这个直觉是错的**，反例很硬：

| 装置 | `blockCnt` | 技能实际语义 | 会挡路吗 |
|---|---|---|---|
| `trap_020_roadblock` 道路障碍物 | **0** | 技能「道路阻塞」：可以阻挡乌萨斯平民与斗士塔露拉前进 | **会** |
| `trap_272_nomstn` 阻道岩壁 | **0** | （名字就叫「阻道」） | **会** |
| `trap_032_mound` 土石结构 | 3 | 阻挡**沙尘暴**，不是阻挡敌人 | **不会** |
| `trap_024_npcsld` 盾卫 | 3 | 是友方 NPC，挡的是敌人 | 会（友方单位） |

**结论：`blockCnt` 只表示「能同时拦住几个单位」，不表示「会不会改变敌人路线」。两者是不同的东西。**

### 3.2 真正的判据：技能描述里的「改变敌人行进路线」

装置的阻挡语义写在**技能描述**里，不在属性里。取官方 `skill_table.json` → `levels[].description`：

| 装置 | 技能 | 技能原文 |
|---|---|---|
| `trap_027_stone` 碎石 | `sktok_stone` 阻挡路线 | 「初始部署在场景中，改变敌人的行进路线。**如果障碍阻挡了敌人，敌人会破坏此障碍**」 |
| `trap_001_crate` 障碍物 | `sktok_crate` 阻挡路线 | 「设置障碍，改变敌人的行进路线。如果障碍阻挡了敌人，敌人会破坏此障碍」 |
| `trap_1105_accrate` 阻隔工事 | `sktok_accrate` 阻隔工事 | 「改变敌人的行进路线。如果阻隔工事阻挡了敌人，敌人会破坏此工事」 |
| `trap_207_mufrwl` 液压式高台 | — | 「修建完成后可部署远程干员并且改变敌人路线」 |

**极其关键的一句话：「如果障碍阻挡了敌人，敌人会破坏此障碍」。**
这说明装置在游戏里的真实身份是——

> **一个「可被敌人摧毁的阻挡实体」，不是「不可通行的地形」。**

这条语义决定了整个方案的架构（见 §3.4）。

### 3.4 语义定论：装置是「可破坏的阻挡实体」

三份独立证据指向同一结论：

1. **技能原文**：「如果障碍阻挡了敌人，敌人会破坏此障碍」；
2. **有 HP**：碎石 8000、障碍物 100、城防路障 5000——**地形墙不会有血量**；
3. **A/B 反证**：把装置当「不可通行地形」时，全库 **3028 条路线变成不可达**（`FAIL`）。真实游戏里敌人不可能因为一个木箱就再也走不到终点。

所以正确的建模是：

```
装置 = 一个占据单格、有 HP、可被敌人摧毁、会阻挡地面敌人的「中立单位」
        ├─ 敌人接触 → 停下并攻击它（进入战斗）
        ├─ 被摧毁   → 该格恢复可通行，后续敌人直接走
        └─ 若绕路更短 → 敌人绕路（等价于「当场作为障碍参与寻路」）
```

**架构含义（全文最重要的一条）：**

> **寻路时把 A 类装置当作 `blocked` 传入（得到「眼前这一刻敌人看到的路」）；
> 但必须同时保留「装置会在几秒后被打破、路随后打通」的状态机。
> 两者缺一不可——只做前者会导致 3028 条路线假性不可达；只做后者则永远算不对路线。**

### 3.5 判定边界清单（必须逐条过）

| 装置 | `blockCnt` | 技能有「阻挡」 | 名字有「阻挡/障碍」 | 结论 |
|---|---|---|---|---|
| `trap_020_roadblock` | 0 | ✅ | ✅ | **确认会挡**（技能明说） |
| `trap_272_nomstn` | 0 | ❌ | ✅ | **需确认**（疑似数据缺陷） |

### 4.2 阶段划分（强烈建议按此顺序，不要并行）

| 阶段 | 内容 | 预估 | 风险 |
|---|---|---|---|
| **S1** | 数据层 + 解析层：装置进 `GameMap.devices` | 1 天 | 低 |

#### 4.3.2 `GameMap` 新增字段

```python
@dataclass
class Device:
    row: int                  # 已自上而下，与 GameMap.tiles 一致
    col: int
    token_key: str            # "trap_027_stone"
    alias: str                # "trap_027_stone#1"
    direction: str            # "UP"
    hidden: bool              # 该实例自己的 hidden
    category: str             # "A"/"B"/"C"/"D"
    affects_route: bool
    block_cnt: int
    max_hp: int
    operable: bool
    stack_size: int = 1       # 同格 hidden 堆叠数，用于「N 选 1」
```

`GameMap` 上加：

```python
devices: List[Device] = field(default_factory=list)
```

以及三个便捷方法：

```python
def device_at(self, row, col) -> Optional[Device]
def route_blocking_cells(self) -> set        # 所有 affects_route=True 的格
def operable_devices(self) -> List[Device]
```

**关键实现要求：**

1. **按格聚合**。`tokenInsts` 里同一 `(row, col)` 若有多个 `hidden: True`，视为「N 选 1」：
   - `devices` 里只保留 1 个代表项，`stack_size = N`；
   - 若同格混有可见与隐藏项，**可见项优先**（可见项才是真身）；
   - 若同格全是隐藏项，取第一个作代表，`stack_size = N`。
2. **`hidden` 逐实例读**，绝不按类型。`trap_027_stone` 132 可见 / 3 隐藏，按类型判会错。
3. **行号不要翻转**。`position.row` 已经是自上而下，与 `GameMap.tiles` 同序。**`maps.py:184` 的 `matrix = list(reversed(matrix))` 只管 `mapData.map`，与装置无关，绝不能动**（见 §6 红线 R1）。
4. **`characterInsts` 单独放**，不要混进 `devices`（见 §4.5）。
5. **一个真实的三选一实例**（好梦在何方）：`tokenInsts` 里 `(2,7)` 和 `(5,4)` 各堆了 3 个隐藏箱
   （`trap_065_normbox` / `trap_066_rarebox` / `trap_068_badbox` 各一），
   聚合后这两格各只保留 1 个 `Device`，`stack_size=3`。**若不做聚合，这两格会画出 3 个重叠图标，
   且阻挡判定会算成 3 个实体。**
6. **解析失败必须静默降级**：任一装置查不到 catalog 时，记 `category="D"`（装饰）并计数告警，**绝不能让整关解析失败**。

#### 4.3.3 稳健性要求

| 场景 | 行为 |
|---|---|
| `predefines` 不存在 / 是 null | `devices = []`，不报错 |
| `tokenInsts` 是 null | 同上 |
| `inst` 缺失 | 跳过该实例，计数 |
| `characterKey` 不在 catalog | 记为 D 类，计数告警 |
| `position` 越界 | 跳过，计数；**不要 clamp**（越界说明数据有问题，clamp 会掩盖） |
| 同一格多个可见装置 | **保留全部**（真实同时存在），不聚合 |

### 4.4 S2：寻路层

#### 4.4.1 改动点（极小，因为管道已经存在）

**好消息：`find_path` / `analyze_route` / `analyze_all` 三层的 `blocked` 参数全都已经存在，且已经打通。**

```python
# core/routes.py:245
def analyze_route(game_map, route, move_speed=1.0, blocked=None, allow_diagonal=None)

# core/routes.py:410
def analyze_all(game_map, move_speed=1.0, blocked=None, allow_diagonal=None)
```

**坏消息：6 个真实调用点里，没有一个传装置。**

| 调用点 | 现状 | 应改为 |
|---|---|---|
| `core/routes.py:410` `analyze_all` | 定义（非调用点） | 本轮唯一改动点 |
| `core/sandbox.py:331` | `RT.analyze_all(gm, ...)` | 传 `gm.route_blocking_cells()` |
| `core/sandbox.py:773` | `RT.analyze_all(gm, blocked=set(self.boxes))` | **合并**装置格：`set(self.boxes) \| gm.route_blocking_cells()` |
| `ui/path_panel.py:1569` | `RT.analyze_all(gm, move_speed=speed, ...)` | 传装置格 |
| `ui/sandbox_panel.py:909` | `RT.analyze_all(gm)` | 传装置格 |
| `mcp/tool_maps.py:101` | `R.analyze_all(gm, move_speed=1.0)` | 传装置格 |
| `mcp/tool_routes.py:33` | `R.analyze_all(gm, move_speed=move_speed)` | 传装置格 |

**最小改动方案**：在 `routes.py` 里加一个统一入口，避免逐个调用点改：

```python
def analyze_all(game_map, move_speed=1.0, blocked=None, allow_diagonal=None,
                include_devices=True):
    if include_devices:
        blocked = set(blocked or ()) | game_map.route_blocking_cells()
    ...
```

这样**所有 9 个调用点自动生效**，且留了 `include_devices=False` 的逃生口（用于对比实验、回归基线）。

**推荐做法**：默认 `True`，但把「是否含装置」显式写进 `RouteAnalysis`（`devices_applied: bool`），让上位代码和测试能分辨。

#### 4.4.2 必须同时做的「装置可破坏」语义

**这是本方案最容易被做错的地方。** 若只做「装置 = 永久障碍」：

- 全库 **3028 条路线变不可达**（已实测）；
- 用户在沙盘里会看到敌人卡死在木箱前永远不动；
- 与真实游戏完全不符（木箱会被打掉）。

因此 S2 必须至少包含**最小可破坏语义**：

| 方案 | 描述 | 采用 |
|---|---|---|
| S2-a | 只当障碍，不做破坏 | ❌ 会假性不可达 |
| **S2-b** | **当障碍参与寻路；同时记录「首个被挡住的格」，沙盘里给该装置一个 `hp` 并允许被破坏** | ✅ **本阶段采用** |
| S2-c | 完整状态机（含攻击动画、受击结算） | 留 S5 |

**S2-b 的具体规则：**

1. `analyze_all` 传 `blocked` 得到「理想绕路」路径（B 路径）；
2. 沙盘推进时，若敌人路径被装置挡住且**无路可绕**（`reachable=False`），则该敌人停下攻击该装置；
3. 装置 HP 按敌人 `atk` 与 `attack_interval` 扣减；
4. HP ≤ 0 → 该装置从 `blocked` 移除 → 后续敌人走直路；
5. **已被摧毁的装置要在沙盘状态里持久化**，不能每帧重算丢失。

#### 4.4.3 `E_NUM` 占位路线（其实已经处理好了，但别踩回去）

好梦在何方原始 `routes` 有 53 条，其中 8 条 `motionMode == "E_NUM"`，`startPosition`/`endPosition` 都是 `{"row":0,"col":0}`、`checkpoints` 为 `null`——这是剧情占位，不是真路线。

**`parse_level` 已经把它们丢掉了**（`models.py` 的 `GameMap.route_by_index` 文档注明全库丢弃 9663 条）。所以 `gm.routes` 只有 47 条，`Route.index` 从 8 起跳。**这是好事，不要改。**

但有三个连带影响，实现时必须知道：

| 影响 | 说明 |
|---|---|
| **`Route.index` ≠ 列表下标** | 47 条路线里 `index` 是 8…52 和 1000/1001。任何地方写 `gm.routes[i]` 都会取错，**必须用 `gm.route_by_index(i)`** |
| **`extraRoutes` 会进 `routes`** | 该关有 2 条 `extraRoutes`（从隐藏箱格 `(2,7)`/`(5,4)` 出发），索引 1000/1001，`motionMode` 是 `WALK`，是真路线 |
| **统计要用 `route_index`** | A/B 对照、回归基线、UI 显示全部按 `Route.index` 记，别用 `enumerate` 的下标 |

**要求：新增的装置逻辑不得修改 `E_NUM` 的过滤行为。** 若为了让「装置格不可达」报错而保留 `E_NUM`，会把 8 条假路线算进来，让所有统计虚高。

### 4.5 可操作装置（S4）

用户提到的「有些装置是可以操作的」。可操作装置同样在 `tokenInsts` 里，判定依据是 `character_table` 的 `profession == "TRAP"` 且该装置在游戏内可被玩家点击操作（典型：可部署的临时设施、可开关的机关）。

**由于 `tokenInsts` 本身没有「可操作」字段，需从 catalog 的 `operable` 标记读取。**
S1 先用人工规则生成初版 `operable`：

| 判据 | 视为可操作 |
|---|---|
| 装置有 `skills[].unlockCond` 且技能是 `MANUAL` / `TRIGGER` 类型 | 是 |
| 装置名含「开关 / 控制 / 发射 / 召唤」 | 是（待人工核） |
| `blockCnt > 0` 的纯障碍 | 否 |
| 纯装饰（`trap_048_neonlamp` 城市霓虹等） | 否 |

**S4 只做「点一下有反馈」，不做完整玩法**（完整玩法属 S5 及以后）。理由是：可操作的语义差异极大（有的是开灯、有的是召唤、有的是改地形），一次做完必然出错。

**关于 `characterInsts`（122 关）：**

| 选项 | 说明 | 建议 |
|---|---|---|
| 完全不接 | 最简单，但那 122 关的友方 NPC 会缺失 | 可接受（阶段一） |
| 接入但只作为「阻挡单位」 | 复用 `Device` 结构，`category="B"` | ✅ **推荐** |
| 完整模拟友方 AI | 工作量巨大 | 不做 |

### 4.6 S3：渲染层

#### 4.6.1 现状约束

| 约束 | 说明 |
|---|---|
| 静态层缓存键 | `MapRenderer._master_static_key()`（`map_render.py:534`）**只允许包含「沙盘是否激活」这个布尔量**，加任何逐帧变化的状态会让每帧重建静态层（实测 60 ms/次） |
| 装置图标 | **一个都没有**（§2.4） |
| 绘制顺序 | `render()` = `_scaled` → `_draw_enemies` → `_draw_portal_link` → `_draw_sandbox` → `_draw_spawn_hover` → `_draw_hover_layer` |
| 单元格尺寸 | `MASTER_CELL=48`，`SS=2` |

#### 4.6.2 放置层：静态还是动态

**装置位置在整局内不变，应该进静态层。**
但静态层的 key 规则极严（§6 红线 R2），因此：

| 方案 | 做法 | 采用 |
|---|---|---|
| 进静态层 | 把装置画进 `_ensure_master` 的合成 | ✅ **推荐**（装置数与关卡绑定，一关内不变） |
| 每帧重画 | 在 `render()` 里加 `_draw_devices` | ❌ 浪费，且会拉低本已只有 0.9 fps 的性能 |

**若装置有「被摧毁」状态变化**（S5），则该装置必须移到动态层。届时按「静态层只画完好装置，被摧毁的装置改由动态层覆盖」处理——**不要为了一个格子重建整个静态层**。

#### 4.6.3 视觉方案（三级降级）

按资源可用性从好到差：

| 级别 | 做法 | 前提 |
|---|---|---|
| **L1** | 装置图标 PNG（`cell × 0.42`，与敌人图标统一尺寸） | 需要补 207 张图标资源 |
| **L2** | 几何图形 + 中文首字 | 无资源也能做 |
| **L3** | 纯色块 + 类别色 | 最简，先跑通链路 |

**推荐先做 L2，跑通后按需升 L1。**

L2 规格：

| 类别 | 底色 | 形状 | 标注 |
|---|---|---|---|
| A 改路型 | `#8B5A2B`（棕） | 圆角矩形 | 中文名首字（碎石→「碎」） |
| B 实体阻挡型 | `#6B7280`（灰） | 圆角矩形 | 首字 |
| C 功能型 | `#2563EB`（蓝） | 圆形 | 首字 |
| D 装饰型 | `#9CA3AF`（浅灰） | 小圆点 | **不画字** |

尺寸：`cell × 0.34`（比敌人 `0.42` 略小，避免抢视觉）。
透明度：`alpha=210`，让下面的地形纹理仍可见。
文字：白色描边 + 深色填充，字号 `cell × 0.22`。

**同时必须做的「N 选 1」角标**：`stack_size > 1` 时，右下角画一个 `×N` 小角标（或 `?` 图标），**绝不能把 N 个方块叠画在同一格**。

#### 4.6.4 与敌人的层级关系

装置在地面，敌人在装置之上。绘制顺序：

```
地形 → 装置（静态层） → 敌人（动态层） → 干员 → 悬浮提示
```

现有顺序里敌人和干员都在动态层，只需保证装置进静态层即可自然满足。

#### 4.6.5 性能预算

好梦在何方 11 个装置、全库单关最多 91 个装置。静态层一次性绘制，**对 0.9 fps 的现状没有可测影响**（静态层本来就每关只重建一次）。
**唯一风险**：若把装置画进每帧路径，则每帧多 91 次 alpha composite——按现有测量（1361 敌人 = 933 ms），91 个装置约 **62 ms/帧**，会再砍掉约 6% 帧率。**所以必须进静态层，这是硬要求。**

#### 4.6.6 悬浮提示

沿用 `map_canvas._enemy_at()`（`map_canvas.py:441`）的命中测试模式，新增 `_device_at(row, col)`。
悬浮时显示：`中文名 · 类别 · HP/blockCnt · 技能摘要`。
**不做**：点击查看详情弹窗（超出本方案范围）。

### 4.7 S5：装置状态机（仅列需求，不展开）

留到下一份文档，这里只定接口：

```python
class DeviceState:
    device: Device
    hp: float
    destroyed: bool
    destroyed_at: Optional[float]     # 沙盘时间
    blocked_enemy_uids: Set[int]
```

沙盘 `pose_at()` 每帧需要：
1. 该时刻哪些装置已被摧毁；
2. 已摧毁的格子从 `blocked` 移除；
3. 被摧毁的装置不再画。

**性能红线**：`blocked` 集合每帧变化会导致 `analyze_all` 每帧重算（现状 `pose_at` 已 33 ms 热路径）。**S5 必须做「按装置摧毁事件分段预计算」**，不能每帧重跑寻路。详见 §6 红线 R5。

## 六、红线（违反必炸）

| # | 红线 | 原因 |
|---|---|---|
| **R1** | **不许动 `maps.py:184` 的 `matrix = list(reversed(matrix))`** | 装置 `position.row` 与 `GameMap.tiles` 同序（都已自上而下）。动了会让全部 11 个碎石落到墙上。若有疑问，重跑 §5.1 #5 |
| **R2** | **`_master_static_key()` 只许包含「沙盘是否激活」** | 加入任何逐帧状态会让静态层每帧重建（实测 60 ms/次）。装置位置一关内不变，可以进静态层，但**不能把装置状态（HP/摧毁）写进 key** |
| **R3** | **`hidden` 必须逐实例读，绝不按类型** | `trap_027_stone` 132 可见 / 3 隐藏。按类型判会同时错两边 |
| **R4** | **A/B/C/D 分类必须人工复核签字** | `blockCnt` 与技能描述存在 8 处冲突（§3.5）。AI 单方面推断必然出错，且错在寻路这种「看起来对其实全错」的地方 |
| **R5** | **S5 不许每帧重跑寻路** | `pose_at` 热路径已 33 ms，`analyze_all` 全量重算更慢。必须按摧毁事件分段预计算 |
| **R6** | **不许把装置逻辑写进 `arrival_time()` / `Timeline.span()`** | 路线分析必须与沙盘无关。装置是沙盘状态，只属于沙盘层 |
| **R7** | **不许把 15 MB `character_table.json` 打进包** | 只需 207 种，提取成约 60 KB 的 `token_catalog.json` |
| **R8** | **解析失败必须降级，不许让整关失败** | 一个未知 `characterKey` 不该让整张图打不开 |
